# 채용 콘솔 `/admin/recruit` — 디자인 브리프 (Claude Design 용 프롬프트)

아래 블록을 그대로 Claude Design 에 붙여넣는다. 데이터·토큰·제약은 전부 실제 값이다.
완성된 디자인은 `docs/design/` 에 두고 구현 시 참조한다.

---

## 프롬프트 (여기부터 복사)

StayOps 라는 숙박업 운영 관리 제품의 **관리자 데스크톱 콘솔**에 새 화면 하나를 디자인해 줘.
새 디자인 언어를 만드는 게 아니라, **이미 있는 콘솔 안에 자연스럽게 들어가는 화면**이어야 해.

### 무엇을 하는 화면인가

도쿄에서 숙박시설(호텔·게스트하우스) 여러 채를 운영하는 회사야. 객실 청소 스태프, 프론트,
시설 관리 인력을 **상시 채용**해. 지원은 별도 채용 사이트에서 받고, 그 지원서가 이 콘솔로 들어와.

이 화면에서 담당자가 하는 일:

1. 새로 들어온 지원서를 **훑어보고 골라낸다** (하루 몇 건, 몰릴 땐 하루 10건 이상)
2. 한 건을 열어 **이력서와 지원 내용을 읽는다**
3. 서류검토 → 면접 → 합격/불합격으로 **상태를 옮긴다**
4. 합격시키면 **초대코드를 발급**해 그 사람이 앱에 가입하게 한다

쓰는 사람은 사무 담당자 2~3명. 하루 종일 보는 화면은 아니고, **알림 받고 들어와 몇 건 처리하고
나가는** 패턴이야. 그래서 "지금 처리할 게 몇 건인지"가 즉시 보여야 해.

### 실제 데이터 (지어내지 말고 이걸 써)

지금 194건이 들어와 있어. 10개월치(2025년 11월 ~ 2026년 9월), 월 평균 20건 정도야.

한 건에 담긴 정보:

- **공고** — 직무명(객실 청소 스태프 / 프론트 스태프 / 시설 관리), 고용형태(정사원 / 아르바이트)
- **기본** — 이름, 나이, 성별, 전화번호, 카카오 ID, 주소, 통근 시간, 유니폼 사이즈
- **체류 자격** — 국적, 비자 종류, 비자 만료 시기 ← *외국인 채용이 많아 실제로 판단에 쓰인다*
- **근무 조건** — 가능 요일(복수), 주 몇 회, 근무 예정 기간, 시작 가능일
- **경험** — 동종업계 경험 유무, 해본 업무(베딩 / 객실 청소 / 인포메이션 / 기타), 지원 경로, 지원 동기
- **첨부** — 이력서 파일 (194건 중 **89건만** 있음. 절반 이상은 첨부가 없다)

주의할 특징:

- **첨부가 없는 지원자가 절반이 넘는다.** 첨부 유무로 화면이 무너지면 안 돼.
- 이력서 형식이 제각각이야 — PDF, 한글(.hwp), 엑셀(.xlsx), **아이폰 사진(.heic)**. 브라우저에서
  바로 못 여는 형식이 섞여 있어.
- 값이 자유 입력이라 짧기도 길기도 해. 지원 동기는 한 줄인 사람도, 열 줄인 사람도 있어.
- 구 지원 폼으로 받은 44건은 항목이 일부 비어 있어. **빈 값이 자연스럽게 보여야 해.**
- 같은 사람이 몇 달 뒤 다시 지원하는 경우가 있어(재지원).

상태는 다섯 가지: **접수 / 서류검토 / 면접 / 합격 / 불합격**. 지금은 194건 전부 「접수」야.

### 디자인 시스템 (반드시 이 토큰을 써)

따뜻한 아이보리 바탕 + 진한 잉크 네이비 강조. **라이트 모드 전용**이야(다크 모드 없음).

```css
/* 바탕·카드 */
--bg:        hsl(42 36% 95%);    /* 페이지 바탕 */
--bg2:       hsl(42 30% 93%);
--card:      hsl(44 52% 98.5%);  /* 카드 표면 */
--card2:     hsl(44 40% 97%);    /* 행 hover */
/* 글자 */
--ink:       hsl(222 28% 14%);
--ink-soft:  hsl(222 20% 28%);
--muted:     hsl(222 10% 44%);
--faint:     hsl(222 10% 62%);
/* 선 */
--line:      hsl(40 20% 84%);
--line-soft: hsl(40 24% 89%);
/* 강조 */
--primary:      hsl(223 46% 32%);
--primary-ink:  hsl(223 54% 22%);
--primary-soft: color-mix(in oklab, hsl(223 46% 32%) 8%, hsl(44 52% 98.5%));
/* 상태색 — 배지·칩에 쓴다 */
--open:   hsl(223 46% 36%);  --open-bg:   hsl(223 42% 94%);
--done:   hsl(146 50% 32%);  --done-bg:   hsl(146 44% 92%);
--warn:   hsl(35 80% 38%);   --warn-bg:   hsl(38 82% 92%);
--info:   hsl(206 70% 40%);  --info-bg:   hsl(206 66% 93%);
--danger: hsl(4 62% 46%);    --danger-bg: hsl(6 70% 95.5%);
/* 모양 */
--r-card: 16px;
--r-pill: 999px;
--sh-card: 0 18px 44px -34px rgba(20,32,43,0.5);
--sh-pop:  0 24px 60px -24px rgba(20,32,43,0.45);
/* 글꼴 */
--serif: "Noto Serif", Georgia, serif;   /* 제목·숫자 강조에만 */
--mono:  "Geist Mono", ui-monospace, monospace;  /* 전화번호·ID·날짜 */
```

본문은 시스템 산세리프. 한국어·일본어·영어가 같은 화면에 섞여도 깨지지 않아야 해.

왼쪽에는 **짙은 에스프레소 색 사이드바**(`hsl(24 30% 18%)`)가 이미 있어. 그건 그리지 않아도 돼 —
**본문 영역만** 디자인해 줘.

### 이미 있는 것 (새로 만들지 말고 이 형태를 따라가)

이 콘솔에는 다른 화면들이 이미 쓰고 있는 패턴이 있어. **똑같은 개념은 똑같이 생겨야 해.**

- **필터 줄** — 화면 상단 가로 한 줄. 알약 모양 세그먼트(상태 탭) + 드롭다운 + 검색 입력
- **표** — 테두리 없는 가로줄 구분, 헤더는 작은 대문자 라벨, 행 hover 시 `--card2`
- **상태 배지** — 알약 모양, 위 상태색 조합 사용
- **오른쪽 상세 패널** — 행을 클릭하면 **새 페이지로 안 가고** 오른쪽에서 슬라이드 인. 뒤는 어둡게.
  패널 안은 상단 헤더(제목·배지) + 스크롤 본문 + 하단 액션 바
- **요약 카드** — 화면 맨 위 가로로 몇 개. 큰 숫자 + 라벨 + 부가 설명
- **날짜 선택** — 292px 폭 팝오버 달력(16px radius, 34px 셀). **브라우저 기본 `<input type="date">`
  는 절대 안 써.** 기간 선택은 이 팝오버 하나로 처리해.
- **내보내기** — Excel·PDF 두 개가 항상 한 쌍으로 붙어 다녀

### 만들어야 할 화면·상태

한 페이지 안에 아래를 전부 보여 줘 (스크롤로 이어 붙여도 되고 섹션을 나눠도 돼):

1. **목록 화면 (기본)** — 요약 + 필터 + 지원자 목록. 실제 데이터 느낌으로 12행 이상 채워 줘
2. **상세 패널 열린 상태** — 한 지원자의 전체 정보. 첨부 **있는** 경우
3. **상세 패널 — 첨부 없는 경우** (194건 중 절반이 이렇다)
4. **상태 변경 UI** — 접수 → 서류검토 → 면접 → 합격/불합격을 어떻게 옮길지
5. **합격 처리 흐름** — 합격시키면 초대코드가 발급된다. 그 결과를 어떻게 보여줄지
6. **빈 상태** — 필터 결과가 0건일 때
7. **재지원 표시** — 같은 사람이 다시 지원한 경우 어떻게 알려줄지

### 네가 판단해 줬으면 하는 것

정답을 정해두지 않았어. 이유와 함께 골라 줘.

- **표인가 카드인가.** 정보가 20개 항목이라 표에 다 못 넣어. 목록에서 무엇을 보여주고 무엇을
  상세로 미룰까? 담당자가 목록만 보고 「이 사람 열어볼 가치가 있다」를 판단할 수 있어야 해.
- **체류 자격을 얼마나 앞에 둘까.** 비자 만료가 3개월 남은 지원자는 채용 판단이 달라져. 그렇다고
  국적을 목록 맨 앞에 큼직하게 두는 건 차별적으로 보일 수 있어. 어디까지가 적절할까?
- **이력서를 어떻게 보여줄까.** PDF·이미지는 미리보기가 되지만 .hwp·.xlsx 는 안 돼. 형식에 따라
  다르게 보이는 게 나은지, 아예 일관되게 「내려받기」로 통일하는 게 나은지.
- **첨부 없는 지원자를 어떻게 다룰까.** 결함처럼 보이면 안 되지만, 첨부가 있는 쪽이 검토 우선순위가
  높은 것도 사실이야.
- **상태 전환을 목록에서 바로 할 수 있게 할까, 상세에서만 할까.**

### 지켜야 할 제약

- **한국어·일본어·영어 3개 국어**로 나가는 제품이야. 「합격」이 일본어로는 「採用決定」, 영어로는
  「Hired」— 버튼과 배지 폭이 **글자 수에 따라 무너지지 않아야** 해. 가장 긴 경우를 기준으로 그려 줘.
- **개인정보 화면이야.** 지원자의 이름·전화·주소·비자가 한 화면에 모여 있어. 어깨너머로 보이는
  상황을 고려해서, 필요 이상으로 크게 노출하지 말아 줘.
- **이름은 지어내서 써.** 예시 데이터에 실제로 보일 법한 한국·일본 이름을 섞어 줘.
- 화면 폭 1280px 기준. 1440px 에서도 자연스럽게.
- 아이콘은 lucide 계열 선 아이콘 느낌으로.

### 결과물

자체 완결된 HTML 한 장으로 줘. 폰트 외 외부 리소스 없이, CSS 는 인라인으로.
각 섹션 위에 **왜 그렇게 설계했는지 한두 줄** 설명을 붙여 줘 — 구현할 때 그 의도를 지켜야 하니까.

## 붙일 때 참고 (디자인 완성 후 구현용 메모)

- 실제 구현은 `src/components/admin/recruit/` 아래 + `recruit-console.css`. CSS 변수는 `--rc-*`
  접두어를 쓴다 — `.adm` 스코프가 클래스는 막아 주지만 **변수는 상속되므로** globals 의 Tailwind
  토큰과 같은 이름을 재정의하면 공용 컴포넌트가 조용히 다른 색이 된다(`admin-console.css` 머리말).
- 상세 패널은 `?application=<id>` 쿼리로 연다. `ComplaintDetailPanel` 과 같은 방식이며 새 라우트를
  만들지 않는다.
- 날짜·내보내기·드롭다운은 `src/components/admin/shared/` 것을 그대로 쓴다. 새로 만들지 않는다
  (CLAUDE.md §4a·§4b).
- 문구는 전부 `dictionary` 에 ko/ja/en 을 함께 넣는다. 하드코딩 금지.
- 권한: `owner` / `senior_managing_director` / `office_admin` 만 열람.
