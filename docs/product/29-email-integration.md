# 29. 이메일(Gmail) 연동 — 기획

**상태: 기획 단계 (2026-08-04). 구현 착수 전.**

## 1. 왜 만드는가

지금은 운영 메일을 처리하려면 Gmail 을 따로 열어야 한다. 확인 → 답장 → 삭제 → 폴더 정리를
StayOps 밖에서 하고, 그 결과가 StayOps 기록과 이어지지 않는다.

**다만 목표는 "Gmail 을 다시 만드는 것"이 아니다.** 메일 클라이언트를 처음부터 만들면 몇 달이
걸리고, 만들어도 Gmail 보다 나을 수 없다. 이 기능의 가치는 하나뿐이다:

> **운영에 관련된 메일만 골라서, StayOps 안에서 곧바로 업무로 바꾼다.**

Airbnb 문의 메일을 읽고 그 자리에서 컴플레인으로 만들어 객실·예약에 연결하는 것 — Gmail 은
그걸 못 한다. 목록·답장만 옮겨 오면 "Gmail 을 더 불편하게 만든 것"에 그친다. §7 의 3단계가
이 기능의 존재 이유다.

## 2. 확정된 결정 (2026-08-04)

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 계정 종류 | **Google Workspace(회사 도메인)** | 구글 심사·CASA 평가 없이 내부 앱으로 게시 가능 |
| 메일함 범위 | **공용 운영 메일함 + 개인 메일함 둘 다** | 운영 대표 주소와 담당자 개인 메일이 모두 쓰인다 |
| 본문 보관 | **저장하지 않는다 — 열 때마다 Gmail API 조회** | 고객 개인정보를 우리 DB 에 쌓지 않는다 |

### 2.1 Workspace 라는 점이 결정적이다

Gmail API 의 읽기·발신·라벨 변경 권한은 구글이 **restricted scope** 로 분류한다. 외부 앱으로
게시하면 OAuth 심사 + **CASA Tier 2 보안 평가**(연 $500~4,500, 수 주 소요)를 매년 받아야 하고,
심사 없이 테스트 모드로 쓰면 **refresh token 이 7일마다 만료**되어 매주 다시 로그인해야 한다 —
실무에서 못 쓴다.

Workspace 도메인이면 OAuth 동의 화면을 **내부(Internal)** 로 게시할 수 있고, 그 조직 계정에
한해 심사·평가가 면제된다. **이 조건이 깨지면(개인 Gmail 로 바뀌면) 이 기획 전체를 다시 봐야
한다.**

### 2.2 본문을 저장하지 않는 이유

메일 본문에는 투숙객 이름·연락처·결제 관련 내용이 섞인다. 우리 DB 에 쌓는 순간 보존 기간·삭제
요청 대응·RLS 설계를 전부 새로 정의해야 하고, 유출 시 피해 범위가 커진다. 조회가 조금 느린
대신 **우리가 보관하지 않는다는 사실 자체가 가장 강한 방어**다.

대가로 포기하는 것: 우리 쪽 전문 검색. 검색은 Gmail 의 검색 API 에 위임한다(§6).

## 3. 권한 범위(scope)

| scope | 쓰는 곳 |
| --- | --- |
| `gmail.readonly` | 목록·본문 조회 |
| `gmail.modify` | 읽음 처리, 라벨 이동, 휴지통 |
| `gmail.send` | 답장 발송 |

**`https://mail.google.com/`(전체 권한)은 쓰지 않는다.** 그 권한이 추가로 주는 것은 사실상
**영구 삭제**뿐인데, 사용자가 "삭제"라고 말할 때 기대하는 동작은 휴지통 이동이다. 운영 메일을
StayOps 에서 복구 불가능하게 지울 수 있어야 할 이유가 없다.

## 4. 인증 설계

**로그인용 구글 OAuth 와 분리한다.** 현재 `signInWithOAuth({ provider: "google" })` 는 인증만
하고 Gmail 권한도, 오프라인 토큰도 받지 않는다. 여기에 Gmail scope 를 얹으면 **로그인하는 모든
사람에게 메일 권한을 요구**하게 되어 잘못된 설계다.

- 메일 연동은 **별도 연결 흐름**으로 둔다(설정 화면의 "메일함 연결" 버튼).
- `access_type=offline` + `prompt=consent` 로 **refresh token** 을 받는다.
- refresh token 은 **service-role 경로에서만** 다루고 클라이언트로 절대 내려보내지 않는다.
  저장 위치는 Supabase Vault 사용을 우선 검토한다(§9 미결).
- 연결 해제 시 구글 쪽 토큰도 revoke 한다. 우리 DB 에서 지우는 것만으로는 권한이 살아 있다.

## 5. 데이터 모델 (초안)

본문을 저장하지 않으므로 **메시지 테이블은 만들지 않는다.** 필요한 것은 "누가 어느 메일함을
연결했는가"와 감사 기록뿐이다.

```txt
email_accounts
  id
  organization_id            -- 조직 격리
  scope: 'shared' | 'personal'
  email_address
  google_subject             -- 구글 계정 식별자
  refresh_token_ref          -- Vault 참조 (평문 토큰을 컬럼에 두지 않는다)
  connected_by_user_id
  status: 'active' | 'revoked' | 'error'
  last_error_at, last_synced_at
```

- `scope = 'shared'` — 조직당 여러 개 가능(info@, reservation@ 등). 볼 수 있는 사람은 권한으로
  결정한다.
- `scope = 'personal'` — `connected_by_user_id` 본인만 볼 수 있다. **관리자도 못 본다.**
  개인 메일을 회사 시스템에서 열 수 있게 만드는 순간 노무·프라이버시 문제가 되므로, 이 경계는
  UI 가 아니라 서버에서 강제한다.
- 발송·삭제·라벨 변경은 `audit_logs` 에 남긴다. **공용 메일함은 누가 답장했는지 추적할 수 없으면
  안 된다** — Gmail 에는 "StayOps 를 통해 홍길동이 보냈다"는 정보가 남지 않기 때문이다.

## 6. 화면 (초안)

- **모바일** — 운영 중 확인·답장이 주 목적. 목록 → 본문 → 답장. 하단 탭 후보이지만 탭 4개
  제한이 있으므로 편집 시트에서 고르게 한다(`docs/product/16-mobile-navigation.md` 계약).
- **콘솔** — 정리 작업(라벨 이동, 대량 처리)과 공용 메일함 관리. 기존 콘솔 공용 프리미티브를
  그대로 쓴다(`CLAUDE.md` §4).
- **검색** — 우리가 색인하지 않으므로 Gmail 검색 문법을 그대로 넘긴다. 사용자에게는 검색창
  하나로 보이고, 뒤에서 `users.messages.list?q=` 로 위임한다.

## 7. 단계

| 단계 | 범위 | 비고 |
| --- | --- | --- |
| **v1** | 공용 메일함 1개 연결 · 목록 · 본문 · 답장 · 읽음 · 휴지통 | 개인 메일함은 모델만 준비하고 UI 는 v2 |
| **v2** | 개인 메일함 연결 · 라벨(폴더) 이동 · 검색 · 첨부 다운로드 | |
| **v3** | **메일 → 컴플레인 / 유지보수 / 투두 전환**, 예약번호·객실 자동 인식·연결 | 이 기능의 존재 이유 |

공용·개인을 "둘 다"로 정했지만 **한 번에 열지 않는다.** 모델은 처음부터 `scope` 로 둘을 담되,
v1 은 공용만 노출한다. 개인 메일함은 프라이버시 경계 설계가 더 필요하고, 그걸 v1 에 끼워 넣으면
검증할 표면이 두 배가 된다.

## 8. 위험

- **HTML 메일 렌더링은 XSS 통로다.** 외부에서 온 임의의 HTML 을 그대로 그리면 안 된다. 정화 후
  `sandbox` iframe 에 격리하고, 원격 이미지는 기본 차단(추적 픽셀)한다. **v1 에서 반드시 처리한다.**
- **답장 스레드가 깨지기 쉽다.** `In-Reply-To` / `References` 헤더를 원본에서 그대로 이어받지
  않으면 받는 쪽에서 새 대화로 뜬다. 고객에게는 "말귀를 못 알아듣는 회사"로 보인다.
- **공용 메일함의 동시 처리.** 두 사람이 같은 메일에 각각 답장할 수 있다. v1 은 감사 기록으로
  사후 추적만 하고, 담당자 지정(assign)은 실제 충돌이 관찰된 뒤에 넣는다.
- **토큰 만료·해지.** 비밀번호 변경, 관리자의 앱 차단, 계정 정지로 refresh token 이 죽는다.
  죽었을 때 화면이 조용히 비면 안 되고 "다시 연결해 주세요"가 떠야 한다.
- **개인 메일함의 노무 이슈.** §5 참고. 관리자 열람 불가를 서버에서 강제한다.

## 9. 미결

1. **refresh token 저장 위치** — Supabase Vault vs 애플리케이션 레벨 암호화. Vault 가 낫다고
   보지만 이 저장소에 선례가 없어 검증이 필요하다.
2. **동기화 방식** — 열 때마다 조회(단순) vs Gmail push 알림(watch + Pub/Sub, 빠르지만 인프라
   추가). v1 은 조회로 시작한다.
3. **알림** — 새 운영 메일 도착을 StayOps 알림으로 띄울지. 알림은 개발 막바지에 전 기능 일괄로
   붙이기로 한 정책에 따라 그때 함께 결정한다.
4. **어느 메일이 "운영 메일"인가** — 전부 보여줄지, 라벨/발신자로 거를지. v3 의 자동 전환 정확도가
   여기에 달려 있다. 실제 메일함을 한 번 보고 정해야 한다.
