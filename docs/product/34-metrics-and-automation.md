# 가동률 · 매출 · 자동화

> 상태: **기획 확정 · 개발 착수 전** (2026-09-16)
> 상위: [31-stay-ari-migration-overview.md](31-stay-ari-migration-overview.md) · 진입: [32-ops-admin-area.md](32-ops-admin-area.md)

전환 순서에서 **가장 먼저** 넘기는 부분이다. 읽기라 위험이 없고, 숫자가 저쪽과 맞는지 대조하면
「우리 데이터가 맞다」는 확신이 생긴다. 그 확신 위에서 캘린더 쓰기를 켠다.

## 지표 정의

저쪽이 쓰는 계산식(`functions/modules/revenueDashboardData.js`). **정의를 그대로 가져간다** —
숫자가 달라지면 대조가 불가능해진다.

| 지표 | 계산 |
| --- | --- |
| 매출 | 예약의 `netRevenue ?? totalPrice ?? price` 합 |
| 판매 객실박 | 예약이 차지한 밤 수 |
| 전체 객실박 | 객실 수 × 기간 일수 |
| 점유율 | 판매 객실박 ÷ 전체 객실박 |
| **ADR** | 매출 ÷ **판매** 객실박 |
| **RevPAR** | 매출 ÷ **전체** 객실박 |
| 객실당 매출 | 매출 ÷ 객실 수 |

**ADR 과 RevPAR 의 분모가 다르다.** ADR 은 판 것만, RevPAR 은 팔 수 있었던 전부. 섞으면 조용히
틀린다.

**겹치는 기간 배분**: 예약이 조회 기간의 양끝을 넘길 때 매출을 어떻게 나눌지 규칙이 있다
(저쪽 주석: *"Revenue follows the app Revenue Dashboard overlap allocation"*). 구현 전에 그 규칙을
정확히 읽어 와야 한다 — **여기가 어긋나면 월 경계에서 숫자가 안 맞는다.**

## 데이터 정합성 — 켜기 전 필수

매출은 예약의 가격에서 나온다. StayOps 의 현재 상태:

| | |
| --- | --- |
| 취소 제외 예약 | 2,767건 |
| 가격 있음 | **2,400건 (87%)** |
| **가격 없음** | **367건 (13%)** |

**13% 가 비면 매출이 실제보다 낮게 나온다.** 그것도 「조금 낮게」가 아니라 어느 채널·어느 기간이
통째로 빠지는 식일 수 있다.

> **점검 시점은 개발 이후로 미룬다**(2026-09-16 결정). 지금 원인을 파느라 설계를 멈추지 않는다.
> 다만 **매출 화면을 켜기 전에는 반드시 해결한다.** 틀린 매출은 안 보이는 것보다 나쁘다 —
> 없으면 「아직 안 됐구나」 하지만, 틀리면 그 숫자로 판단한다.

점검할 것: 어느 채널이 비는가 · 어느 기간이 비는가 · Beds24 원본에는 있는가(있다면 우리 동기화가
빠뜨린 것) · `invoiceItems` 로 받아와야 하는가(현재 0건).

`functions/index.js` 의 스케줄 함수. **전부 Asia/Tokyo 기준.**

**예약·건물·리뷰 동기화는 가져오지 않는다.** StayOps 가 이미 같은 일을 한다. 중복으로 돌리면
Beds24 크레딧만 두 배로 쓴다.

**가격 동기화는 가져와야 한다.** 매출 계산의 재료이고 이쪽에 없다. 위 「데이터 정합성」의 367건이
여기와 관련 있을 가능성이 높다.

### 실행 기반이 다르다

| | 저쪽 | StayOps |
| --- | --- | --- |
| 스케줄 | Firebase Cloud Functions (`onSchedule`) | **GitHub Actions** + Vercel Cron |
| 이유 | — | 2026-07-22 에 Vercel 크론이 며칠 발화하지 않아 예약 5일치가 조용히 비었다. 이후 새 스케줄은 외부 트리거를 쓴다 |

**옮기면서 GitHub Actions 로 바꾼다.** 기존 워크플로(`beds24-reconcile.yml` ·
`recruit-sync.yml`)와 같은 방식이다.

> 다만 GitHub Actions 의 예약 시각은 **보장되지 않는다.** 2026-09-11 실측에서 5분 주기가 실제로는
> 40분~3시간 40분 간격이었다. **「08:45 정각에 슬랙」 같은 요구는 지킬 수 없다.** 시간이 중요한
> 리포트는 Vercel Cron(하루 1회, 상한 2개)이나 외부 크론 서비스를 검토한다 — 개발 시 결정.

## 전환 — 켜는 순간 저쪽을 끈다

자동화는 **한 쌍으로 움직인다.** 이쪽을 켜고 저쪽을 그대로 두면 **슬랙에 리포트가 두 번 온다.**

```
① 이쪽 구현 — 발송하지 않는 상태로 둔다(드라이런: 만들어질 메시지를 로그·화면에만)
② 내용 대조 — 저쪽이 실제로 보낸 것과 나란히 비교
③ 같은 날 전환 — 저쪽 스케줄 끄기 + 이쪽 켜기. 리포트 단위로 하나씩
④ 며칠 관찰 — 빠진 발송이 없는지
```

**리포트 하나씩 넘긴다.** 13종을 한 번에 넘기면 무엇이 잘못됐는지 알 수 없다.

## 저쪽에서 아쉬웠던 점 → 이번에 바꾸는 것

| 아쉬웠던 점 | 이번 |
| --- | --- |
| 모바일에서 대시보드를 제대로 못 봄 | **모바일 우선.** 지표 카드·차트 전부 |
| 웹과 리포트의 숫자 근거가 흩어짐 | 지표 계산을 **한곳**에 두고 화면·리포트가 같은 함수를 쓴다 |
| 리포트가 안 왔을 때 알기 어려움 | 발송 상태를 **운영 관리자 「자동화」 탭**에서 본다 |

> 이 표도 **열린 질문의 답을 받으면 채워진다.**

## 열린 질문

1. 겹치는 기간 매출 배분 규칙의 정확한 내용 (저쪽 코드에서 읽어 와야 함)
2. 빠진 가격 367건의 원인
3. 시간이 중요한 리포트가 무엇인가 — 「08:45」가 업무상 꼭 지켜져야 하는지에 따라 실행 기반이 갈림
4. 구글 시트 리포트(4,679줄)가 실제로 얼마나 쓰이는가 — 안 쓰면 이전 범위에서 뺀다
