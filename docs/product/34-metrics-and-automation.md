# 가동률 · 매출 · 자동화

> 상태: **기획 확정 · 개발 착수 전** (2026-09-16)
> 상위: [31-stay-ari-migration-overview.md](31-stay-ari-migration-overview.md) · 진입: [32-ops-admin-area.md](32-ops-admin-area.md)

전환 순서에서 **가장 먼저** 넘기는 부분이다. 읽기라 위험이 없고, 숫자가 저쪽과 맞는지 대조하면
「우리 데이터가 맞다」는 확신이 생긴다. 그 확신 위에서 캘린더 쓰기를 켠다.

## 지표 정의

저쪽이 쓰는 계산식(`functions/modules/revenueDashboardData.js`). **정의를 그대로 가져간다** —
숫자가 달라지면 대조가 불가능해진다.

| 지표 | 계산 |
| --- | --- |
| 매출 | 예약의 `netRevenue ?? totalPrice ?? price` 합 |
| 판매 객실박 | 예약이 차지한 밤 수 |
| 전체 객실박 | 객실 수 × 기간 일수 |
| 점유율 | 판매 객실박 ÷ 전체 객실박 |
| **ADR** | 매출 ÷ **판매** 객실박 |
| **RevPAR** | 매출 ÷ **전체** 객실박 |
| 객실당 매출 | 매출 ÷ 객실 수 |

**ADR 과 RevPAR 의 분모가 다르다.** ADR 은 판 것만, RevPAR 은 팔 수 있었던 전부. 섞으면 조용히
틀린다.

**겹치는 기간 배분**: 예약이 조회 기간의 양끝을 넘길 때 매출을 어떻게 나눌지 규칙이 있다
(저쪽 주석: *"Revenue follows the app Revenue Dashboard overlap allocation"*). 구현 전에 그 규칙을
정확히 읽어 와야 한다 — **여기가 어긋나면 월 경계에서 숫자가 안 맞는다.**

## 데이터 정합성 — 확인 완료 (2026-09-16)

2026-09-16 에 2022년부터 전량 백필한 뒤 다시 쟀다. **앞서 「13% 가 빈다」고 본 것은 착시였다.**

| | |
| --- | --- |
| 매출 대상 예약(취소·노쇼 제외) | **11,332건** |
| 가격 있음 | **11,192건 (98.8%)** |
| 가격 없음 | 117건 |

빠져 보였던 것은 **취소분이 섞여 있었기 때문**이다. 취소되면 Beds24 가 금액을 0 으로 비운다:

| | 건수 | 가격 있음 |
| --- | --- | --- |
| 확정 Airbnb | 6,010 | **100%** |
| 확정 Booking.com | 4,885 | **100%** |
| 취소 Booking.com | 2,700 | 5% |
| 취소 Airbnb | 1,244 | 6% |

**매출은 취소를 빼고 계산하므로 문제가 없다.** 남은 117건은 대부분 수기 예약(금액 0 으로 넣은
지인 예약 등)으로 보인다.

## 취소도 볼 수 있어야 한다

저쪽 웹에는 취소 현황이 있고, **우리도 데이터는 이미 갖고 있다**(취소 4,094건, 2022-11~2027-02).

취소는 단순히 「안 팔렸다」가 아니라 **채널을 평가하는 지표**다:

| 채널 | 취소 | 유효 | 취소율 | 예약 후 취소까지 |
| --- | --- | --- | --- | --- |
| Booking.com | 2,700 | 4,885 | **35.6%** | 17일 |
| Airbnb | 1,244 | 6,010 | **17.1%** | 17일 |

**부킹닷컴 취소율이 에어비앤비의 두 배다.** 이 차이를 모르면 「예약이 많이 찼다」를 잘못 읽는다.

보여줄 것: 취소율(기간·채널·건물별) · 취소된 금액 · 예약→취소까지 걸린 시간 · 추이 · 취소 목록.

**한계**: 취소 사유는 Beds24 가 주지 않는다(`subStatus` 가 전부 비어 있다). 사유별 분석은
불가능하다. 취소 금액도 Beds24 가 0 으로 비우므로 **모르는 건을 0원으로 세지 말고 「미상」으로
구분**해야 한다.

**캘린더에도 필요하다** — 저쪽 캘린더에는 「취소된 예약 보기」 토글이 있다(`showCancelled`).
기본은 꺼 두고, 켜면 취소 예약이 흐릿하게 같이 보인다. 「이 방이 왜 비어 있지?」 →
「어제 취소됐구나」를 알기 위한 것이다. → [33](33-calendar-write-features.md)

## 기간 — StayOps 의 창을 넓혀야 한다

**이것이 이번 이전에서 데이터 쪽 가장 큰 변경이다.** 두 프로젝트가 다루는 기간이 다르다.

| | STAY ARI Manager | StayOps (현재) |
| --- | --- | --- |
| 예약 동기화 | **과거 6개월 ~ 미래 12개월** | 당월 + 2개월 (**3개월**) |
| 예약 조회 상한 | 미래 **24개월** | — |
| 가격·캘린더 | 미래 **12개월** | **가격 자체가 없다** |
| 차단(블록) | 12개월 | 3개월 |

**가격은 몇 달 앞을 미리 잡는 일이다.** 다음 달 것만 보이는 캘린더로는 가격 운영을 할 수 없다.
운영 캘린더는 **최소 12개월**을 봐야 한다.

### 지금 StayOps 에 이미 있는 구멍

예약 웹훅은 **날짜와 무관하게** 들어온다. 그래서 3개월 창 밖의 예약도 DB 에 있다 —
2026-09-16 기준 **223건**(가장 먼 것 2027-05-03).

**그런데 6시간 정합성 작업은 3개월만 훑는다.** 즉 그 223건은 **안전망 밖**이다. 웹훅을 한 번
놓치면 영영 안 들어온다. 2026-09-11 에 크리스마스 예약 3건(O102·O207·O210, 12/25~1/1)이 빠져
있던 것이 정확히 이 현상이었다.

> **이 구멍은 이전과 무관하게 이미 존재한다.** 창을 넓히면 같이 닫힌다.

### 넓힐 때 따져야 할 것

- **Beds24 크레딧** — 훑는 기간이 4배가 되면 요청도 는다. 정합성 주기를 늘리거나(6시간 → 12시간),
  먼 미래는 덜 자주 훑는 식으로 나눈다.
- **가격 저장소가 새로 필요하다.** StayOps 에 가격 테이블이 없다. 객실 90개 × 365일이면
  **약 33,000행** — Postgres 에 부담되는 양은 아니다.
- **차단 창도 같이 넓힌다.** 지금 3개월이라 먼 미래의 차단이 안 보인다.

**예약·건물·리뷰 동기화는 가져오지 않는다.** StayOps 가 이미 같은 일을 한다. 중복으로 돌리면

**가격 동기화는 가져와야 한다.** 매출 계산의 재료이고 이쪽에 없다. 위 「데이터 정합성」의 367건이
여기와 관련 있을 가능성이 높다.

### 실행 기반이 다르다

| | 저쪽 | StayOps |
| --- | --- | --- |
| 스케줄 | Firebase Cloud Functions (`onSchedule`) | **GitHub Actions** + Vercel Cron |
| 이유 | — | 2026-07-22 에 Vercel 크론이 며칠 발화하지 않아 예약 5일치가 조용히 비었다. 이후 새 스케줄은 외부 트리거를 쓴다 |

**옮기면서 GitHub Actions 로 바꾼다.** 기존 워크플로(`beds24-reconcile.yml` ·
`recruit-sync.yml`)와 같은 방식이다.

> 다만 GitHub Actions 의 예약 시각은 **보장되지 않는다.** 2026-09-11 실측에서 5분 주기가 실제로는
> 40분~3시간 40분 간격이었다. **「08:45 정각에 슬랙」 같은 요구는 지킬 수 없다.** 시간이 중요한
> 리포트는 Vercel Cron(하루 1회, 상한 2개)이나 외부 크론 서비스를 검토한다 — 개발 시 결정.

## 전환 — 켜는 순간 저쪽을 끈다

자동화는 **한 쌍으로 움직인다.** 이쪽을 켜고 저쪽을 그대로 두면 **슬랙에 리포트가 두 번 온다.**

```
① 이쪽 구현 — 발송하지 않는 상태로 둔다(드라이런: 만들어질 메시지를 로그·화면에만)
② 내용 대조 — 저쪽이 실제로 보낸 것과 나란히 비교
③ 같은 날 전환 — 저쪽 스케줄 끄기 + 이쪽 켜기. 리포트 단위로 하나씩
④ 며칠 관찰 — 빠진 발송이 없는지
```

**리포트 하나씩 넘긴다.** 13종을 한 번에 넘기면 무엇이 잘못됐는지 알 수 없다.

## 저쪽에서 아쉬웠던 점 → 이번에 바꾸는 것

| 아쉬웠던 점 | 이번 |
| --- | --- |
| 모바일에서 대시보드를 제대로 못 봄 | **모바일 우선.** 지표 카드·차트 전부 |
| 웹과 리포트의 숫자 근거가 흩어짐 | 지표 계산을 **한곳**에 두고 화면·리포트가 같은 함수를 쓴다 |
| 리포트가 안 왔을 때 알기 어려움 | 발송 상태를 **운영 관리자 「자동화」 탭**에서 본다 |

> 이 표도 **열린 질문의 답을 받으면 채워진다.**
