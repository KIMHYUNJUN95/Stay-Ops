# 가동률 · 매출 · 자동화

> 상태: **매출 화면 구현(2026-10-06)** · 가동률 · 전표 · 자동화 착수 전 (2026-09-16 기획, 2026-09-28 조사 반영)
> 상위: [31-stay-ari-migration-overview.md](31-stay-ari-migration-overview.md) · 진입: [32-ops-admin-area.md](32-ops-admin-area.md)

전환 순서에서 **가장 먼저** 넘기는 부분이다. 읽기라 위험이 없고, 숫자가 저쪽과 맞는지 대조하면
「우리 데이터가 맞다」는 확신이 생긴다. 그 확신 위에서 캘린더 쓰기를 켠다.

## 지표 정의 — 저쪽 코드에서 읽은 그대로 (2026-09-28 전수 조사)

> 2026-09-16 에 적었던 정의(`netRevenue ?? totalPrice ?? price`)는 **틀렸다.** 저쪽 코드를 전부 읽어
> 바로잡았다. 이대로 만들면 저쪽 숫자와 맞지 않았다.

### 매출

| 항목 | 저쪽 실제 규칙 | 근거 |
| --- | --- | --- |
| 금액 | **총액**(`totalPrice` · `price`). 수수료를 빼지 않는다. `net` 모드는 코드에 있지만 **부르는 곳이 없다** | `RevenueDashboard.jsx:534`, `revenueDashboardData.js:58-62`(기본 `gross`) |
| 인식 기준 | **숙박일 · 1박 균등 분배.** `총액 ÷ 박수` 를 조회 기간과 겹친 밤 수만큼. 체크아웃 날은 빼고, 월을 넘기면 월마다 다시 쪼갠다 | `RevenueDashboard.jsx:546-560`, `revenueDashboardData.js:585-600` |
| 예약일 기준 | 없다. `bookDate` 는 「예약 생성 건수」 집계에만 | `:747` |
| 취소 | `status == "confirmed"` 만. 취소 수수료 반영 없음(취소 = 0원) | 모든 쿼리 |
| 세금 · 보증금 · 통화 | 저장만 하고 **안 쓴다.** 표시는 항상 ¥ | `functions/index.js:1393-1437` |

**화면마다 제외 범위가 다르다 — 대조할 때 가장 큰 함정이다.**

| 계산 | 빼는 건물 | 채널 조건 |
| --- | --- | --- |
| 매출 대시보드 | 다이쿄초 | 없음(수기 포함) |
| 매출 분석 | 다이쿄초 · 사노시 · 오쿠보A동 | 없음 |
| 전표 스냅샷 | 다이쿄초 · 사노시 · 오쿠보A동 | **Airbnb · Booking.com 만** |
| Notion · 목표 시트 | 다이쿄초(사노시는 참고 버킷, 오쿠보 A/B/C 는 `okubo` 버킷) | — |

플랫폼 분류(`normalizePlatformKey`)는 `platform · referer · referrer · apiSource · subSource · source ·
channel` 을 소문자로 이어 붙여 부분 일치로 가른다: direct/manual/phone/walk → booking → expedia →
agoda → airbnb → other. 홈 요약·인원 리포트에는 **축소판 사본**이 따로 있다(서로 조금씩 다르다).

### 가동률

| 항목 | 저쪽 실제 규칙 |
| --- | --- |
| 점유일(분자) | 객실(건물+방 이름)별로 체크인~**체크아웃 전날**의 날짜를 Set 으로 모은 개수. **겹친 예약(듀얼 유닛)은 1박** |
| 분모 | **하드코딩된 객실 목록** × 기간 일수 |
| 차단(blackout) | 분자에서만 빠진다 — **분모에서는 안 빠진다**(막아 둔 날도 팔 수 있던 날로 센다) |
| 노쇼 · 오너 · 0원 | 따로 없다 — **확정이면 전부 점유**(매출은 0원을 건너뛴다) |
| 새 객실 | 목록에 넣는 순간 **과거 달 분모까지 소급**된다(9/15 Apartment Hotel 26실 추가로 개업 전 달 가동률이 낮아졌다) |
| 제외 | 다이쿄초(매각)는 전부. 사노시는 합계·추이에서 빼고 카드로만. **단 객실 성과의 매출 KPI 에는 사노시가 들어간다**(불일치) |

객실 목록 사본이 **네 벌**이다(가동률 · 객실 성과 · 홈 · `functions/index.js:4529`). 서버 쪽만 듀얼
roomId 를 같은 이름으로 합친다.

### ADR · RevPAR

**화면에는 없다** — 서버 모듈(`revenueDashboardData.js:308-312`)에만 있고 Notion·목표 시트가 쓴다.

| 지표 | 계산 |
| --- | --- |
| ADR | 매출 ÷ **판매** 객실박(중복 제거한 박수) |
| RevPAR | 매출 ÷ **전체** 객실박 |
| 객실당 매출 | 매출 ÷ 객실 수 |

**분모가 다르다.** ADR 은 판 것만, RevPAR 은 팔 수 있었던 전부. 섞으면 조용히 틀린다.

### 복제 현황 → 우리는 하나로

같은 계산이 저쪽에 **4~5벌** 복사돼 있다(점유일 Set · 1박 배분 · 플랫폼 분류). 우리는 **공통 지표
계층 하나**를 만들고 화면·리포트가 전부 그걸 부른다. 기준 모양은 `buildRevenueDashboardSnapshot`
(건물·객실별 점유·매출·ADR·RevPAR·플랫폼·참고 버킷을 다 가짐)이되, 월 단위 고정을 **기간
파라미터**로 일반화하고 **제외 건물·채널 조건을 파라미터**로 받는다. 손님 국가는
`resolveGuestCountry` 를 쓴다(아래).

### 전표 — 장부가 아니라 「매일 찍는 앞날 스냅샷」이다

> 2026-09-16 에 「일별 매출 전표」라고 적은 것은 **틀렸다.**

`sales_logs/{기록일}` 한 문서 = **그날 알고 있던 향후 8개월**(기록일의 달 ~ +7개월)의 월별
`{revenue, nights, occupancy}`. 즉 **부킹 페이스**다 — 「9/1 에는 10월 매출이 얼마로 잡혀 있었나」.

| 규칙 | 내용 |
| --- | --- |
| 대상 | 확정 · 다이쿄초·사노시·오쿠보A동 제외 · **Airbnb·Booking.com 만** |
| 금액 | `price \|\| totalPrice`(순서만 반대, 저장 시 같은 값) |
| 분모 | `BUILDING_ROOMS` 에서 사노시·오쿠보A동 뺀 수 × 월 일수. 2026-01 만 다이쿄초 가중(`(25*with + 6*without)/31`) |
| 생성 | 00:30 **어제** 문서(있으면 건너뜀) **+ 예약이 바뀔 때마다 오늘·어제 덮어쓰기**(웹훅·동기화·수기 예약 등). 그래서 각 날짜는 약 D+2 에 굳는다 |
| 사람 입력 | 메모 — `salesLogMemos` 에 **키 형식이 두 가지**(`{YYYY-MM-DD}` / `{companyId}_{YYYY-MM[-DD]}`). `/sales-log` 에서도 메모를 쓴다 |
| 죽은 컬렉션 | `dailySalesLog` — 화면이 안 쓴다(값이 있는지만 이관 전에 확인) |

**과거 스냅샷은 Beds24 로 다시 만들 수 없다.** 지금 예약으로 다시 계산하면 그 뒤의 취소·변경이
섞여 값이 달라진다 — **원본 그대로 옮긴다.** 메모도 사람이 쓴 것이라 옮긴다. 저쪽 「Re-generate」·
`bulkRegenerateSalesLog` 로 과거 날짜를 덮으면 그날의 페이스가 사라진다(화면의 Delete/Re-generate
버튼은 「고른 연·월 + **오늘의 일**」을 쓰는 버그도 있다).

**목표(goal)는 화면에 없다** — `targetGoalsSheet.js` 가 구글 시트로만 낸다. 매출 화면의
「Target Group (A)」는 목표가 아니라 **비교 그룹 이름**이다.

### 국가 — 전화번호로 채운다 (2026-09-28)

국가별 화면을 옮길 때 **그대로 옮기면 Airbnb 손님 절반이 `Unknown`** 이다. Airbnb 는 국가를 거의
주지 않는다(체크인 6월 이후 1,460건 중 709건 빈칸). 대신 전화번호를 국제 형식으로 준다.

**국가는 `resolveGuestCountry()`(`src/lib/guest-country.ts`)로 정한다** — 채널 값이 먼저, 없으면
전화번호의 국가번호. 실측으로 Airbnb 미상이 **709 → 0건**이 된다(추정 상위: 미국 376 · 호주 87 ·
인도네시아 26 · 영국 25 · 싱가포르 22 · 캐나다 20).

지표를 만들 때 정할 것 — **출처(`channel` / `phone`)를 나눠 셀지.** 전화번호의 나라와 국적은 다를
수 있다. 기본은 합쳐 세고, 필요하면 「추정 포함 / 제외」 토글을 둔다. 결정은 국가별 화면을 만들 때.

저쪽 국가별 화면은 **예약 건수**를 **체크인일** 기준으로 센다(박수 아님). 인원 리포트는 **예약일**
기준이라 둘은 원래 안 맞는다 — 옮길 때 하나로 정한다.

## 매출 요약 모달 — 쓰는 식 (2026-09-30, 결정 1 = 그대로 재현)

판매 캘린더 「매출 요약」([33](33-calendar-write-features.md))이 첫 적용처다. 식은 `src/lib/ops-sales-summary.ts`
(합계에 넣을 건물을 고르면 — 기본으로 오쿠보A · 사노 제외, 2026-10-05 — `combineSalesSummary` 가 고른 건물의 합으로
다시 내고 비율은 합을 다시 나눈다. 전년 동기 = 같은 날짜 1년 전 창을 같은 식으로 — 객실별로 비교해 「기존 객실 증감 +
전년 매출 없던 객실」로 나눈다, `src/lib/ops-sales-yoy.ts`)
**한 곳**에 있고, 저쪽 함수를 식 그대로 옮긴 무작위 대조 테스트(`ops-sales-summary.test.ts`, 시드 5개)로 고정한다.
저쪽 화면끼리 다를 때는 **건물 캘린더 분석 카드**를 따른다(결정 2 — 쓰임이 가장 가깝다).

| 지표 | 식 | 저쪽 출처 |
| --- | --- | --- |
| 대상 예약 | 원본 `status` 가 `1`·`2`·`new`·`confirmed` 만(= 저쪽 「confirmed」). `request`/`inquiry`·`black`·취소 제외. **노쇼 포함**(저쪽은 `subStatus` 를 안 본다). 우리 표가 `cancelled` 면 원본과 무관하게 뺀다 | `functions/index.js` `determineStatus` (:1196) |

## 취소도 볼 수 있어야 한다

저쪽 웹에는 취소 현황이 있고, **우리도 데이터는 이미 갖고 있다**(취소 4,094건, 2022-11~2027-02).

취소는 단순히 「안 팔렸다」가 아니라 **채널을 평가하는 지표**다:

| 채널 | 취소 | 유효 | 취소율 | 예약 후 취소까지 |
| --- | --- | --- | --- | --- |
| Booking.com | 2,700 | 4,885 | **35.6%** | 17일 |
| Airbnb | 1,244 | 6,010 | **17.1%** | 17일 |

**부킹닷컴 취소율이 에어비앤비의 두 배다.** 이 차이를 모르면 「예약이 많이 찼다」를 잘못 읽는다.

보여줄 것: 취소율(기간·채널·건물별) · 취소된 금액 · 예약→취소까지 걸린 시간 · 추이 · 취소 목록.

**한계**: 취소 사유는 Beds24 가 주지 않는다(`subStatus` 가 전부 비어 있다). 사유별 분석은
불가능하다. 취소 금액도 Beds24 가 0 으로 비우므로 **모르는 건을 0원으로 세지 말고 「미상」으로
구분**해야 한다.

**캘린더에도 필요하다** — 저쪽 캘린더에는 「취소된 예약 보기」 토글이 있다(`showCancelled`).
기본은 꺼 두고, 켜면 취소 예약이 흐릿하게 같이 보인다. 「이 방이 왜 비어 있지?」 →
「어제 취소됐구나」를 알기 위한 것이다. → [33](33-calendar-write-features.md)

### 저쪽의 위험 — 옮기면서 고친다

- **인증 없는 수동 발송 주소 4개**(`sendSlackDailyReportManual` · `runDailyReportNow` · `sendNotionReport`
  · `testNotionSync`) — 누구나 리포트를 쏠 수 있다.
- 취소·당일예약 알림 **중복 방지 없음**.
- 청소 인력 예측이 **예약 쓰기마다 시트 전체 재작성**.
- 월간 Notion 리포트 **멱등성 없음**.
- 예약 변경 시 Slack 재발송 코드는 `skipSlack` 기본값 때문에 **도달 불가**(죽은 코드).

### 실행 기반이 다르다

| | 저쪽 | StayOps |
| --- | --- | --- |
| 스케줄 | Firebase Cloud Functions (`onSchedule`) | **GitHub Actions** + Vercel Cron |
| 이유 | — | 2026-07-22 에 Vercel 크론이 며칠 발화하지 않아 예약 5일치가 조용히 비었다. 이후 새 스케줄은 외부 트리거를 쓴다 |

> 다만 GitHub Actions 의 예약 시각은 **보장되지 않는다.** 실측에서 5분 주기가 40분~3시간 40분
> 간격이었다. **「06:30 정각에 슬랙」은 지킬 수 없다.** 청소 명단은 아침 업무 시작 전에 와야
> 하므로 실행 기반을 개발 시 따로 정한다(Vercel Cron 하루 1회 · 외부 크론 서비스 등).

## 전환 — 켜는 순간 저쪽을 끈다

> **2026-10-06 갱신**: 사용자가 저쪽 Slack 자동화를 **먼저 전부 껐고** 저쪽의 Beds24 API 연결도 끊었다. 아래 「한 쌍으로」
> 순서는 Slack 에 대해서는 더 이상 해당하지 않는다(이중 발송 위험 없음). 대조는 **Slack 채널에 남은 저쪽의 지난 메시지**와
> 같은 날짜를 우리 쪽에서 다시 만들어 비교한다. 지금은 발송 공백 — 36번 순서대로 서둘러 켠다.

자동화는 **한 쌍으로 움직인다.** 이쪽을 켜고 저쪽을 그대로 두면 **슬랙에 리포트가 두 번 온다.**

```
① 이쪽 구현 — 발송하지 않는 상태로 둔다(드라이런: 만들어질 메시지를 로그·화면에만)
② 내용 대조 — 저쪽이 실제로 보낸 것과 나란히 비교
③ 같은 날 전환 — 저쪽 스케줄 끄기 + 이쪽 켜기. 리포트 단위로 하나씩
④ 며칠 관찰 — 빠진 발송이 없는지
```

**리포트 하나씩 넘긴다.** 한 번에 넘기면 무엇이 잘못됐는지 알 수 없다.
