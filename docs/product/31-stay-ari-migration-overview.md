# STAY ARI Manager 이전 — 전체 계획

> 상태: **캘린더 이식 거의 완료 · 지표·자동화 착수 전** (2026-09-16 기획, 2026-09-28 갱신)
> 관련: [32-ops-admin-area.md](32-ops-admin-area.md) · [33-calendar-write-features.md](33-calendar-write-features.md) · [34-metrics-and-automation.md](34-metrics-and-automation.md)

## 무엇을 왜 하는가

지금 업무가 **웹 두 개에 나뉘어** 있다. StayOps(현장 운영)와 STAY ARI Manager(가격·매출·자동화).
이 이전의 목적은 **하나의 웹에서 모든 업무를 하는 것**이다. 이전이 끝나면 저쪽 웹은 폐지한다.

단순 복사가 아니다. 목적이 셋이다.

1. **합친다** — 두 웹을 오가지 않는다.
2. **고친다** — 저쪽에서 아쉬웠던 부분을 그대로 옮기지 않고 개선한다.
3. **모바일에서 쓴다** — 아래 참고. 이번 이전에서 **가장 중요한 요구**다.

### 모바일이 설계의 출발점이다

저쪽 웹은 PWA 이지만 **모바일이 제대로 구현돼 있지 않다.** 사실상 PC 에서만 쓴다.

StayOps 로 옮기면서 **읽기와 쓰기 모두 모바일에서 가능해야 한다.** 「누워서도, 어디서도」가
요구사항 그대로다. 이것은 부가 조건이 아니라 **기능 설계의 제약**이다 —

저쪽 캘린더의 핵심 상호작용은 **마우스 드래그**로 기간을 고르는 방식이다
(`handleCalendarMouseDown → MouseMove → MouseUp`). 손가락으로는 스크롤과 충돌하고, 좁은 화면에서
30일 × 26객실을 드래그하는 것은 실용적이지 않다. **그대로 옮길 수 없다.** 입력 방식을 새로
설계한다 → [33-calendar-write-features.md](33-calendar-write-features.md)

## 병행 운영 원칙 (확정)

> **개발이 끝나기 전에는 데이터를 가져오지 않는다. 설계와 구현만 해 둔다.**
> 이쪽 개발이 완료되고 데이터 동기화 후 문제가 없으면, 그때 저쪽을 폐지한다.

이 원칙이 두 가지 큰 위험을 **원천적으로 없앤다.**

| 위험 | 왜 사라지는가 |
| --- | --- |
| 두 웹이 같은 Beds24 에 써서 서로 덮어씀 | 이쪽은 켜기 전까지 **쓰지 않는다** |
| 슬랙·노션 리포트가 양쪽에서 이중 발송 | 이쪽 자동화는 켜기 전까지 **보내지 않는다** |

대신 하나가 생긴다 — **켜기 전에 어떻게 검증하는가.** 실제로 쓰거나 보내보지 않고는 확신할 수
없기 때문이다. 각 문서의 「전환 전 검증」 절이 이 문제를 다룬다.

### 전환(cutover)의 단위

기능 단위로 끊어서 넘긴다. **한 번에 전부 넘기지 않는다** — 되돌릴 구간이 없어진다.

```
① 읽기 (가동률·매출)  → 위험 없음. 숫자가 저쪽과 맞는지만 대조한다.
② 자동화              → 이쪽을 켜는 순간 저쪽 스케줄을 끈다. 한 쌍으로 움직인다.
③ 캘린더 (쓰기)       → 마지막. 그 전까지 데이터 정합성을 충분히 본다.
```

**왜 이 순서인가**: 읽기는 틀려도 화면 숫자가 이상할 뿐이지만, 쓰기는 틀리면 에어비앤비·
부킹닷컴에 그대로 나간다. 읽기로 데이터가 맞다는 것을 먼저 확인하고, 그 확신 위에서 쓰기를
켠다.

### 저쪽 폐지 조건

아래가 **전부** 충족되면 폐지한다. 하나라도 빠지면 유지한다.

- [ ] 4개 영역이 StayOps 에서 동작한다
- [ ] 가동률·매출 숫자가 저쪽과 **한 달치 이상 일치**한다
- [ ] 자동화 13종이 이쪽에서 발송되고, 저쪽 스케줄이 꺼져 있다
- [ ] 캘린더 쓰기가 실제 Beds24 에 반영되는 것을 확인했다
- [ ] 모바일에서 읽기·쓰기가 모두 된다
- [ ] 사무실 직원이 실제 업무를 일주일 이상 StayOps 에서만 했다

## 데이터 — 결국 Supabase 하나로

두 앱이 **같은 Beds24 를 각자 동기화**하고 있다. 저쪽은 Firestore, 이쪽은 Supabase 다.
최종 상태는 **Supabase 하나**이고 Firestore 는 폐기한다.

~~**알려진 구멍**: 가격이 있는 예약이 87% 뿐이다~~ → **착시였다**(2026-09-16 전량 백필 후 재측정:
취소 제외 11,332건 중 98.8% 에 가격이 있다. 빠져 보인 것은 취소분 — Beds24 가 취소 시 금액을 0 으로
비운다). 매출 금액도 `netRevenue` 우선이 아니라 **총액**이다(2026-09-28 저쪽 코드 조사).
→ [34-metrics-and-automation.md](34-metrics-and-automation.md) 「데이터 정합성」 · 「지표 정의」

**남은 데이터 구멍**: 예약 정합성 작업이 **3개월만** 훑는다. 매출·전표(향후 8개월)를 켜기 전에
넓혀야 한다 → 34번 「기간」.

## 진입 — 분리된 관리자 영역

가져오는 기능은 **기존 StayOps 콘솔에 섞지 않는다.** 사무실 직원 소수만 들어가는 별도 영역을
만들고 그 안에서만 쓴다. 특히 캘린더는 **기존 예약 캘린더와 물건이 다르다**(읽기 전용 vs 쓰기).
→ [32-ops-admin-area.md](32-ops-admin-area.md)

## 열린 질문

기획 단계에서 아직 답이 없는 것. **개발 중에 답이 필요한 순서대로** 적는다.

1. ~~가격 수정을 실제로 어떻게 쓰는가?~~ → **해결.** 스코프 바(객실·주·요일 축)로 묶어서 고친다
   (2026-09-24 사용자 확인).
2. **저쪽 웹에서 모바일 말고 아쉬웠던 점은?** 느렸다 / 화면이 복잡했다 / 특정 작업이 여러
   단계였다 — 구체적일수록 개선 항목이 분명해진다.
3. ~~빠진 가격 367건의 원인~~ → **해결.** 취소분이 섞인 착시(34번 「데이터 정합성」).
4. 지표를 저쪽 숫자 그대로 재현할지 고칠지 등 — 34번 「착수 전에 정할 것」.
