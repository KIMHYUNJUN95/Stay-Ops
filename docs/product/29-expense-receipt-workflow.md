# 29. 영수증 정산(활동비 · 경비) — 기획

**상태: 기획 단계 (2026-08-05). 구현 착수 전 — 문서만 선행.**

## 0. 이름과 자리

| ko | ja | en |
| --- | --- | --- |
| **영수증 내역** | **領収書明細** | **Receipts** |

**사이드바에 독립 항목**으로 둔다(청소·근태·분실물과 같은 층). 기존 사이드바가 짧은 명사로
통일돼 있어 그 결에 맞춘다.

`明細` 는 "내역" 에 대응하는 일본 실무어다. 영어는 사이드바 폭을 고려해 `Receipts` 로 짧게 둔다.

> 근태 안에 이미 **교통비 정산**이 있어 이름이 가깝다. 교통비는 **근무일 기반**이라 근태 소속을
> 유지하고, 영수증 내역은 별개로 둔다. 이 기능이 자리 잡으면 교통비를 흡수할지 그때 판단한다.

## 1. 지금 무엇이 아픈가

월 1회, 개인별로 이렇게 처리한다.

1. 한 달간 영수증을 모아 둔다
2. **A4 용지에 영수증을 붙인다**
3. **금액에 형광펜을 긋는다** — 경리가 금액을 찾기 쉽게
4. 엑셀에 항목을 **손으로 친다**
5. 영수증과 엑셀을 **대조**한다
6. 경리 담당자에게 제출한다

**금액 자체는 크지 않다.** 아픈 것은 돈이 아니라 **2·3·4·5의 손일**이다. 이 문서의 목표는 그
손일을 없애는 것이지, 회계 시스템을 만드는 것이 아니다.

## 2. 두 종류는 돈의 방향이 반대다

| | 흐름 | 영수증의 의미 |
| --- | --- | --- |
| **활동비** | 회사 → 직원 (선지급) | **사용 증빙** — 받은 돈을 어디에 썼나 |
| **경비** | 직원 → 회사 (청구) | **지급 근거** — 얼마를 돌려줘야 하나 |

**총액을 하나로 합치면 뜻을 잃는다.** 활동비 3만 + 경비 5만 = 8만이지만 회사가 지급할 돈은
5만뿐이다. 집계는 반드시 종류별로 나눈다.

- **활동비**는 **개인별 정액 한도**가 있고 그 안에서 써야 한다 → 잔액 표시가 필요하다.
- **경비**는 현장 비품을 개인 돈으로 먼저 사고 나중에 청구하는 방식이다.

## 3. 산출물 — 개인별·월별 두 개 한 쌍

```
[A4 인쇄물]                       [엑셀]
 ①  [영수증 사진]                  ①  08-03  세븐일레븐  ¥1,280  간식
     현장 직원 야간 간식                └ 현장 직원 야간 간식
 ②  [영수증 사진]                  ②  08-05  카인즈      ¥3,450  비품
 ③  [영수증 사진]                  ③  ...
```

- **번호가 사진과 엑셀 행을 잇는다.** 엑셀의 `¥1,280` 이 맞는지 ① 사진을 보면 끝난다 —
  **대조 작업과 형광펜이 동시에 사라진다.**
- A4 는 **영수증 사진이 붙어 있는 것처럼** 배치해 인쇄한다. **실물을 붙이는 작업은 없어진다.**
  원본은 봉투에 보관한다.
- 영수증은 길이가 제각각이라(편의점 건 길고 좁다) **비율을 유지한 채 흘려 담는다.**
- **메모**를 영수증마다 입력할 수 있고, 엑셀과 A4 **양쪽에 표시**한다 — 경리가 A4 만 봐도
  "왜 샀는지" 를 알아야 한다.

## 4. OCR — 목적은 "엑셀 자동 기입"

산 자리에서 사진을 찍으면 OCR 이 값을 읽어 **미리 채워 둔다.**

| 항목 | 기대 |
| --- | --- |
| 금액 · 날짜 · 가게명 | 자동 기입 |
| 활동비 / 경비 구분 | 사용자가 선택 |
| 품목 | 잘 안 나온다 — 영수증에 `ｵﾆｷﾞﾘ鮭` 같은 축약이 많다. 필요하면 직접 입력 |

**OCR 결과는 초안이지 확정이 아니다.** 저장 전에 사용자가 확인하는 화면을 반드시 거친다 —
틀린 금액이 그대로 정산에 들어가면 안 된다.

### 제공자: Azure Document Intelligence (확정, 2026-08-05)

| | 무료 | 필요한 것 | 비고 |
| --- | --- | --- | --- |
| **Azure Document Intelligence** | **월 500장** (F0) | Azure 계정 | 영수증 전용 모델, 일본어 지원 |
| Claude API | ✗ 종량제 | `ANTHROPIC_API_KEY` | 품질·유연성 최고. 100장 ≈ $0.5 (Sonnet 5) |

월 80~100장 규모라 **Azure 무료 구간 안**이다. 무료 티어는 요청당 앞 2페이지만 처리하지만
영수증은 1장이라 무관하다.

**품질이 부족하면 Claude 로 바꾼다.** 호출부 하나만 갈아끼우면 되도록 어댑터를 사이에 둔다.
Claude 는 「이 영수증이 간식인지 비품인지」 분류까지 한 번에 시킬 수 있다는 점이 다르다.

> 배경: 이 저장소는 업무일지에서 LLM 방식을 프로토타입까지 갔다가 되돌린 적이 있다
> (decision log — "Claude 소비자 구독으로는 API 인증이 안 되고 종량제 과금을 원하지 않았다",
> **현재 스택에 LLM 의존성 없음**). Azure 선택은 그 제약을 유지한다.

## 4-1. 권한 — 파트타임 알바는 기본 차단 (2026-08-06 확정)

**일반 파트타임 알바는 쓸 수 없다.** 활동비·경비는 돈이 오가는 기록이라 접근을 좁힌다.

기존 **권한 오버라이드 체계**(`docs/product/27-permission-override-workflow.md`)를 그대로 쓴다 —
새 권한 구조를 만들지 않는다.

- `src/config/permission-overrides.ts` 의 `PERMISSION_OVERRIDE_KEYS` 에 키를 하나 추가한다
  (예: `expense_receipt`). 이 배열이 검증·UI 순서의 단일 출처다.
- 기본 규칙은 업무일지(`canGenerateDailyReport`)와 같은 모양으로 둔다:
  **`role != 'part_time_staff'`, 단 개인별 예외가 부여되면 허용.**
- 서버 게이트에 `OR has_permission_override(org, user, '<key>')` 를 붙인다. **UI 만 가리는 것으로는
  안 된다**(`CLAUDE.md` §6 — 권한은 서버에서 강제).
- 사람 이름/설명 문구는 i18n `admin.users.console.keys` 에 ko·ja·en 로 추가한다.
- 예외 부여는 관리자 사용자 관리 화면에서 한다. 오버라이드는 **기간 제한**과 **사유**를 받고,
  `granted_by_user_id <> user_id` 제약이 있어 **자기 자신에게는 못 준다.**

> 왜 파트타임을 막는가: 활동비는 개인별 선지급 잔액이고 경비는 회사가 지급할 금액이다. 남의 정산을
> 열람하거나 항목을 만들 수 있으면 돈에 직접 닿는다. 실무상 필요한 소수(관리 업무를 겸하는
> 파트타이머)는 개인별 예외로 연다 — 업무일지가 이미 그 방식으로 운영되고 있다.

## 5. 재사용 — 새로 만들지 않는다

**교통비 정산 모듈이 이미 같은 모양이다.**

```
transport_reimbursement_reports   월 · 개인 · draft → submitted → reviewed
  └ _items                        금액 · 날짜 · 메모 · 근무 맥락
      └ _item_images              영수증 사진
```

모바일·콘솔 화면과 **엑셀 워크북 생성기**(`attendance-transport-workbook.ts`)까지 있다. 이 기획은
**새 모듈이 아니라 경비 종류를 넓히는 일**에 가깝다. 데이터 모델·상태 흐름·검토 UI 를 그대로
따르고, 다음만 더한다:

- `kind`(활동비 / 경비) — 집계를 나누기 위해
- 활동비 개인별 한도 + 잔액
- OCR 로 채운 값과 사용자가 고친 값의 구분(원본 추적)
- A4 인쇄 레이아웃

## 6. 법 요건 — **해당 없음** (원본을 계속 보관하므로)

일본 **전자장부보존법(電子帳簿保存法)** 조사 결과, 요건을 갖추면 종이 원본을 폐기할 수 있다:
정정·삭제 이력이 남는 시스템, 날짜·금액·거래처 검색, 200dpi·256계조 이상, 2개월+7영업일 내 입력,
사무처리규정·시스템 개요서 비치. 사전 승인은 2022년 폐지되었고 **JIIMA 인증도 필수가 아니라**
자체 개발 시스템도 가능하다.

**그러나 이 기획은 그 길을 가지 않는다.** 금액이 크지 않은데 법 요건을 지는 시스템이 되면
삭제 이력·검색 요건·보관 기간(7~10년)·세무조사 증명 책임·법 개정 대응까지 따라온다. 얻는 것에
비해 짊어지는 것이 크다.

**원본은 계속 종이로 보관한다.** 그래서 법 요건에서 자유롭고, 목표(형광펜·붙이기·엑셀·대조 제거)는
그대로 달성된다.

> 주의: **전자로 받은 영수증**(메일·PDF·웹)은 다르다. 2024년 1월부터 **전자보관이
> 의무**라 인쇄해서 종이로 보관하면 안 된다. 지금 그렇게 처리 중이라면 별도 확인이 필요하다.
> 종이 원본 폐기 여부와 소비세 매입세액공제 요건은 **세무사 확인 대상**이다.

## 7. 주의할 것

- **이미지 압축.** 이 저장소는 업로드 시 클라이언트 압축을 건다(`CLAUDE.md` §8). 그대로 쓰면
  **인쇄했을 때 금액이 안 읽힐 수 있다.** 영수증은 압축을 약하게 가야 한다 — 경리가 눈으로
  대조하는 것이 목적이므로 읽히는 것이 최우선이다.
- **OCR 오류가 돈으로 흐른다.** §4 의 확인 화면은 선택이 아니라 필수다.
- **A4 레이아웃.** 영수증 비율이 제각각이라 늘리거나 잘라내면 안 된다.

### 다루지 않기로 한 것 (2026-08-05 확정)

- **활동비 한도 초과를 막거나 별도 판정하지 않는다.** 초과하면 잔액이 음수가 되고 그대로 다음
  달로 넘어간다(실물에서도 그렇게 굴러가고 있다 — §9). 자기 부담 판정·차단은 두지 않는다.
- **비품 주문 요청(`order_requests`)과 연결하지 않는다.** 영수증 정산과 주문 요청은 **완전히 별개
  업무**다. 억지로 이으면 두 화면이 서로를 끌고 다니게 된다.

## 9. 실물 서식 (2026-08-06 확인)

구글 스프레드시트 `26年06月_民泊経費精算書`. 시트가 용도별로 갈려 있다 —
`マネージャー(活動費)` / `マネージャー(消耗品費用)`, 그리고 개인·연도별 시트들.

### 사람별 블록

한 시트 안에 **사람마다 작은 표**를 두고, 페이지에 **2열로** 배치한다.

```
【民泊経費精算】(김은성)
 06月           明　細                          支出
 05月繰り越し                                   ¥1,372     ← 전월 이월
 2026-06-05     仮払金                          ¥10,000    ← 지급 (노랑)
 2026-06-28     飲み物 현서 다희 우성 은성 상열  -(¥1,533)  ← 지출 (음수, 괄호)
                                                ¥9,839     ← 잔액 (노랑)
```

### 계산 규칙 — **이월이 핵심이다**

```
잔액 = 전월 이월 + 仮払金 − Σ지출
잔액 → 다음 달 「◯月繰り越し」로 넘어간다
```

- **지급액(仮払金)은 사람마다 다르다** — 실물에 ¥5,000 과 ¥10,000 이 섞여 있다.
- **잔액은 음수가 될 수 있고 그대로 이월된다** — 실물에 `05月繰り越し −¥604` 가 있다.
- 지출이 하나도 없는 달도 있다(이월 + 지급 = 잔액).

> 이 때문에 활동비는 "월 한도" 가 아니라 **개인별 러닝 밸런스**로 봐야 한다. 월별로 끊어
> 계산하면 실물과 숫자가 어긋난다.

### 컬럼

| 열 | 내용 |
| --- | --- |
| `06月` | 날짜 (또는 `05月繰り越し` / 빈칸) |
| `明細` | 무엇을 샀는지 **+ 누가 먹었는지 이름** — 예: `飲み物&おやつ(현덕,천우,주은,형민,규민)` |
| `支出` | 금액. 지출은 `-(¥1,533)` 처럼 **음수·괄호** 표기 |

`明細` 에 참여자 이름이 들어간다는 점이 중요하다. §3 의 **메모**가 그 자리를 대신하게 되며,
자유 입력만으로는 부족할 수 있다(이름 선택 UI 를 검토할 것).

### 색

`仮払金` 행과 마지막 `잔액` 행에 **주황 배경**을 준다. 경리가 눈으로 찾는 앵커다.

### 우리 서식으로 간다 (2026-08-06 확정)

실물의 **셀 배치·색·문구를 그대로 재현하지 않는다.** 사람별 블록을 한 시트에 2열로 흩어 놓는
구조는 사람이 손으로 만들 때의 형태이지, 자동 생성에 맞는 형태가 아니다. 재현하려면 병합·좌표
계산에 손이 많이 가는 데 비해 얻는 것이 없다.

**담아야 하는 값은 그대로 유지한다:**

| 반드시 있어야 하는 것 |
| --- |
| 전월 이월 |
| 지급액(`仮払金`)과 그 날짜 |
| 지출 한 건마다 — 날짜 · 명세(품목 + 참여자) · 금액 |
| 잔액 (= 다음 달 이월) |
| **개인별로 구분** |

출력은 콘솔 공용 계약을 따른다(`CLAUDE.md` §4b) — `<AdminExportButtons>` 로 **Excel 과 PDF 를
항상 함께** 내보내고, 워크북은 `buildAdminTableWorkbookBase64()` / 리포트는
`buildAdminTableReportHtml()` 를 쓴다. 새 내보내기 경로를 만들지 않는다.

> 경리 담당자가 형식 변경을 받아들일 것이라는 전제다. 만약 반려되면 그때 실물 재현으로 돌아온다 —
> 값이 같으므로 **서식만 갈아끼우면 되고 앞단(촬영·OCR·집계)은 흔들리지 않는다.**
