# 운영 캘린더 — 쓰기 기능

> 상태: **기획 확정 · 개발 착수 전** (2026-09-16)
> 상위: [31-stay-ari-migration-overview.md](31-stay-ari-migration-overview.md) · 진입: [32-ops-admin-area.md](32-ops-admin-area.md)

이번 이전에서 **가장 크고 가장 위험한** 부분이다. 저쪽 원본은 단일 파일 **11,672줄**
(`BuildingCalendar.jsx`).

## StayOps 는 지금까지 Beds24 에 써 본 적이 없다

**이 사실이 이 문서의 전제다.** 지금까지 Beds24 연동은 전부 읽기였다 — 예약을 받아오고, 방
목록을 받아오고, 차단을 받아온다. 이번에 처음으로 **쓴다.**

저쪽이 쓰는 엔드포인트는 둘이다.

```
POST /inventory/rooms/calendar   가격 · 최소 숙박일
POST /bookings                   예약 생성 · 수정 · 취소
```

### 저쪽 서버 함수는 7개가 전부다 (2026-09-16 실측)

`BuildingCalendar.jsx` 가 부르는 API 를 전부 세어 보면 이렇다.

| 함수 | 하는 일 | Beds24 |
| --- | --- | --- |
| `getCachedPrices` | 가격·minStay·numAvail·override 읽기 | 읽기 |
| **`setRoomPrices`** | 가격 쓰기 (큐) | `/inventory/rooms/calendar` |
| **`setMinStay`** | 최소 숙박일 쓰기 | `/inventory/rooms/calendar` |
| `createBooking` | 예약 생성 | `/bookings` |
| `updateBooking` | 예약 수정 | `/bookings` |
| `cancelBooking` | 예약 취소 | `/bookings` |
| `getPriceJobStatus` · `triggerPriceJobNow` | 작업 큐 조회·즉시 실행 | — |

**`numAvail`(재고)과 `override: blackout`(차단)을 쓰는 경로는 없다.** 둘 다 **읽기만** 한다.

그럼 저쪽에서 「블록」은 어떻게 만드는가 — **예약으로 만든다.** `createBooking` 으로 만든
예약이 곧 블록이고, 해제는 `cancelBooking` 이다. `isAppCreatedBlockEntry` ·
`isBulkDeletableBlockEntry` 가 있는 이유가 이것이다 — **앱이 만든 블록(예약)과 사람이 Beds24
화면에서 직접 건 blackout 을 구분**해야 하기 때문이다. 후자는 앱이 지울 방법이 없다.

> **우리가 취할 태도.** blackout 쓰기는 Beds24 가 지원하므로 나중에 열 수 있지만,
> **1차 이전에서는 저쪽과 똑같이 「블록 = 예약」으로 간다.** 이유는 두 가지다 —
> ① 저쪽 데이터와 개념이 어긋나면 병행 기간에 두 화면이 다른 소리를 한다.
> ② StayOps 는 이미 blackout 을 **읽어서** 표시하고 있다([15](15-reservation-calendar.md)).
> 읽기는 blackout, 쓰기는 예약 — 이 비대칭을 화면에서 숨기지 말고 범례로 구분해 보여준다.

**잘못 쓰면 채널에 그대로 나간다.** 가격을 0 으로 쓰면 0 원에 팔리고, 재고를 열면 팔리면 안 되는
방이 팔린다. 우리 DB 가 틀어지는 것과는 급이 다르다.

> 저쪽 코드에도 크레딧 인식 재시도와 가드가 들어 있다(`beds24PostV2WithRetry` ·
> `beds24PostV2WithGuard`). 이미 한 번 데였다는 뜻으로 읽는다 — 우리도 같은 자리를 밟는다.

취소 지표(취소율·취소 금액·예약→취소 시간)는 [34](34-metrics-and-automation.md) 참고.

**예약 취소는 쓰기다.** 저쪽은 예약 상세에서 취소할 수 있고 **Beds24 에도 반영된다**
(확인창: *"This will also be cancelled in Beds24"*). 되돌릴 수 없으므로 확인 단계가 필요하다.

**차단은 이미 읽고 있다.** 2026-09-11 에 Beds24 의 `override: blackout` 을 읽어와 캘린더에
표시하는 기능을 만들었다 → [15-reservation-calendar.md](15-reservation-calendar.md).
이번에는 **거기에 쓰기를 더한다.** 읽는 규칙(양끝 포함, 열린 꼬리 제외)은 그대로 쓴다.

## 저쪽 설계 — 읽어낸 내용

> **가져올 기준은 저쪽 설계 그 자체다**(2026-09-16 확정). 캘린더는 매출을 운영하는 곳이라
> 임의로 단순화하지 않는다. 아래는 원본 코드에서 읽어낸 규칙이며, 구현은 이것을 따른다.

### 가격은 큐를 거쳐 비동기로 쓴다 — 이 구조가 핵심이다

**화면에서 Beds24 로 바로 쏘지 않는다.** 원본 `setRoomPrices` 의 주석이 명시한다 —
*"Firestore에 price job 생성 — 즉시 Beds24 호출 없음"*.

```
화면  →  setRoomPrices          작업을 큐에 넣고 즉시 응답 (jobId)
      →  price job (queued)
      →  워커 (1분마다)         큐에서 하나 집어 Beds24 에 순차 전송
      →  Beds24 POST /inventory/rooms/calendar
```

**왜 이렇게 하는가.** 42칸을 바꾸면 여러 객실 × 여러 날짜를 Beds24 에 써야 하는데, Beds24 는
5분 단위 크레딧 제한이 있어 한 번에 다 보낼 수 없다. 동기로 처리하면 사용자가 몇 분을 기다리거나
타임아웃이 난다. **모바일에서는 더 나쁘다 — 화면을 끄면 요청이 끊긴다.**

큐 방식이면 **저장을 누른 순간 응답이 오고, 나머지는 서버가 한다.** 「누워서도 쓴다」는 요구와
직접 맞닿아 있다.

#### 작업 상태

| 상태 | 뜻 |
| --- | --- |
| `queued` | 접수됨. 워커를 기다린다 |
| `processing` | 처리 중. **한 번에 하나만**(락) |
| `completed` | 전부 성공 |
| `partial_failed` | **일부만 성공** — 어느 객실이 실패했는지 남긴다 |
| `failed` | 실패 |

원본이 이미 다루고 있는 것들, **전부 가져온다**:

- **멈춘 작업 회수** — `processing` 인 채로 오래 남은 작업을 `queued` 로 되돌리거나 실패 처리한다.
  워커가 죽으면 작업이 영원히 갇힌다.
- **작업 합치기**(`coalescedIntoJobId`) — 같은 대상에 대한 작업이 쌓이면 하나로 묶는다. 안 하면
  같은 칸을 여러 번 쓴다.
- **락**(`lock_busy`) — 두 작업이 동시에 같은 객실을 쓰면 나중 것이 앞의 것을 덮는다.
- **API 쿨다운**(`beds24_api_cooldown`) — 크레딧이 모자라면 다음 주기로 미룬다.
- **진행 상황 조회** — `progress: { processed, total, results }` + 실패한 roomId 목록.
- **7일 지난 작업 정리.**

#### 낙관적 표시 (`pendingPriceCellMap`)

큐에 들어간 가격은 **아직 Beds24 에 없지만 화면에는 새 값으로 보여준다.** 안 그러면 저장 직후
옛 값이 보여 「안 됐나?」 하고 다시 누른다. 반영이 확인되면 실제 값으로 바뀐다.

### 채널별 가격

Beds24 의 가격 슬롯과 채널 대응:

| 슬롯 | 채널 |
| --- | --- |
| `p1` (price1) | **에어비앤비** |
| `p2` (price2) | **부킹닷컴** |
| `p3` (price3) | 에어비앤비 대체가 |

**편집은 에어비앤비 가격만 한다.** 저장 시 `p1` 과 `p3` 에 **같은 값**을 쓰고, **`p2`(부킹닷컴)는
건드리지 않는다.** 부킹닷컴 가격은 읽어서 보여주기만 한다.

**부킹닷컴은 Beds24 가 알아서 맞춘다**(2026-09-16 확인). 에어비앤비 가격을 바꾸면 Beds24 쪽
규칙에 따라 부킹닷컴 가격이 **자동으로 따라 조정된다** — 두 플랫폼의 가격대가 조금 다르기
때문이다.

그래서 **우리가 `p2` 를 쓰면 안 된다.** 쓰면 Beds24 의 규칙과 충돌한다. 읽어서 보여주기만 한다.
저쪽이 `p1`·`p3` 만 쓰는 이유가 이것이다.

읽을 때는 `p1` 을 먼저 보고, 없으면 `p3` 로 떨어진다(`preferAirbnbPrice3` 옵션).

### 객실 하나가 roomId 여러 개일 수 있다

같은 「201호」가 Beds24 에서 여러 `roomId` 로 존재한다(유닛 분리). 가격을 쓸 때는 **활성 유닛
전부에 써야** 한다 — 하나만 쓰면 다른 유닛이 옛 가격으로 팔린다.

**활성 판정**: 그 날짜의 `minStay` 가 `1 이상, INACTIVE_MINSTAY_THRESHOLD 미만`이면 활성.
StayOps 에도 같은 개념이 있다(`BEDS24_INACTIVE_MIN_STAY_THRESHOLD = 50`) — **기준을 맞춘다.**

활성 유닛이 하나도 없으면 **전체 유닛에 쓴다**(안전 쪽으로 떨어진다).

> **하드코딩된 예외가 하나 있다**: 아라키초A 501호는 `roomId` 두 개(`502229`, `383975`)를
> 반드시 함께 갱신한다. 프론트와 백엔드 양쪽에 같은 예외가 박혀 있다
> (`shouldMergeArakichoA501PriceRoomIds`). **이런 예외는 코드가 아니라 데이터로 옮긴다** —
> 객실 마스터에 「함께 갱신할 유닛」을 두면 새 건물이 생겨도 코드를 고치지 않는다.

### 조정 방식 두 가지

| 모드 | 입력 | 계산 |
| --- | --- | --- |
| **직접 입력** | 금액 | 선택한 칸 전부를 그 금액으로 |
| **퍼센트** | ±% | 칸마다 `현재가 × (1 + %/100)`, 반올림 |

퍼센트는 **칸마다 현재가가 기준**이라 결과 금액이 칸마다 다르다. 프리셋 버튼:
`-20 · -10 · -5 · +5 · +10 · +20 · +30`.

> **모드 토글은 두지 않는다** (2026-09-16 확정). 저쪽은 `adjustMode` 로 `direct` / `percent` 를
> 갈라 놓았지만, **둘은 같은 값을 정하는 두 가지 방법일 뿐**이라 한 화면에서 같이 쓴다.
>
> ```
> 현재 평균 ¥26,100  →  변경 ¥30,000  (+15%)
> [-20%][-10%][-5%][+5%][+10%][+20%][+30%][± %]
> ```
>
> 금액을 직접 쓰면 **% 배지가 계산되어 바뀌고**, 퍼센트를 누르면 **금액이 계산되어 채워진다.**
> 어느 쪽으로 넣든 결과는 한 곳에 모이므로 모드를 고를 이유가 없다. 퍼센트일 때는 칸마다
> 결과가 다르므로 「변경」을 **범위**로 표시한다(`¥35,600 ~ ¥55,800`).
>
> 서버로 보낼 때는 저쪽과 같이 `adjustMode` 를 그대로 기록한다 — 이력에 「퍼센트로 바꿨다」가
> 남아야 한다. **화면에서만 합치고 데이터는 구분한다.**

### 선택은 「객실 × 날짜」 조합이다

`selectedCells` 는 **room-date 쌍의 목록**이다(cartesian product). 「201호의 9/20」과
「202호의 9/21」처럼 **들쭉날쭉한 선택**이 가능하다. 단순한 사각형 범위가 아니다.

> **이 자유도를 모바일에서 어떻게 줄 것인가가 설계의 숙제다.** 아래 참고.

### 이력을 남긴다

가격 변경 시 **칸 단위로** 기록한다 — 날짜 · 객실 · 이전가 · 새 가격, 그리고 **누가 바꿨는지**
(이름·이메일). 저쪽의 `price_change_logs` 에 해당한다. 화면에도 이력이 보인다
(`PriceChangeHistory.jsx`).

## 요금이 우리 표로 들어오는 두 경로 (2026-09-17 구현)

### ① 백필 — 어제 ~ **+12개월**

저쪽과 **같은 창**이다 (`tokyoNow.add(12, "month")` — `functions/index.js` 2859 · 3252 · 6789행).
그 안에서 Beds24 가 설정된 만큼 돌려준다. 2026-09-17 실측으로 **2027-04 까지 97.8%** 가 차 있고
그 뒤는 아직 가격을 안 넣은 구간이라 비어 있다.

```
BEDS24_WEBHOOK_SECRET=… bash scripts/dev/beds24-backfill-rates.sh
```

**과거는 가져올 수 없다.** `GET /inventory/rooms/calendar` 는 **오늘 이후만** 준다 —
2025-06 · 2026-01 을 요청해도 0구간이고, 오늘 이전을 포함해 요청하면 **오늘부터** 잘라서 준다
(2026-09-17 실측). 과거 매출은 가격표가 아니라 **예약의 실제 금액**으로 계산한다.

우리 표는 `upsert` 만 하고 지우지 않으므로 **오늘부터 이력이 저절로 쌓인다.**

#### `includeLinkedPrices` 는 필수다 (2026-09-17 회귀)

`includePrices=true` 만 붙이면 **그 유닛에 직접 박아 둔 값만** 온다. Beds24 에서 가격은 연결로
퍼지는데(같은 물리적 방의 다른 유닛, 채널별 파생가) 그 연결분은 파라미터를 따로 켜야 나온다.
저쪽 원본은 처음부터 둘 다 보낸다(`functions/index.js` 2966행).

실측 — 오쿠보C · 2026-10-01:

| | 648399 (그날 판매 중) | 450096 (그날 비활성) |
| --- | --- | --- |
| 없이 | `p1 —` | `p1 79000` `p2 —` `p3 —` |
| 켜고 | **`p1 79000`** | `p1 79000` **`p2 116920`** **`p3 102700`** |

없이 받으면 두 가지가 동시에 빈다.

1. **파생가로 파는 유닛의 가격 전부.** 오쿠보C 는 10/1 에 판매 유닛이 450096 → 648399 로
   바뀐다(450096 의 minStay 가 50 으로, 648399 가 2 로). 우리는 활성 유닛을 정확히 골랐는데
   그 유닛에 가격이 없어서 **10/1 부터 가격 칸이 통째로 비었다.** 최소숙박 `2` 는 그대로
   보였으니 「안 파는 날」과 구별도 안 됐다.
2. **모든 방의 `price2`(부킹닷컴) · `price3`(대체가).** 33,306행 전부 0건이었다.
   화면은 에어비앤비 가격(`p1`)만 쓰고 있어 티가 나지 않았다.

같이 고친 것 — **응답 쪽 넘기기**(`pages.nextPageExists` / `nextPageLink`). 저쪽은 이 처리가
가격 조회에만 빠져 있었고 「잘린 뒤쪽은 조용히 사라져 영구 미동기화」가 됐다고 주석에 남겼다.
우리는 건물 단위로 나눠 불러 아직 한 쪽에 들어오지만, 객실이 늘면 같은 자리에서 끊긴다.
쪽 상한(20)에 닿으면 `skipped` 에 남긴다.

### ② 웹훅 — 가격이 바뀌면 그때

**저쪽은 가격 변경을 전부 웹훅으로 받는다**(`exports.priceWebhook`). 백필만으로는 Beds24 화면에서
가격을 바꾼 순간부터 우리 표가 틀린 값을 들고 있게 되고, 판매 캘린더가 **없는 가격을 보여주는
화면**이 된다.

배달은 **예약 웹훅과 같은 엔드포인트**로 오고 예약이 들어 있지 않다.

```
V1(GET)  ?roomId=440617&action=PRICE_CHANGE&propId=176430
V2(POST) {"roomId":440617,"action":"PRICE_CHANGE","propId":176430}
```

`src/lib/beds24/price-webhook.ts` 가 처리한다.

| | |
| --- | --- |
| 판정 | `roomId` 가 있고 `action` 이 `PRICE_CHANGE`·`SYNC_ROOM`·**없음** — 저쪽과 같은 집합 |
| 모르는 방 | **Beds24 를 부르지 않고 끝낸다.** 남의 계정 웹훅으로 크레딧을 쓰지 않는다 |
| 범위 | 그 **건물** 전체를 다시 가져온다 — `/inventory/rooms/calendar` 가 건물 단위로 응답하므로 어차피 다 온다 |
| 디바운스 | **건물별 60초.** 일괄 변경이면 웹훅이 객실 수만큼 쏟아진다 |

**디바운스는 건물별이어야 한다.** 조직 전체로 재면 아라키초A 를 방금 동기화한 탓에 가부키초
웹훅이 통째로 버려진다 — 여러 건물의 가격을 함께 바꾸면 실제로 그렇게 된다.

> **쓰기를 켤 때 할 일.** 우리가 Beds24 에 가격을 쓰면 Beds24 가 웹훅을 되돌려 보낸다.
> 지금은 쓰지 않아 문제가 없지만, 그때는 「우리가 만든 변경인가」 판정이 필요하다.
> 그때까지는 디바운스가 그 역할을 겸한다.

**2026-09-17 실측 — 가격 웹훅은 우리에게 오지 않고 있다.**

| | |
| --- | --- |
| 2026-07-22 ~ 09-16 배달 | **20,157건, 전부 예약** |
| 가격 배달 | **0건** |

Beds24 설정 화면의 그 칸은 **「予約Webhook」**(예약 웹훅)이고, 거기 우리 URL 을 포함해 3개가
등록돼 있다. 저쪽의 첫 번째 URL 이름도 `beds24**booking**webhook` 이다 — 저쪽 `priceWebhook` 은

## 1박 갭 감지 — 이 기능이 업무 시간을 줄인다 (2026-09-16 정밀 확인)

> **사용자 확인:** 「재고·최소숙박은 내 업무 시간을 굉장히 단축시켜주는 기능이다. 1박 갭 감지가
> 중요하다.」 → 원본 `getCheckInGapInfo` · `gapCellSet` 을 줄 단위로 읽어 아래에 옮겼다.
> **이 규칙은 임의로 단순화하지 않는다.**

### 무엇을 찾는가

**「하루만 비어 있는데 최소 2박이라 아무도 살 수 없는 날」.**

```
11/20        11/21         11/22
예약 있음  │  비어 있음  │  예약 있음
           └ 팔 수 있는 밤은 1박
             그런데 minStay = 2
             → 아무도 못 산다. 이 밤은 그냥 버려진다
```

객실 90개 × 12개월을 눈으로 훑어 이런 날을 찾는 것이 원래 업무였다. **자동으로 찾아서 한 번에
`1박`으로 바꾸는 것**이 이 기능의 전부다.

### 판정식 (원본 그대로)

```js
availableNightsFromDate =
    nextDateStatus === "blocked"   ? 1
  : nextDateStatus === "available" ? 2
  : 0;

isSegmentEntry = (previousDateStatus === "blocked" || previousDateStatus === "past");

isOneNightMinStayGap =
  availableNightsFromDate === 1 && cellMinStay === 2 && isSegmentEntry;
```

세 조건이 **전부** 맞아야 한다.

| 조건 | 뜻 | 왜 필요한가 |
| --- | --- | --- |
| `availableNightsFromDate === 1` | **내일이 막혀 있다** | 이틀 이상 이어지면 2박으로 팔 수 있다 |
| `cellMinStay === 2` | 그 칸의 최소 숙박일이 **정확히 2** | 1이면 이미 팔린다. 3 이상은 다른 정책이다 |
| `isSegmentEntry` | **어제가 막혀 있거나 과거다** | 구간의 **첫날**만 센다. 안 그러면 같은 공실을 여러 번 센다 |

### 「막혀 있다 / 팔 수 있다」의 정의

`available`(팔 수 있다)이 되려면 **다섯 가지가 전부** 참이어야 한다.

| # | 검사 | 아니면 |
| --- | --- | --- |
| 1 | `minStay` 를 숫자로 읽을 수 있다 | `unknown` — **갭으로 세지 않는다** |
| 2 | `override !== "blackout"` | `blocked` (price_blackout) |
| 3 | `1 ≤ minStay < INACTIVE_MINSTAY_THRESHOLD` | `blocked` (inactive_room) |
| 4 | `numAvail > 0` | `blocked` (numavail_zero) |
| 5 | 그 날짜에 예약·블록이 없다 | `blocked` (reservation_or_block) |

**1번이 중요하다.** 가격 데이터가 아직 안 온 칸은 `unknown` 이 되고, `unknown` 은
`availableNightsFromDate = 0` 이라 갭이 되지 않는다. **모르는 것을 갭이라고 하지 않는다** —
잘못 감지해서 minStay 를 바꾸면 실제로 팔리면 안 되는 방이 팔린다.

3번의 `INACTIVE_MINSTAY_THRESHOLD` 는 StayOps 의 `BEDS24_INACTIVE_MIN_STAY_THRESHOLD = 50`
과 같은 개념이다 — **기준을 맞춘다.**

### 객실 하나에 roomId 가 여럿일 때 (듀얼 객실)

여기가 가장 까다롭다. 같은 「201호」가 Beds24 에서 두 계정으로 존재할 수 있다.

- **오늘 날짜**: 팔 수 있는 유닛들 중 `pickPreferredRoomInfo` 로 하나를 고른다
- **어제·내일 날짜**: `getDualRoomPhysicalStatus` 를 쓴다 — **roomId 가 바뀌어도 같은 방으로 본다**

원본 주석이 이유를 적어 놨다:

> *"For dual-account rooms, physical continuity matters more than keeping the same Beds24 roomId.
> If the sellable roomId changes on the next date, the room should still be treated as continuously
> sellable for gap detection."*

**물리적으로 같은 방이면 이어진 것이다.** 이걸 안 하면 유닛이 바뀌는 날마다 가짜 갭이 쏟아진다.

듀얼 객실에는 검사가 둘 더 붙는다 — `roomId` 가 없는 예약(`generic_reservation_without_roomid`)과
`roomId` 가 없는 블록이 그 날짜에 걸리면 **어느 유닛인지 몰라도 막힌 것으로 본다.** 안전 쪽이다.

### 감지 범위와 제외

- **예약이 하나도 없는 객실은 통째로 건너뛴다** (`roomAllReservationsMap[room].length === 0`).
  예약이 없으면 갭이라는 개념 자체가 없다
- **과거 날짜도 감지 대상에는 들어간다.** 다만 「자동 선택」 버튼이 **자기가 과거를 걸러낸다**
- 이미 예약이 찬 칸은 `isGap` 이 아니다 (`!isFullyOccupied && gapCellSet.has(...)`)
- 성능: 화면 범위 전체를 `gapInfoByCellKey` 에 미리 계산해 O(1) 조회한다.
  90객실 × 30일 = 2,700칸을 매 렌더마다 재계산하면 안 된다

### 구현 (2026-09-17)

| | |
| --- | --- |
| 판정식 | `src/lib/ops-gap-detection.ts` — **순수 모듈** |
| 회귀 테스트 | `src/lib/__tests__/ops-gap-detection.test.ts` (14건) |
| 데이터 | `room_daily_rates` (`min_stay` · `num_avail` · `override_kind`) |
| 화면 | 판매 캘린더 격자 — 갭 칸 빨간 테두리 + 최소숙박 `2` 빨간색 + 상단 개수 배지 |

저쪽과 다르게 한 것 하나 — **점유 판정에 예약·블락을 함께 본다.** `numAvail` 은 요금 동기화
시점의 값이라 그 뒤에 들어온 예약을 모른다(예약은 웹훅으로 실시간, 요금은 주기 동기화).
그 틈으로 이미 팔린 밤이 갭으로 잡히면 minStay 를 1로 바꿔 놓고 「왜 안 팔리지」가 된다.

듀얼 유닛은 **날짜별로** 판단한다. `rooms.status` 는 `inventory-sync` 가 읽은 **오늘 하루의
스냅샷**이라 「10월 3일에 이 유닛이 팔렸는가」에는 답하지 못한다. 한 행에 유닛이 여럿이면
그 날짜에 **팔 수 있는 유닛**의 값을 쓴다(저쪽 `pickPreferredRoomInfo(sellableInfos)` 와 같다).

창의 **하루 바깥까지** 요금을 읽는다. 판정이 어제·내일을 보는데 가장자리에서 데이터가 끊기면
실제 갭을 「모른다」로 흘려보낸다.

### 유닛이 여럿인 칸 — 운영 값과 가격을 다르게 다룬다 (2026-09-17)

한 캘린더 행 뒤에 Beds24 **방 계정이 여럿**일 수 있다. 오쿠보C 는 셋이고 그중 하나가
**메인**이다.

```
450096 오쿠보 2-1 (메인)  p1 79000  p2 116920  p3 102700   minStay 50 ← 10/1 부터 비활성
496532 1-13-1-2           p1 79000  p2 —       p3 —        minStay 99
648399 OkuboCC            p1 79000  p2 —       p3 —        minStay 2  ← 10/1 부터 판매
```

메인은 Beds24 화면에서 AirBnB · Booking.com · Agoda · Homepage 네 줄을 다 들고 있고,
나머지 둘은 에어비앤비 한 줄만 연결로 받는다. 그래서 **부킹닷컴·아고다 가격은 메인에만
있다.** 판매 중인 유닛에는 없다.

규칙 (`src/lib/ops-rate-merge.ts`, 저쪽 `getDisplayUnitInfosForDate` +
`getMergedRoomChannelPrices` + `getMinStayFromUnitInfos`):

| | 어디서 읽나 | 여럿이면 |
| --- | --- | --- |
| 최소숙박 | **운영 중인 유닛만** (`1 ≤ minStay < 50`) | 가장 **짧은** 값 |
| 재고 | 운영 중인 유닛만 | 하나라도 있으면 **있다** |
| blackout | 운영 중인 유닛만 | 하나라도 걸리면 **막힘** |
| 가격 p1·p2·p3 | 운영 중인 유닛 **먼저, 없으면 그 행의 아무 유닛** | 항목마다 **처음 나오는 값** |

운영 중인 유닛이 하나도 없으면 그 칸은 **비운다**(저쪽 `EMPTY_PRICE_CELL`).

두 가지를 헷갈리면 안 된다.

- **가격 폴백을 안 걸면** 10/1 부터 부킹닷컴 가격이 사라진다 — 판매 유닛에 없기 때문이다
- **최소숙박까지 폴백을 걸면** 메인의 `50` 이 올라와 「팔 수 없는 날」이 된다.
  그건 팔리는 방을 안 판다는 뜻이다

폴백은 **항목별**이다. 유닛 하나를 골라 그 행을 통째로 쓰지 않는다 — p1 은 판매 유닛 것,
p2 는 메인 것으로 섞이는 것이 정상이다.

### 쓰기 대상 유닛 — **가격과 최소숙박이 서로 다른 유닛으로 간다** (2026-09-24)

읽기는 위 병합 규칙으로 메인을 몰라도 되지만, **쓸 때는 대상 유닛을 골라야 한다.** 저쪽 주석
그대로다 — *"Price writes must target the source price row, while inventory/min-stay writes
must continue to target the active roomId."*

| 쓰는 것 | 대상 | 왜 |
| --- | --- | --- |
| 가격 `p1·p2·p3` | **가격 소스 유닛**(메인) | 가격은 연결로 퍼진다. 소스가 아닌 곳에 쓰면 반영되지 않는다 |
| 최소숙박 · 재고 | **그 날짜에 운영 중인 유닛** | 재고는 유닛마다 따로다. 안 파는 유닛의 minStay 를 바꿔도 아무 일도 안 일어난다 |

오쿠보C 2026-10-01 이면 — **가격은 450096, 최소숙박은 648399.** 둘이 다른 유닛이다.

**엉뚱한 유닛에 써도 Beds24 는 `success: true` 를 돌려준다.** 화면에는 「적용됨」이라 뜨고
실제 채널 가격은 그대로다. 그래서 쓴 뒤 **다시 읽어 대조한다**(워커의 readback 검증) —
소스는 직접 설정값만(`includeLinkedPrices=false`), 연결 유닛은 전파값까지(`true`) 읽는다.
기준이 달라 한 번의 조회로 합칠 수 없다.

판정은 순수 모듈 `src/lib/beds24/write-target-room.ts` + 테스트 12건.

#### 소스 연결은 **API 에서 동기화한다** — 박아 두지 않는다

> **남은 것** — 운영 중인 유닛이 **둘 이상**인 날 어느 쪽에 최소숙박을 쓰는가. 저쪽은

### 페이지를 쭉 내리고, 날짜 머리글이 따라온다 (2026-09-24 확정)

**격자 안에서 스크롤하지 않는다.** 객실이 90개라 안에서 굴리면 작은 창 안을 들여다보는 꼴이
된다. 페이지를 쭉 내리면서 보고, **날짜 머리글과 조작 패널이 화면을 따라온다.**

`position: sticky` 가 붙어 있었는데도 안 먹던 이유 — 격자 카드의 `overflow: hidden`(둥근
모서리용)이 **그 카드를 스크롤 상자로 만든다.** 그러면 안쪽 sticky 는 페이지가 아니라 카드에
붙고, 카드가 페이지와 함께 올라가니 머리글도 같이 사라진다.

`overflow: clip` 으로 바꿨다 — 모서리만 깎고 **스크롤 상자를 만들지 않는다.**

- 머리글은 **불투명해야 한다**(`--card2`). 붙어 있는 동안 아래 객실 줄이 비치면 숫자가 겹친다
- 조작 패널도 `sticky` 다. 아래쪽 객실을 고르는데 조작부가 위에 남아 있으면 값을 넣으려고
  매번 올라와야 한다
- 스크롤 상자는 `.adm .content` 이고 그 위에 상단 바(62px)가 있다 — `top` 은 그 안쪽
  기준이라 0 부터 센다

> 한 번은 반대로 갔었다 — `.ops` 에 `height: 100%` 를 주고 격자 안에서 스크롤하게. 머리글은
> 고정됐지만 **보이는 객실이 한 화면치로 줄어** 정작 아래를 훑을 수가 없었다. 이 화면은
> 「길게 내려 보는」 화면이다.

### 날짜 점프 — 가로축 라벨이 달력이다 (2026-09-24)

화살표는 30일(또는 한 달)씩 옮긴다. **먼 날짜로 가려면 여러 번 눌러야 한다** — 2027년 4월
가격을 보려면 일곱 번이다. 라벨 자체를 눌러 달력에서 고르면 한 번에 간다.

| 뷰 | 고르는 것 | 공용 프리미티브 |
| --- | --- | --- |
| 30일 | **날짜** — 고른 날이 창의 **시작일**이 된다 | `AdminDatePicker` |
| 월간 | **달** | `AdminMonthPicker` |

**달력은 새로 만들지 않는다.** 이 콘솔에는 달력이 하나뿐이다(CLAUDE.md §4a). 여기만의 것은
방아쇠에 뜨는 글자뿐이라, 공용 `AdminDatePicker` 에 `display` 를 선택적으로 더했다 —
고른 날이 곧 30일 창의 시작일이라 방아쇠에는 `09/23 → 10/22` 로 범위가 떠야 한다.

월간 뷰의 URL 파라미터는 `month` 가 아니라 **`ym`** 이다 — 공용 월 선택기가 그 키로 이동한다.
우리만 다른 이름을 쓰면 그 컴포넌트를 못 쓰고 달력을 또 만들게 된다. 월 선택기는 화살표를
스스로 들고 있으므로 그쪽에서는 우리 화살표를 접는다.

### 선택 (2026-09-24 구현)

평소에는 **읽는 화면**이다. 「가격 수정」을 눌러야 칸이 선택 대상이 된다 — 저쪽도 `priceMode`
토글로 갈라 놓았다. 읽으려다 실수로 바꾸는 일을 막는 것이 이 구분의 목적이다.

판정은 순수 모듈 `src/lib/ops-calendar-selection.ts` + 테스트 19건.

#### 스코프 바 — 세 축이 곱해진다

| 축 | 내용 |
| --- | --- |
| 객실 | 전체 / 개별 |
| 기간 | **주 단위** — 요금이 주말가·평일가로 주 단위로 움직인다 |
| 요일 | 전체 / **주말·금~일** / **평일·월~목** / 개별 |

**빈 축은 「전체」다.** 요일을 하나도 안 고르면 전 요일이지, 아무 날도 아닌 게 아니다.
「이번 주 × 금토일 × 3층 전부」가 칩 세 번으로 나온다.

**사내 주말은 금·토·일이다.** 일반적인 토·일이 아니다 — 주말 요금이 금요일부터 붙는다.
여기를 토·일로 바꾸면 **금요일이 평일가로 팔린다.** 테스트로 못 박았다.

주는 **월요일 시작**이고 일요일은 앞 주에 붙는다. 일요일을 다음 주로 밀면 주말 한 덩어리가
두 칩으로 쪼개진다.

#### 직접 조작도 같이 쓴다

- 칸 **드래그** — 누른 칸의 상태가 방향을 정한다(꺼진 칸에서 시작하면 켜고, 켜진 칸에서
  시작하면 끈다). 매 칸 다시 판단하면 드래그가 깜빡인다
- **객실명 클릭** — 그 행 전체
- **날짜 머리글 클릭** — 그 열 전체. **Shift 를 누르면 직전 날짜부터 범위**
- 전부 골라져 있는 묶음을 다시 누르면 **해제**된다

#### 축을 바꿔도 직접 찍은 칸은 살아남는다

선택을 통째로 덮어쓰면 칸을 하나씩 손본 것이 축을 건드릴 때마다 날아간다. **직전 축이
기여했던 키만** 걷어내고 새 축을 얹는다(저쪽 `scopeCellKeysRef` 와 같다).

> **고른 칸과 직전 축 키는 한 state 에 둔다**(2026-09-24 회귀). 축 키를 `useRef` 에 넣고
> `setSelection` 업데이터 **안에서** 갱신했더니, 객실 체크를 풀어도 그 칸이 선택에 남았다 —
> React 는 업데이터를 **두 번 부르고**(StrictMode · 동시성 렌더) 두 번째 호출 때는 ref 가 이미
> 새 값이라 걷어낼 대상을 못 찾는다. 판정식(`applyScopeToSelection`)은 처음부터 멀쩡했고
> **부르는 쪽이 업데이터를 불순하게** 썼다. 한 state 로 묶으면 업데이터가 순수해져 몇 번을
> 불려도 같은 결과가 나온다. 회귀 테스트 4건이 그 성질을 고정한다.

#### 자동으로 빠지는 것

- **과거 날짜.** 지난 밤의 가격을 바꿔도 아무 일도 안 일어나는데 「42칸」에는 들어가 사람을
  속인다
- **팔린 밤.** 단, blackout(Beds24 차단)·재고 블록·**취소된 예약**은 막지 않는다 —
  차단해 둔 날도 가격은 미리 정해 둘 수 있고 취소된 예약은 이미 없는 예약이다.
  저쪽 `isCellPriceBlocked` 가 `hasBlockingReservation` 만 보는 이유다

**빠진 개수를 따로 알리지 않는다**(2026-09-24). 한때 「판매된 N칸 제외」 배지를 띄웠는데,
칸을 고를 때마다 나타났다 사라져 **그 아래 격자가 위아래로 들썩였다.** 팔린 칸은 격자에서
빗금으로 이미 보이고, 남는 숫자(**고른 칸 수**)가 무엇이 바뀔지를 정확히 말한다.
현재 가격이 없어 빠지는 칸은 **확인 단계**가 「{count}칸이 바뀝니다」로 말해 준다.

#### 선택하는 동안 화면이 움직이지 않는다

칸을 고르는 내내 위쪽 줄 높이가 고정이다.

- 조작 패널은 **편집 모드 내내** 떠 있다. 선택이 비면 「격자에서 칸을 고르세요」로 자리만 지킨다
- 「현재 → 변경」 자리에 최소 폭을 줘, 값이 들어왔다 나가도 옆 버튼이 좌우로 밀리지 않는다
- 1박 갭 버튼은 **첫 줄**에 있다. 아래 줄이면 갭 칸을 고를 때마다 줄이 새로 생긴다
- 아래 줄(확인 · 경고 · 결과)은 **값을 치거나 누른 뒤에만** 열린다 — 선택 상태로는 열지 않는다
- **줄 높이를 못 박는다.** 현황 줄의 「해제」 버튼(22px)은 고른 칸이 있을 때만 나타나는데,
  높이를 내용에 맡기면 글자만 있을 때 24px · 버튼이 생기면 32px 이 되어 **칸을 고를 때마다
  8px 씩 격자가 밀린다**
- **가로 스크롤바도 숨긴다.** 넘칠 때만 생기는 막대가 줄 높이를 바꿔 격자를 밀어낸다
  (콘솔의 `.ops__props` 와 같은 처리)

### 조작 패널은 **격자 오른쪽**이다 (2026-09-24 확정)

시안(`3-select.dc.html`)대로 세로 카드로 둔다. 한때 위쪽 가로 바로 만들었다가 되돌렸다.

**이유는 세로다.** 위에 두면 그만큼 격자가 아래로 밀리는데, **가격을 고칠 때야말로 객실을
아래까지 길게 봐야 한다.** 옆에 두면 세로를 0 먹는다(편집 모드 상단 소모 115px → 41px).

옆에 두니 세로로 쌓을 자리가 생겨 따라온 것들:

- **무엇을 고치는가**를 머리말에 적는다 — 「아라키초A · 402 · 501 · 502 / 11/20 → 11/22」.
  「9칸」만으로는 **어느 방 어느 날인지 모른 채** 적용하게 되는데, 가격은 채널로 그대로 나간다
- 현재 평균 → 변경을 **큰 숫자 두 개**로 나란히. 가로 바에서는 작게 한 줄에 박혀 잘못 읽기 쉬웠다
- 빠진 칸은 **개수가 아니라 이유**를 적는다 — 「기준이 될 현재 가격이 없습니다」
- 채널 규칙을 화면에 적는다 — 「에어비앤비 가격만 씁니다. 부킹닷컴은 Beds24 가 자동으로
  맞춥니다.」 없으면 「왜 부킹닷컴은 안 바뀌지?」가 나온다
- 확인이 **2단계**다 — 「다음 · N칸 확인」 → 「N개 객실 N칸이 바뀝니다」
- 두 버튼은 **크기가 다르다**(1 : 1.6). 같으면 어느 쪽이 기본인지 안 읽힌다

패널은 **내용 높이만큼만 선다**(`align-self: flex-start`). 늘리면 격자 높이(객실 90개 =
화면 끝까지)를 따라가고, 바닥에 붙은 「다음 · N칸 확인」이 프리셋에서 한참 아래로 떨어진다 —
값을 누르고 적용하려면 마우스가 화면을 세로로 가로질러야 한다. **시안은 객실 11개짜리라 이
차이가 안 보인다.**

편집 모드가 아닐 때 스코프 바는 **바탕이 없다.** 전에는 그 줄이 격자 카드 *안*에 있어
`--surface2` 가 머리띠처럼 읽혔는데, 패널을 옆으로 빼면서 카드 밖으로 나오자 페이지 바탕과
색이 비슷해 **희미한 빈 상자**로 보였다. 편집 모드일 때만 카드가 된다.

가로 바에서 가져온 것: 모드 토글 없는 금액·퍼센트 한 덩어리, 고른 칸 수·조작 안내를 **줄을
새로 만들지 않고** 스코프 바 오른쪽에 붙이는 것.

### 조작 — 가격 · 「1박으로」 (2026-09-24 구현)

계산은 순수 모듈 `src/lib/ops-price-adjustment.ts` + 테스트 18건. **여기서 나온 숫자가 그대로
채널로 나간다** — 반올림 한 번, 기준가 하나만 틀려도 잘못된 가격에 팔린다.

#### 모드 토글이 없다

금액과 퍼센트를 한 줄에 둔다. 금액을 쓰면 % 배지가 계산되고, 퍼센트를 누르면 금액이 채워진다
(기준은 현재 평균). 다만 **적용 결과는 다르다.**

| | 적용 |
| --- | --- |
| 금액 | 고른 칸 **전부**를 그 값으로 |
| 퍼센트 | 칸마다 **자기 현재가** × (1 + %/100), 반올림 |

퍼센트는 칸마다 결과가 다르므로 「변경」을 **범위**로 보여준다(`¥44,000 ~ ¥66,000`).
프리셋은 저쪽과 같은 `-20 · -10 · -5 · +5 · +10 · +20 · +30`.

#### 현재 가격이 없는 칸은 빠진다

퍼센트는 기준가가 있어야 계산되고, 「원래 안 팔던 날」에 값을 넣는 것은 다른 행위다
(저쪽도 `if (!currentPrice.hasPrice) return;` 로 거른다). **몇 칸이 빠졌는지 알려준다.**

#### 확인을 한 번 더 받는다

「{rooms}개 객실 {count}칸이 바뀝니다. **채널에 그대로 나갑니다.**」 그리고 비정상 값에는
경고를 띄운다 — 0원 이하, 현재가의 절반 아래, 현재가의 세 배 위. **막지는 않는다**(있을 수
있는 조정이다) 대신 반드시 눈에 띄게 한다.

#### 저장은 `p1`·`p3` 에 같은 값, `p2` 는 **건드리지 않는다**

부킹닷컴 가격은 Beds24 가 에어비앤비 가격에서 규칙으로 파생시킨다. 우리가 직접 쓰면 그
규칙과 충돌한다(저쪽이 `p1`·`p3` 만 쓰는 이유).

#### 서버가 같은 계산을 다시 한다

화면이 보낸 금액을 그대로 믿지 않는다. 보이는 것과 보내는 것이 갈라지면 「¥30,000 으로
바꿨다」는데 다른 값이 나간다. 실패 사유는 **코드로** 돌려주고 문구는 화면이 사전에서 고른다 —
서버가 한국어를 돌려주면 일본어·영어 사용자에게 한국어가 뜬다.

#### 낙관적 표시

접수하면 **서버 응답을 기다리기 전에** 화면의 가격을 새 값으로 바꾸고 점선 밑줄을 친다.
왕복 동안 옛 값이 보이면 사람은 「안 됐나?」 하고 다시 누른다(저쪽도 같은 이유로 앞으로 당겼다).

#### 「1박으로」 — 이 기능의 목적

1박 갭 칸이 선택에 들어 있으면 그 자리에서 `minStay = 1` 로 보낸다. 찾아만 주고 못 고치면
**오히려 일이 한 단계 는다** — Beds24 를 따로 열어 하나씩 바꿔야 하기 때문이다.

가격과 달리 **그 날짜에 운영 중인 유닛**으로 간다. 실측(오쿠보C · 2026-10-01):

```
같은 칸,  가격  → 450096 (소스/메인)
          최소숙박 → 648399 (그날 파는 유닛)
```

### 작업 큐와 워커 (2026-09-24 구현)

화면에서 Beds24 로 **바로 쏘지 않는다.** `beds24_price_jobs` 에 접수만 하고 워커가 처리한다.

이유 둘 — Beds24 V2 의 **5분 크레딧이 계정 단위**라 객실 90개를 즉시 순차 POST 하면 예약
동기화·웹훅과 다투고 429 가 난다. 그리고 **모바일에서 특히 중요하다**: 접수하고 응답하면
화면을 꺼도 서버가 끝낸다.

| | |
| --- | --- |
| 접수 | `enqueueBeds24PriceJob` — **여기서 대상 유닛이 정해진다**(가격→소스, 최소숙박→운영 중) |
| 워커 | `runNextPriceJob` — 락 하나로 직렬화, 한 번에 최대 5작업 / 45초 |
| 실행 | 접수 직후 호출(정상 경로) + 크론 `3,13,…,53`(안전망) |

#### 쓰고 나서 **반드시 다시 읽는다**

**Beds24 는 값을 반영하지 않고도 `success: true` 를 돌려준다.** 되읽어 대조하지 않으면 반영
실패가 「성공」으로 기록되고, 화면에는 바뀐 값이 뜨는데 채널에 나가는 가격은 옛것이다.

- 우리가 POST 한 유닛 → `includeLinkedPrices=false`(직접 설정값만). 연결된 Daily Price 쪽에
  잘못 쓰인 요청을 성공으로 오인하지 않기 위해서다
- 연결 유닛 → `includeLinkedPrices=true`, **`p1` 만**. 안 맞아도 **작업을 실패로 만들지
  않는다** — 소스 쓰기는 성공했고 전파가 늦은 것일 수 있다. 크게 로그를 남기고 그 유닛의
  로컬 값은 건드리지 않아 다음 동기화가 실제 값으로 채우게 둔다
- **잘린 응답으로는 「일치한다」를 증명할 수 없다.** 쪽이 남으면 검증 실패로 다룬다
- 링크 전파에 시간이 걸려 최대 3회 재시도(500ms · 1s)

`minStay 1` 은 Beds24 가 **빈칸으로 돌려준다.** 양쪽을 1 로 정규화해 비교하지 않으면
**「1박으로」가 성공했는데 실패로 보고된다.**

#### 검증을 통과한 값만 우리 표에 바로 반영한다

다음 요금 동기화(최대 15분 뒤)를 기다리면 그동안 화면이 옛 값을 보여주고, 사람은 반영이 안
된 줄 알고 한 번 더 바꾼다.

#### 요금 동기화가 **양보한다**

저쪽이 실제로 겪은 사고다 — 작업이 POST 후 검증 재시도를 도는 사이 주기 동기화가 Beds24 에서
옛 가격을 읽어 캐시를 덮었고, 「Beds24 가 되돌렸다」는 허위 이력까지 남겼다. `rates-sync` 는
대기 중인 작업이 있으면 `202 yielded_to_price_job` 으로 물러난다.

#### 크레딧 쿨다운은 **모든 경로가** 본다

429 를 맞거나 잔여 크레딧이 10 미만이면 `beds24_sync_locks` 의 `api_cooldown` 을 켠다.
쓰기만 쉬면 크론이 계속 긁어 한도가 안 풀린다. 쉬는 시간은 Beds24 가 알려준 리셋 +2초,
15~300초로 가둔다.

#### 그 밖에

- **멈춘 작업 회수** — 15분 넘게 `processing` 이면 되돌린다. 서버리스에서는 함수가 중간에
  사라지는 일이 정상 범주다
- **작업 합치기** — 같은 건물·같은 종류·2분 안이면 하나로 합친다. 같은 날짜는 나중 것이
  이기고, **항목별이 아니라 날짜 단위로 통째로** 덮는다. 안 합치면 중간 상태가 채널로
  나간다(5만원 → 6만원인데 5만원이 실제로 팔릴 수 있다)
- 작업 락 수명 15분 — 저쪽은 5분이었다가 *"백오프 + 검증 재시도로 6분 넘게 도는 job의 락이
  만료되어 두 번째 job이 같은 roomId에 동시에 POST"* 하는 사고를 겪고 올렸다

#### 실측 (2026-09-24)

11개월 뒤 빈 날짜(201호 · 2027-08-15)에서 `minStay 2 → 3 → 2`.

```
POST → 되읽기 검증 → 로컬 반영 → completed
Beds24 직접 조회:  2027-08-15 minStay=3   (바뀌었다)
원복 후:           2027-08-13~17 minStay=2 (구간이 원래대로 합쳐졌다)
```

무효 쓰기(같은 값)만으로는 **POST 가 아무것도 안 해도 통과한다.** 그래서 실제로 바꿨다가
되돌려 확인했다. 요금 동기화 양보도 확인 — 대기 작업을 두니 `202 yielded_to_price_job`.

### 읽기는 쪽을 나눠야 한다 (2026-09-17 회귀)

PostgREST 는 한 번에 **1,000행까지만** 준다(Supabase `db-max-rows` 기본값). 초과분은 오류가
아니라 **조용히 잘린다** — 화면은 멀쩡히 그려지고 데이터만 사라진다.

30일 창 하나에 필요한 행:

| 표 | 행 수 | 1,000행 |
| --- | --- | --- |
| `room_daily_rates` | 객실 91 × 32일 = **2,912** | **넘는다** |
| `reservations` | 716 | 아직 밑 |
| `room_blocks` | 5 | 밑 |
| `rooms` | 91 | 밑 |

첫 화면에서 실제로 터졌다 — **9/28 부터 가격·최소숙박이 통째로 비어 보였다.** 값이 없는 칸은
「안 판다」로 그리므로 잘린 것과 팔지 않는 날을 화면에서 구별할 수 없다. 갭 판정도 그 구간을
전부 `unknown` 으로 봤다.

`readAllPages()` (`src/lib/ops-calendar.ts`) 로 네 표를 전부 쪽 나눠 읽는다. 예약은 지금
1,000행 밑이지만 같이 고쳤다 — 넘는 순간 **예약 막대가 조용히 사라지고**, 그건 이미 팔린 방을
비었다고 보여준다는 뜻이다.

쪽을 나눌 때는 **정렬이 유일해야 한다.** 같은 값이 여럿이면 쪽 경계에서 어떤 행은 두 번 오고
어떤 행은 한 번도 안 온다. 날짜 뒤에 `id` 를 붙여 순서를 못 박았다(요금은 `(room_id,
stay_date)` 가 유니크라 그대로 확정).

### 고치는 방법

| 버튼 | 값 | 언제 |
| --- | --- | --- |
| **1박으로** | `minStay = 1` | **이게 본래 목적이다.** 버려지던 하루를 판다 |
| 2박으로 | `minStay = 2` | 되돌리기 |
| 직접 입력 | 3 ~ 30 | 성수기·장기 정책 |

`POST /setMinStay` 로 `cells: [{roomName, date, dateKey, roomId, minStay}]` 를 보낸다.
서버가 roomId 별로 묶어 `calendar: [{from, to, minStay}]` 로 Beds24 에 쓴다.
**가격과 같은 큐를 탈 수 있다** — 응답에 `queued: true` + `jobId` 가 오면 워커가 처리한다.

### 원본에 있던 함정 — 고쳐서 가져온다

원본 주석에 실패 기록이 남아 있다. **같은 자리를 밟지 않는다.**

| 원본에서 있었던 일 | 우리가 할 것 |
| --- | --- |
| 롤백이 `catch` 에만 있었다. `fetch` 는 `.catch` 로, 타임아웃은 `Promise.race` 로 resolve 되어 **catch 에 도달하지 않았다.** 서버가 실패해도 낙관적 minStay 가 화면과 캐시에 남아 건물을 바꿨다 와도 되살아났다 | **실패 경로를 하나로 모으고** 낙관적 패치를 반드시 되돌린다 |
| 「최신 서버에서 재조회」라는 주석만 있고 **실제 재조회가 없었다.** 화면이 낙관적 값만 보고 있었다 | 쓰기 직후 **되읽어 대조한다** (「쓰기 안전장치」 ③과 같은 원칙) |
| 롤백 백업으로 `roomPrices` 와 `priceCache` **전체를 `structuredClone`** 했다. 수 MB 가 되어 적용 직후 메인 스레드가 멈칫했다 | **바뀌는 칸의 이전 `m` 값만** 백업한다 |
| 타임아웃 180초 → 실패로 처리하지만 **Beds24 에는 적용됐을 수 있다** | 「타임아웃 — 반영됐을 수 있음」을 **실패와 구분해서** 보여준다 |

## 뷰 모드 두 가지 — 월간 / 30일 (2026-09-16 확인)

저쪽 캘린더에는 격자의 **가로축을 정하는 토글**이 하나 더 있다(`viewMode`). 지금까지 못 보고
있었는데, 실제로는 이쪽이 **평소에 쓰는 모드**다.

| | `monthly` (월간) | `rolling` (30일) |
| --- | --- | --- |
| 버튼 표시 | `Monthly` | `30-Day View` |
| 가로축 | 그 달 **1일 ~ 말일** | **시작일부터 30일** |
| 시작일 | 달의 1일 | **어제** (오늘 − 1일) |
| 이동 | 이전 달 / 다음 달 | **± 30일** |
| Today | 이번 달로 | **시작일을 다시 「어제」로** |

**핵심은 「어제부터 30일」이다.** 오늘을 왼쪽 끝에 붙이지 않고 **하루만 뒤로 물려서** 시작한다 —
어제 체크아웃이 왼쪽 끝에 걸려 보이고, 그 오른쪽이 오늘 이후 한 달이다. 월간 뷰는 달이 바뀔 때
「오늘」이 격자 오른쪽 끝에 처박히는데, 30일 뷰는 **언제 열어도 오늘이 항상 왼쪽 근처**다.

원본 그대로:

```js
// rolling: rollingStartDate 부터 30일
for (let i = 0; i < 30; i++) days.push(start.add(i, 'day'));

// Today / 모드 전환 시
const yesterday = new Date();
yesterday.setDate(yesterday.getDate() - 1);
setRollingStartDate(yesterday);
```

**날짜 점프 검색도 이 모드로 떨어진다.** 날짜를 입력해 이동하면(`applyDateSearch`) **무조건
`rolling` 로 전환하고 그 날짜를 시작일로 잡는다.** 「2026-12-24 를 보자」가 곧 「12/24 부터
30일을 보자」다. 그리고 그 검색의 **Today 버튼은 도쿄 기준 오늘**을 넣는다
(`Intl.DateTimeFormat` / `Asia/Tokyo`) — StayOps 의 도쿄 운영일 규칙과 이미 같다.

### 우리는 이렇게 가져온다

- **두 모드 전부 가져온다.** 기본값은 **30일 뷰**로 둔다 — 열자마자 오늘이 보여야 한다.
- 30일 뷰의 시작일 계산은 **도쿄 기준 어제**다. 브라우저 로컬 시간으로 `setDate(-1)` 하지 않는다
  (저쪽은 로컬 기준이라 밤에 열면 하루 어긋날 수 있다 — **이건 고쳐서 가져온다**).
- 이동 단위는 ±30일. **월 단위로 바꾸지 않는다** — 바꾸면 오늘이 다시 격자 끝으로 밀린다.
- 월간 뷰의 월 이동은 StayOps 의 `shiftMonthKey()` 를 쓴다 (CLAUDE.md 4a).

## 선택과 조작 — 저쪽 실제 설계 (2026-09-16 재확인)

앞서 「드래그 방식이라 모바일에 못 옮긴다」고만 적었는데, **실물을 보니 훨씬 정교했다.**
드래그는 여러 선택 수단 중 하나일 뿐이고, **이미 모바일에서도 쓸 수 있는 구조가 들어 있다.**

### 평소에는 일반 캘린더, 「가격 수정」을 누르면 선택 모드

`priceMode` 토글이다(`isBulkSelectMode = priceMode || gapEditMode`). 이 구분이 중요하다 —

| | 일반 모드 | 선택 모드(가격 수정) |
| --- | --- | --- |
| 칸을 누르면 | **예약 생성 시작** (시작일 → 종료일 두 번 클릭) | 셀 선택 토글 |
| 스코프 바 | 없음 | **뜬다** |
| 드래그 | 스크롤 | 범위 선택 |

**예약 생성과 블록은 별도 탭이 아니라 캘린더에서 바로 한다.** 빈 칸을 클릭하면 시작일,
한 번 더 클릭하면 종료일이 되어 그 범위로 예약 생성 흐름이 열린다. 같은 날을 두 번 누르면
0박이라 선택이 취소된다. 다른 방을 누르면 시작점이 그 방으로 옮겨간다.

### 스코프 바 — 자유도 높은 일괄 선택

선택 모드에서 위에 뜨는 세 줄. **이것이 이 화면의 핵심 조작부다.**

```
Scope    1 rooms × 11 dates = 11 cells

ROOMS    [전체] [201호] [202호] [301호] [302호] [401호] [402호] [501호] …
PERIOD   [전체] [10/26–11/1] [11/2–11/8] [11/9–11/15] [11/16–11/22] …   ← 주 단위
DAYS     [매일] [주말·금~일] [평일·월~목] [월][화][수][목][금][토][일]
```

- **주 단위 기간 칩** — 「11/9–11/15」처럼 한 주씩. 임의 기간이 아니라 주 단위로 끊어
  누르기 쉽게 했다
- **요일 프리셋** — 같은 프리셋을 다시 누르면 해제된다
- **선택 결과를 식으로 보여준다** — `1 rooms × 11 dates = 11 cells`

> **「주말」은 금·토·일이다.** 월~목이 평일이다(원본 주석: *「금·토·일(사내 주말가) / 월~목」*).
> 일반적인 토·일이 아니므로 **그대로 따라야 한다.** 요금 체계가 그 기준으로 짜여 있다.

이 구조는 **드래그 없이도 원하는 범위를 정확히 집는다.** 「다음 주 주말 전 객실」이 세 번의
탭으로 끝난다 — 모바일에서도 그대로 쓸 수 있다는 뜻이다. 모바일을 위해 새 방식을 발명할 필요가
없고, **이 스코프 바를 좁은 화면에 맞게 배치하면 된다.**

### 선택에서 자동으로 빠지는 것

`buildSelectableCells` 가 거른다.

- **과거 날짜는 못 고른다** — 오늘 이전은 아예 선택 대상이 아니다
- **예약·블록이 있는 칸은 자동으로 빠진다.** 몇 개가 빠졌는지(`skipped`) 세어 알려준다

**이걸 반드시 가져와야 한다.** 「42칸 선택」이라 해 놓고 그중 5칸이 이미 팔린 방이면 그 5칸은
바뀌지 않는데, 말해주지 않으면 바뀐 줄 안다.

판정은 모드마다 다르다 — 가격 모드는 `isCellPriceBlocked`, 갭 모드는 `isCellOccupied`.

### 그 밖의 선택 수단

- **객실 이름의 체크박스** — 그 행 전체 선택
- **날짜 열 머리글 클릭** — 그 열 전체 선택, **Shift 로 범위**
- **드래그** — 사각 범위

## 모바일 입력 설계

**스코프 바를 그대로 쓴다.** 위에서 확인했듯 드래그 없이도 정확한 선택이 되는 구조가 이미 있다.

좁은 화면에서 달라지는 것:

- 세 줄(ROOMS/PERIOD/DAYS)을 **가로 스크롤되는 칩 줄**로. 줄당 한 축
- `1 rooms × 11 dates = 11 cells` 식은 **항상 고정**으로 보인다
- 격자에서의 개별 탭 토글은 그대로 (드래그가 아니라 탭이므로 스크롤과 충돌하지 않는다)
- 드래그 선택은 **데스크톱 전용**으로 둔다 — 없어도 스코프 바로 다 된다

확인 단계는 아래 「확인 단계」와 동일하다.

### 확인 단계

저쪽에도 2단계 흐름이 있다(`step 1: 입력 → step 2: 확인`). **그 구조를 가져오되 내용을
강화한다.**

```
아라키초A · 402, 501, 502호     3개 객실
11월 20일 ~ 26일 · 주말(금~일)   3박
가격  ¥26,100 → ¥30,000          9칸 변경

⚠ 예약이 있어 제외된 칸 2개
⚠ 평소의 1/10 이하인 칸 1개

[ 취소 ]  [ 9칸 저장 ]
```

- **칸 수를 센다.** 예상보다 크면 손이 멈춘다
- **제외된 칸을 밝힌다** — 위 「선택에서 자동으로 빠지는 것」
- 퍼센트 모드는 칸마다 결과가 다르므로 **범위**로 보여준다
- **비정상 값 경고** — 0원, 평소의 1/10 이하, 10배 이상. 막지 않되 한 번 더 묻는다

## 쓰기 안전장치

### 켜기 전까지 쓰지 않는다

**병행 기간에는 이쪽이 Beds24 에 쓰지 않는다**(전체 계획의 확정 원칙). 화면과 로직은 만들되
실제 전송은 막아 둔다.

그러면 「켜기 전에 어떻게 검증하는가」가 남는다. 세 단계로 푼다.

**① 미리보기 모드** — 보낼 페이로드를 화면·로그에 그대로 보여주고 전송은 하지 않는다.
사람이 눈으로 대조할 수 있다.

**② 한 방·짧은 기간으로 실전 확인** — 전환 직전에 **거의 안 쓰는 객실 하나**의 **짧은 기간**에만
실제로 써 본다. Beds24 화면에서 반영을 확인하고 되돌린다. 전면 전환은 그다음이다.

**③ 쓴 것을 되읽어 대조한다** — 쓰기 직후 같은 구간을 다시 읽어 **의도한 값이 들어갔는지** 확인한다.
POST 성공 응답만으로는 부족하다.

### 그 밖에

- **크레딧 인식 대기** — Beds24 는 5분 단위 크레딧 제한이 있다. 응답 헤더
  (`x-five-min-limit-remaining` / `-resets-in`)를 읽어 잔여가 적으면 선제 대기한다.
  헤더 이름은 소문자다 — 2026-08-07 에 대문자로 찾다가 가드가 한 번도 발동하지 않은 적이 있다
  ([01-beds24-integration.md](../engineering/01-beds24-integration.md)).
- **실패 복구** — 여러 칸을 쓰다 중간에 실패하면 **어디까지 됐는지** 남기고 사람에게 보여준다.
  조용히 반만 적용된 상태가 제일 나쁘다.
- **누가 무엇을 바꿨는지 남긴다** — 가격 변경 이력. 저쪽에도 `price_change_logs` 가 있다.
