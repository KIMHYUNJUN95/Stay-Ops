# 운영 캘린더 — 쓰기 기능

> 상태: **기획 확정 · 개발 착수 전** (2026-09-16)
> 상위: [31-stay-ari-migration-overview.md](31-stay-ari-migration-overview.md) · 진입: [32-ops-admin-area.md](32-ops-admin-area.md)

이번 이전에서 **가장 크고 가장 위험한** 부분이다. 저쪽 원본은 단일 파일 **11,672줄**
(`BuildingCalendar.jsx`).

## StayOps 는 지금까지 Beds24 에 써 본 적이 없다

**이 사실이 이 문서의 전제다.** 지금까지 Beds24 연동은 전부 읽기였다 — 예약을 받아오고, 방
목록을 받아오고, 차단을 받아온다. 이번에 처음으로 **쓴다.**

저쪽이 쓰는 엔드포인트는 둘이다.

```
POST /inventory/rooms/calendar   가격 · 최소 숙박일
POST /bookings                   예약 생성 · 수정 · 취소
```

### 저쪽 서버 함수는 7개가 전부다 (2026-09-16 실측)

`BuildingCalendar.jsx` 가 부르는 API 를 전부 세어 보면 이렇다.

| 함수 | 하는 일 | Beds24 |
| --- | --- | --- |
| `getCachedPrices` | 가격·minStay·numAvail·override 읽기 | 읽기 |
| **`setRoomPrices`** | 가격 쓰기 (큐) | `/inventory/rooms/calendar` |
| **`setMinStay`** | 최소 숙박일 쓰기 | `/inventory/rooms/calendar` |
| `createBooking` | 예약 생성 | `/bookings` |
| `updateBooking` | 예약 수정 | `/bookings` |
| `cancelBooking` | 예약 취소 | `/bookings` |
| `getPriceJobStatus` · `triggerPriceJobNow` | 작업 큐 조회·즉시 실행 | — |

> **정정 (2026-09-25).** 이 표는 `BuildingCalendar.jsx` 가 **부르는 함수 이름**만 센 것이라,
> 그 함수 안에서 갈라지는 것을 놓쳤다. 아래가 실제 동작이다.

**블록은 예약이 아니다 — `override: blackout` 이다.**

`createBooking` 은 이름과 달리 `isBlock` 이면 **예약을 만들지 않는다**
(`functions/index.js:7923`):

```js
if (isBlock) {
    restoreNumAvailByDate = await getStoredNumAvailSnapshotForBlock(...);
    await createBeds24BlackoutOverride({ roomId, arrival, departure });   // ← POST /inventory/rooms/calendar
    newBookingId = getInventoryOverrideBlockDocId(roomId, arrival, departure);
} else {
    ... POST /bookings ...
}
```

해제(`cancelBooking:8246`)도 `/bookings` 가 아니라 `override: "none"` 이다. 즉 저쪽은
**`numAvail` 과 `override` 를 둘 다 쓴다.**

#### 저쪽 블록의 실제 규칙

| | |
| --- | --- |
| Beds24 | `POST /inventory/rooms/calendar`, `override: blackout`, `from=체크인` `to=체크아웃−1` (`getInventoryOverrideEndDate`) — **숙박일 기준**이라 우리 읽기 규칙과 같다 |
| 로컬 행 | `inventory-blackout:<roomId>:<arrival>:<departure>` 라는 합성 id 의 **가짜 예약 행**, `status: blackout`, `isInventoryOverrideBlock: true` |
| **numAvail 스냅샷** | 막기 **전에** 저장했다가 해제할 때 복원한다(`preBlockNumAvailByDate`). blackout 을 걸면 Beds24 가 재고를 건드리므로, 그냥 `override: none` 만 돌리면 **막기 전 재고로 안 돌아간다** |
| 보상 롤백 | Beds24 는 성공했는데 로컬 저장이 실패하면 **blackout 을 되돌린다.** 안 그러면 「화면엔 아무것도 없는데 방은 판매 정지」인 고아 블록이 남고, UI 로 손댈 방법이 없다 |
| 일괄 | 같은 날짜 구간의 세그먼트를 묶어 POST 1회 — 듀얼 ID 객실은 모든 roomId 가 같은 구간이라 왕복이 1회로 준다 |

`isAppCreatedBlockEntry` · `isBulkDeletableBlockEntry` 가 있는 이유는 **앱이 만든 블록과 사람이
Beds24 화면에서 직접 건 blackout 을 구분**하기 위해서다. 후자는 복원할 `numAvail` 스냅샷이
없으므로 앱이 함부로 해제하면 재고를 잘못된 값으로 되돌린다.

> **우리가 취할 태도 (2026-09-25 결정).** 저쪽과 **똑같이 blackout override 로** 간다.
> StayOps 는 이미 blackout 을 **읽어서** 표시하고 있으므로([15](15-reservation-calendar.md))
> 읽기·쓰기가 대칭이 되고, 저쪽이 이미 걸어둔 블록도 우리 화면에서 해제할 수 있다.
> 「블록 = 예약」으로 갔으면 우리가 만든 블록이 우리 캘린더에 예약 줄로 보였을 것이다.

**잘못 쓰면 채널에 그대로 나간다.** 가격을 0 으로 쓰면 0 원에 팔리고, 재고를 열면 팔리면 안 되는
방이 팔린다. 우리 DB 가 틀어지는 것과는 급이 다르다.

> 저쪽 코드에도 크레딧 인식 재시도와 가드가 들어 있다(`beds24PostV2WithRetry` ·
> `beds24PostV2WithGuard`). 이미 한 번 데였다는 뜻으로 읽는다 — 우리도 같은 자리를 밟는다.

#### 가격 개입 전환 규칙 (저쪽 `src/utils/priceAttribution.js`, 9/24)

가격을 바꾼 뒤 그 방·그 날짜로 들어온 예약을 「가격 조정이 만든 예약」으로 센다.

- **개입 로그**: `success !== false`, 또는 실패여도 `priceSnapshot` 이 있으면 인정(`bdf0d0a`).
- **예약**: 확정만. 생성 시각은 `bookingCreatedAtMs` → `bookingTime/bookTime/entryTime` → `bookDate` 의
  23:59:59 JST 순으로 찾는다.
- **매칭**: 같은 건물·방 · 숙박이 로그의 dateFrom~dateTo 와 겹침 · `개입 < 예약 ≤ 개입 + 48h`
  (로그에 `attributionWindowHours` 가 있으면 그 값) · 대상 날짜 중 하나 이상이 **개입 당시 비어
  있었다**(그 날짜를 처음 점유한 예약의 생성 시각이 개입보다 늦다).
- 대상 날짜: `priceSnapshot` 의 (방, 날짜) → `dates` 키 × rooms → dateFrom~dateTo.
- 후보가 여럿이면 **가장 최근 개입 하나**.
- 화면: 캘린더 토글(전환된 막대만 진하게, 나머지 0.08 로 흐리게 — 목록에서 빼지는 않는다) + 목록
  (수정 전 가격, ±% — `ee7321d`). 가격 변동은 **로그 평균이 아니라** 그 예약의 방·날짜 스냅샷 행으로.
- 우리 `price_change_logs` 는 이미 **칸 단위**(방·날짜·이전·이후)라 조건을 만족한다. 웹훅으로 들어온
  외부 변경도 이력에 남기는지는 구현 때 확인.

#### 가격 개입 전환 — 구현 (2026-09-29)

| 자리 | 동작 |
| --- | --- |
| 판정 | `attributePriceConversions`(`src/lib/ops-price-attribution.ts`, 테스트 9건) — 위 규칙 그대로 |
| 데이터 | `getOpsCalendarData` 가 **가격을 바꾼 시각 기준 최근 90일**의 `price_change_logs`(`field = price1`)를 작업(`job_id`)으로 묶고, 바꾼 날짜를 덮는 확정 예약(창 밖 포함 — 「그때 비어 있었나」를 재려면 필요)을 격자와 같은 매칭으로 방에 붙인다. 예약 생성 시각은 Beds24 `bookingTime` |
| 격자 | 툴바 「가격 개입 성공 N」 토글 — 켜면 전환된 예약만 진하게(테두리), 나머지 0.12 로 흐리게. 목록에서 빼지는 않는다 |

**저쪽과 다르게 한 것.**

- 저쪽 목록은 **캘린더에 보이는 기간의 숙박만** 담아 나머지는 「Price History」 화면에 따로 있었다.
  여기는 **최근 90일 전체**를 한 목록에 — 창과 무관하다(격자 토글은 보이는 막대에만 걸린다).
- 이전 → 이후 가격을 **칸 단위 이력에서 그 예약의 밤만** 뽑는다. 저쪽은 스냅샷이 없으면 로그 전체
  평균으로 대신했다(「log average」 표시).
- 최소숙박 변경(「1박으로」)은 저쪽처럼 **세지 않는다** — 저쪽 `setMinStay` 는 가격 이력을 남기지
  않는다.

#### Beds24 에서 바꾼 가격도 개입으로 센다 (2026-09-29 사용자 결정)

저쪽은 Beds24 가격 웹훅으로 외부 변경도 로그에 남겼다(`origin: Beds24`). 우리도 남긴다. 웹훅에는
**가격이 없고** 「이 방이 바뀌었다」 신호뿐이라, 요금 동기화(`room-rates-sync.ts`)가 우리 표를 덮기
**직전에 이전 값과 비교**해 바뀐 칸을 `price_change_logs`(`changed_by_name = "Beds24"`,
`adjust_mode = "beds24"`, `job_id` 없음)에 남긴다(`detectExternalPriceChanges`, 테스트 6건).

- **가격 소스 유닛의 `price1` 만** 센다. 자식 유닛·Booking.com·`p3` 는 링크가 따라 바꾸는 값이라 세면
  한 번의 변경이 여러 번 잡힌다.
- 이전 값을 모르는 칸(12개월 창에 새로 들어온 날) · 지난 날짜 · 지워진 가격은 안 센다.
- 우리 앱이 쓴 값은 워커가 우리 표도 바로 고쳐 두므로 동기화 때 같은 값이라 안 잡힌다. 그 사이 몇 초에
  동기화가 끼어 「Beds24」로 한 번 더 남는 경우는 판정에서 거른다(같은 방·날짜·값, 15분 안).
- 한 번의 동기화에서 잡힌 변경은 **같은 시각**으로 남겨 판정이 한 번의 개입으로 묶는다.
- 우리 표를 끝까지 갱신했을 때만 남긴다. 칸 이력 툴팁에도 「Beds24」로 나온다.

## 저쪽 설계 — 읽어낸 내용

> **가져올 기준은 저쪽 설계 그 자체다**(2026-09-16 확정). 캘린더는 매출을 운영하는 곳이라
> 임의로 단순화하지 않는다. 아래는 원본 코드에서 읽어낸 규칙이며, 구현은 이것을 따른다.

### 가격은 큐를 거쳐 비동기로 쓴다 — 이 구조가 핵심이다

**화면에서 Beds24 로 바로 쏘지 않는다.** 원본 `setRoomPrices` 의 주석이 명시한다 —
*"Firestore에 price job 생성 — 즉시 Beds24 호출 없음"*.

```
화면  →  setRoomPrices          작업을 큐에 넣고 즉시 응답 (jobId)
      →  price job (queued)
      →  워커 (1분마다)         큐에서 하나 집어 Beds24 에 순차 전송
      →  Beds24 POST /inventory/rooms/calendar
```

**왜 이렇게 하는가.** 42칸을 바꾸면 여러 객실 × 여러 날짜를 Beds24 에 써야 하는데, Beds24 는
5분 단위 크레딧 제한이 있어 한 번에 다 보낼 수 없다. 동기로 처리하면 사용자가 몇 분을 기다리거나
타임아웃이 난다. **모바일에서는 더 나쁘다 — 화면을 끄면 요청이 끊긴다.**

큐 방식이면 **저장을 누른 순간 응답이 오고, 나머지는 서버가 한다.** 「누워서도 쓴다」는 요구와
직접 맞닿아 있다.

#### 작업 상태

| 상태 | 뜻 |
| --- | --- |
| `queued` | 접수됨. 워커를 기다린다 |
| `processing` | 처리 중. **한 번에 하나만**(락) |
| `completed` | 전부 성공 |
| `partial_failed` | **일부만 성공** — 어느 객실이 실패했는지 남긴다 |
| `failed` | 실패 |

원본이 이미 다루고 있는 것들, **전부 가져온다**:

- **멈춘 작업 회수** — `processing` 인 채로 오래 남은 작업을 `queued` 로 되돌리거나 실패 처리한다.
  워커가 죽으면 작업이 영원히 갇힌다.
- **작업 합치기**(`coalescedIntoJobId`) — 같은 대상에 대한 작업이 쌓이면 하나로 묶는다. 안 하면
  같은 칸을 여러 번 쓴다.
- **락**(`lock_busy`) — 두 작업이 동시에 같은 객실을 쓰면 나중 것이 앞의 것을 덮는다.
- **API 쿨다운**(`beds24_api_cooldown`) — 크레딧이 모자라면 다음 주기로 미룬다.
- **진행 상황 조회** — `progress: { processed, total, results }` + 실패한 roomId 목록.
- **7일 지난 작업 정리.**

#### 낙관적 표시 (`pendingPriceCellMap`)

큐에 들어간 가격은 **아직 Beds24 에 없지만 화면에는 새 값으로 보여준다.** 안 그러면 저장 직후
옛 값이 보여 「안 됐나?」 하고 다시 누른다. 반영이 확인되면 실제 값으로 바뀐다.

### 채널별 가격

Beds24 의 가격 슬롯과 채널 대응 — **2026-09-29 전수 실측**(`/properties?includePriceRules=true`):

| 슬롯 | 채널 | 값 |
| --- | --- | --- |
| `p1` (price1) | **에어비앤비** | 소스 유닛의 **직접값**. 실제로 파는 자식 유닛은 이걸 ×1 로 링크한다 |
| `p2` (price2) | **부킹닷컴** | `p1` × 1.48 등 — **링크** |
| `p3` (price3) | **방마다 다르다** — 홈페이지 ×1(37개) · **오쿠보C 는 Agoda ×1.3** · **사노는 Booking.com ×1.65** | 전부 **링크** |
| `p4` | Agoda ×1.35 · 홈페이지 등 | 링크 |

**편집은 에어비앤비 가격(`p1`)만 쓴다. 나머지는 전부 Beds24 링크가 계산한다.**

> 2026-09-28 까지는 저쪽을 따라 `p3` 에도 같은 값을 썼다(「p3 = 대체가 ×1」 전제). 실측해 보니
> `p3` 는 방마다 다른 채널이고 전부 링크 슬롯이라 Beds24 가 직접값을 **무시**했다(피해 없음 —
> 450096 에 88,000 을 썼는데 직접값이 남지 않았다). 그러나 누가 링크를 끊는 순간 **그 방의
> Agoda·Booking.com 가격이 에어비앤비 가격으로 덮인다**(오쿠보C Agoda 23%, 사노 Booking.com
> 39% 싸짐). 2026-09-29 부터 **`p1` 만** 쓴다.

**채널까지 반영되는 것을 실측으로 확인했다**(2026-09-29, 9/24 에 우리 앱으로 바꾼 오쿠보C 12/11):
소스 450096 `p1` = 88,000(우리가 쓴 값) → 실제 판매 유닛 648399 `p1` 88,000(링크 ×1, Airbnb 채널 켜짐)
· Booking.com 130,240(×1.48, booking 채널 켜짐) · Agoda 114,400(×1.3). 채널 화면(Airbnb 호스트 ·
Booking.com 엑스트라넷)에서의 최종 표시는 API 로 볼 수 없어 사람이 한 번 확인한다.

**부킹닷컴은 Beds24 가 알아서 맞춘다**(2026-09-16 확인). 에어비앤비 가격을 바꾸면 Beds24 쪽
규칙에 따라 부킹닷컴 가격이 **자동으로 따라 조정된다** — 두 플랫폼의 가격대가 조금 다르기
때문이다.

그래서 **우리가 `p2` 를 쓰면 안 된다.** 쓰면 Beds24 의 규칙과 충돌한다. 읽어서 보여주기만 한다.
저쪽이 `p1`·`p3` 만 쓰는 이유가 이것이다.

읽을 때는 `p1` 을 먼저 보고, 없으면 `p3` 로 떨어진다(`preferAirbnbPrice3` 옵션).

### 객실 하나가 roomId 여러 개일 수 있다

같은 「201호」가 Beds24 에서 여러 `roomId` 로 존재한다(유닛 분리). 가격을 쓸 때는 **활성 유닛
전부에 써야** 한다 — 하나만 쓰면 다른 유닛이 옛 가격으로 팔린다.

**활성 판정**: 그 날짜의 `minStay` 가 `1 이상, INACTIVE_MINSTAY_THRESHOLD 미만`이면 활성.
StayOps 에도 같은 개념이 있다(`BEDS24_INACTIVE_MIN_STAY_THRESHOLD = 50`) — **기준을 맞춘다.**

활성 유닛이 하나도 없으면 **전체 유닛에 쓴다**(안전 쪽으로 떨어진다).

> **하드코딩된 예외가 하나 있다**: 아라키초A 501호는 `roomId` 두 개(`502229`, `383975`)를
> 반드시 함께 갱신한다. 프론트와 백엔드 양쪽에 같은 예외가 박혀 있다
> (`shouldMergeArakichoA501PriceRoomIds`). **이런 예외는 코드가 아니라 데이터로 옮긴다** —
> 객실 마스터에 「함께 갱신할 유닛」을 두면 새 건물이 생겨도 코드를 고치지 않는다.

### 조정 방식 두 가지

| 모드 | 입력 | 계산 |
| --- | --- | --- |
| **직접 입력** | 금액 | 선택한 칸 전부를 그 금액으로 |
| **퍼센트** | ±% | 칸마다 `현재가 × (1 + %/100)`, 반올림 |

퍼센트는 **칸마다 현재가가 기준**이라 결과 금액이 칸마다 다르다. 프리셋 버튼:
`-20 · -10 · -5 · +5 · +10 · +20 · +30`.

> **모드 토글은 두지 않는다** (2026-09-16 확정). 저쪽은 `adjustMode` 로 `direct` / `percent` 를
> 갈라 놓았지만, **둘은 같은 값을 정하는 두 가지 방법일 뿐**이라 한 화면에서 같이 쓴다.
>
> ```
> 현재 평균 ¥26,100  →  변경 ¥30,000  (+15%)
> [-20%][-10%][-5%][+5%][+10%][+20%][+30%][± %]
> ```
>
> 금액을 직접 쓰면 **% 배지가 계산되어 바뀌고**, 퍼센트를 누르면 **금액이 계산되어 채워진다.**
> 어느 쪽으로 넣든 결과는 한 곳에 모이므로 모드를 고를 이유가 없다. 퍼센트일 때는 칸마다
> 결과가 다르므로 「변경」을 **범위**로 표시한다(`¥35,600 ~ ¥55,800`).
>
> 서버로 보낼 때는 저쪽과 같이 `adjustMode` 를 그대로 기록한다 — 이력에 「퍼센트로 바꿨다」가
> 남아야 한다. **화면에서만 합치고 데이터는 구분한다.**

### 선택은 「객실 × 날짜」 조합이다

`selectedCells` 는 **room-date 쌍의 목록**이다(cartesian product). 「201호의 9/20」과
「202호의 9/21」처럼 **들쭉날쭉한 선택**이 가능하다. 단순한 사각형 범위가 아니다.

### 이력을 남긴다 (2026-09-24 구현)

이 값들은 **채널로 그대로 나간다.** 가격이 이상하면 제일 먼저 나오는 질문이 「누가 언제
얼마에서 얼마로 바꿨나」다. 작업 큐에는 **결과만** 남고 이전 값이 없어 되돌릴 근거가 없었다.

`price_change_logs` — **(객실, 날짜) 한 칸이 한 행**이다. 저쪽은 한 번의 수정을 문서 하나에
`priceSnapshot` 배열로 담고 화면에서 펼치는데(Firestore 라 그게 쌌다), 우리는 칸 단위라
「이 칸의 이력」이 인덱스 조회 한 번으로 끝난다 — 저쪽이 상한(`PRICE_HISTORY_TOTAL_BUDGET`)을
두고 메모리에서 펼치던 일을 안 해도 된다.

| | |
| --- | --- |
| 쓰는 곳 | 워커. **검증을 통과한 칸만** |
| 이전 값 | POST **전에** `room_daily_rates` 에서 읽어 둔다 — 쓰고 나면 영영 알 수 없다 |
| 안 남기는 것 | 값이 그대로인 칸. 같은 값을 다시 보낸 것까지 남기면 진짜 변경이 묻힌다 |
| 객실 잇기 | `room_label`. 가격은 소스 유닛, 최소숙박은 운영 중인 유닛이라 `room_id` 가 다를 수 있는데 **사람이 보는 행은 하나다** |

검증을 통과한 것만 적는다 — Beds24 가 안 받아들인 값을 「바꿨다」고 적으면 이력이 거짓말을
하고, 그건 **이력이 없는 것보다 나쁘다.** 반대로 이력 기록에 실패해도 작업을 실패로 만들지는
않는다(값은 이미 Beds24 에 들어갔다).

`null` 은 **값이 없었다**는 뜻이고 0 이 아니다 — 화면도 「0에서 올렸다」가 아니라
「¥42,000 로 설정」이라고 적는다.

화면에서는 손댄 칸에 **점 하나**가 붙고, 올리면 「09-24 14:03 · 김현준 · ¥38,453 → ¥42,000
(+9%)」이 뜬다(최대 5줄, 나머지는 「외 N건」). 30px 칸에 더 넣을 자리가 없고 가격 숫자를
가려서도 안 된다.

시각은 **도쿄 기준**이고 자리를 직접 맞춘다 — 로케일에 맡기면 `sv-SE` 는 `24/09`, 다른
로케일은 또 다르게 내놓아 **같은 이력이 사람마다 다른 순서로 읽힌다.**

판정은 순수 모듈 `src/lib/ops-price-history.ts` + 테스트 13건.

실측(2026-09-24): 201호 2027-08-20 을 `2박 → 3박 → 2박` 으로 바꾸니 이력 두 줄이 그대로
이어졌다.

이 화면에서 제일 위험한 것이 **「몇 시간 된 가격인지 모른 채 퍼센트 조정」**이다. 상단에
`객실 67 · 12분 전 동기화` 를 적고, 15분을 넘으면 빨갛게 쓴다(시안에도 같은 자리에 있다).

분 단위로만 센다 — 초까지 적으면 새로고침마다 숫자가 달라져 **값이 바뀐 것처럼** 보인다.
기준은 창 안에서 **가장 오래된** 칸이다: 한 칸이라도 낡았으면 그 화면은 낡은 것이다.

#### 낡았으면 화면을 열 때 당겨 온다 (2026-09-24)

저쪽은 Cloud Scheduler 로 **15분마다 정확히** 돈다(`schedule: "every 15 minutes"`).
우리 주기 동기화는 GitHub Actions 라 같은 15분을 걸어 뒀는데 **실제 간격이 3~5시간**이다.

```
설정  7,22,37,52 * * * *
실제  06:14 → 01:17 → 22:53 → 19:52 → 16:49 → 12:04
```

그 사이 Beds24 화면에서 가격을 바꾸면 우리 화면은 몇 시간째 옛 값이고, **그 값을 기준으로
퍼센트 조정을 하게 된다.**

그래서 창이 15분보다 낡았으면 화면을 열 때 채운다. `after()` 라 **응답을 보낸 뒤에** 도므로
화면 속도는 그대로다 — 이번 화면은 여전히 옛 값이지만 다음 화면은 맞는다.

**보이는 창 + 고른 건물만** 당긴다. 9건물 × 12개월은 30초에 크레딧도 그만큼 쓴다 —
화면을 열 때마다 할 일이 아니다. 쓰기 작업이 대기 중이면 물러나고(방금 쓴 값을 옛 값으로
덮으면 「되돌아갔다」로 보인다), 크레딧 쿨다운도 존중하고, 락으로 동시 열기를 한 번으로 묶는다.

> **진짜 해법은 가격 웹훅 등록이다.** Beds24 v2 API 가 노출하는 웹훅은 속성 수준의
> **예약 한 벌뿐**이라(`/properties?includeWebhooks=true` → `version: twoWithPersonalData`),
> 가격 트리거는 Beds24 웹 화면에서만 걸 수 있다. 등록되면 위 두 가지는 안전망으로 남는다 —
> 저쪽도 `priceWebhook`(즉시)과 `scheduledBeds24PriceSync`(15분)를 함께 돌린다.

### `includeLinkedPrices` 는 필수다 (2026-09-17 회귀)

`includePrices=true` 만 붙이면 **그 유닛에 직접 박아 둔 값만** 온다. Beds24 에서 가격은 연결로
퍼지는데(같은 물리적 방의 다른 유닛, 채널별 파생가) 그 연결분은 파라미터를 따로 켜야 나온다.
저쪽 원본은 처음부터 둘 다 보낸다(`functions/index.js` 2966행).

실측 — 오쿠보C · 2026-10-01:

| | 648399 (그날 판매 중) | 450096 (그날 비활성) |
| --- | --- | --- |
| 없이 | `p1 —` | `p1 79000` `p2 —` `p3 —` |
| 켜고 | **`p1 79000`** | `p1 79000` **`p2 116920`** **`p3 102700`** |

없이 받으면 두 가지가 동시에 빈다.

1. **파생가로 파는 유닛의 가격 전부.** 오쿠보C 는 10/1 에 판매 유닛이 450096 → 648399 로
   바뀐다(450096 의 minStay 가 50 으로, 648399 가 2 로). 우리는 활성 유닛을 정확히 골랐는데
   그 유닛에 가격이 없어서 **10/1 부터 가격 칸이 통째로 비었다.** 최소숙박 `2` 는 그대로
   보였으니 「안 파는 날」과 구별도 안 됐다.
2. **모든 방의 `price2`(부킹닷컴) · `price3`(대체가).** 33,306행 전부 0건이었다.
   화면은 에어비앤비 가격(`p1`)만 쓰고 있어 티가 나지 않았다.

같이 고친 것 — **응답 쪽 넘기기**(`pages.nextPageExists` / `nextPageLink`). 저쪽은 이 처리가
가격 조회에만 빠져 있었고 「잘린 뒤쪽은 조용히 사라져 영구 미동기화」가 됐다고 주석에 남겼다.
우리는 건물 단위로 나눠 불러 아직 한 쪽에 들어오지만, 객실이 늘면 같은 자리에서 끊긴다.
쪽 상한(20)에 닿으면 `skipped` 에 남긴다.

### ② 웹훅 — 가격이 바뀌면 그때

**저쪽은 가격 변경을 전부 웹훅으로 받는다**(`exports.priceWebhook`). 백필만으로는 Beds24 화면에서
가격을 바꾼 순간부터 우리 표가 틀린 값을 들고 있게 되고, 판매 캘린더가 **없는 가격을 보여주는
화면**이 된다.

배달은 **예약 웹훅과 같은 엔드포인트**로 오고 예약이 들어 있지 않다.

```
V1(GET)  ?roomId=440617&action=PRICE_CHANGE&propId=176430
V2(POST) {"roomId":440617,"action":"PRICE_CHANGE","propId":176430}
```

`src/lib/beds24/price-webhook.ts` 가 처리한다.

| | |
| --- | --- |
| 판정 | `roomId` 가 있고 `action` 이 `PRICE_CHANGE`·`SYNC_ROOM`·**없음** — 저쪽과 같은 집합 |
| 모르는 방 | **Beds24 를 부르지 않고 끝낸다.** 남의 계정 웹훅으로 크레딧을 쓰지 않는다 |
| 범위 | 그 **건물** 전체를 다시 가져온다 — `/inventory/rooms/calendar` 가 건물 단위로 응답하므로 어차피 다 온다 |
| 디바운스 | **건물별 20초 + 창이 끝나면 한 번 더 읽기** (2026-09-29). 일괄 변경이면 웹훅이 객실 수만큼 쏟아진다 |
| 함께 갱신 | 요금 12개월(`room_daily_rates`) **+ 그 건물의 차단 막대**(`room_blocks`, 현장 예약 캘린더) — `refreshProperty` |

**디바운스는 건물별이어야 한다.** 조직 전체로 재면 아라키초A 를 방금 동기화한 탓에 가부키초
웹훅이 통째로 버려진다 — 여러 건물의 가격을 함께 바꾸면 실제로 그렇게 된다.

> **되받아치기 (2026-09-25 갱신).** 우리가 Beds24 에 가격을 쓰면 Beds24 가 그 변경을 웹훅으로
> 되돌려 보낸다. 쓰기 기능이 살아 있으므로 이건 실제로 일어나는 일이다. **디바운스가 그 역할을
> 겸한다** — 가격 작업 워커는 쓴 뒤 `room_daily_rates` 를 직접 갱신하므로 그 건물의 `synced_at`
> 이 방금 값이 되고, 뒤따라 오는 되받이는 60초 안에 들어와 버려진다. 디바운스보다 늦게 오는
> 되받이는 통과하지만 그때는 같은 값을 다시 읽는 것이라 해롭지 않다. 「우리가 만든 변경인가」
> 판정이 필요해지는 건 디바운스를 줄일 때다.

#### 모든 가격·재고를 웹훅 기준으로 (2026-09-29)

재고 웹훅이 이쪽으로 전환된 뒤(아래 「전환 완료」) 가격·재고·차단이 **변경 몇 초 뒤** 반영되도록
세 가지를 고쳤다.

1. **디바운스가 변경을 버리지 않는다.** 전에는 60초 창 안에 온 배달을 그냥 버렸다 — 첫 배달로
   동기화한 직후 Beds24 에서 또 바꾸면 그 변경은 다음 주기 동기화(실측 약 6시간)까지 안 보였다.
   이제 창 안의 배달은 **건물당 하나만** 「창이 끝나면 한 번 더 읽기」를 예약한다(DB 잠금
   `price-webhook-trailing:<건물>`, 55초). 라우트는 Beds24 에 바로 200 을 주고 그 읽기를
   `after()` 로 돌린다(`maxDuration = 60`). 잠금은 **읽기 전에** 푼다 — 읽는 도중 들어온 배달이
   또 한 번을 예약할 수 있어야 마지막 변경이 빠지지 않는다.
2. **현장 예약 캘린더의 차단 막대도 같이 갱신한다.** 요금 동기화는 판매 캘린더만 고쳤고
   `room_blocks` 는 주기 동기화 때만 바뀌었다. 이제 웹훅이 그 건물의 차단도 다시 읽는다
   (`syncBeds24RoomBlocks({ externalPropertyIds })` — 지우기도 **그 건물 이름으로만** 한정한다.
   다른 건물 행을 지우면 다음 주기까지 그 건물 차단이 사라진다).
3. **최소 숙박일도 웹훅이 온다 — 실측.** 공식 문서는 재고 웹훅이 가격·가용성 변경에만 온다고 읽혔지만,
   2026-09-29 사용자가 Beds24 화면에서 최소숙박일만 바꾸자 그 건물(176430) 배달이 02:48:01 UTC 에 와서
   12개월(8,052행)을 다시 읽었다. 웹훅은 건물 12개월을 통째로 다시 읽으므로 가격·재고·차단·최소/최대
   숙박이 한 번에 맞춰진다. 주기 동기화는 놓친 배달을 메우는 안전망으로만 둔다.
4. **같은 초의 중복 배달을 한 번만 읽는다.** Beds24 는 한 번의 변경에 배달을 여러 건 같은 초에 보낸다
   (실측: 343112 에 5건, 176430 에 2건). 전에는 전부 `synced_at` 이 오래됐다고 보고 각자 12개월을 다시
   읽었다(크레딧 낭비). 이제 건물당 「지금 읽기」 잠금(`price-webhook-run:<건물>`)을 하나만 잡고 —
   잡은 뒤 150ms 뒤 다시 확인해 같은 순간의 경합도 거른다 — 나머지는 「창이 끝나면 한 번 더」로
   돌린다(읽는 도중 들어온 변경을 놓치지 않게).

예약은 원래부터 예약 웹훅으로 실시간이다.

> **되받아치기와 20초.** 우리 쓰기 뒤 되받이도 이제 「한 번 더 읽기」를 만들 수 있다. 같은 값을
> 다시 읽는 것이라 해롭지 않고, 가격 이력은 값이 바뀐 칸만 남기므로(`detectExternalPriceChanges`)
> 우리 변경이 Beds24 변경으로 두 번 잡히지 않는다. 비용은 건물당 Beds24 호출 한 번이다.

#### 화면도 웹훅 기준으로 (2026-09-29, 사용자 결정: 「모바일이건 대시보드이건 Beds24 관련은 전부」)

데이터가 몇 초 안에 들어와도 화면이 새로고침을 기다리면 실시간이 아니다. 전에는 모바일 예약
캘린더의 **예약**만 자동으로 바뀌었다(`reservations` postgres 변경 알림). 차단·요금은 어느 화면에서도
새로고침해야 보였고, 어드민 예약 캘린더와 판매 캘린더는 구독 자체가 없었다.

**신호 하나 방식.** Beds24 데이터를 우리 표에 쓴 서버 코드가 끝에 조직 채널
`beds24-live:<organizationId>` 로 Realtime broadcast `changed` 를 **한 번** 보낸다(`{ kind, at }` —
데이터 없음). 화면은 받으면 0.6초 모아 `router.refresh()` 한다 — 평소와 같은 서버 권한·조직 검사로
다시 읽는다. 탭이 가려져 있으면 다시 보일 때 한 번.

| 보내는 곳 (`signalBeds24Change`, `src/lib/beds24/live-signal.ts`) | kind |
| --- | --- |
| 예약 웹훅·수동 예약·예약 수정 (`processBeds24WebhookBooking` 성공) | reservations |
| 예약 정합성 크론 (`backfillBeds24Reservations`, 바뀐 행이 있을 때) | reservations |
| 판매 캘린더 예약 취소 | reservations |
| 요금 동기화 (`syncBeds24RoomRates` — 재고 웹훅·크론, 쓴 행이 있을 때) | rates |
| 가격·최소숙박 작업 워커 완료(하나라도 성공) — **다른 사람** 화면용 | rates |
| 차단 동기화 (`syncBeds24RoomBlocks`) · 차단 걸기/풀기 (`block-write.ts`) | blocks |

| 듣는 화면 | 방식 |
| --- | --- |
| `/admin` 대시보드 · `/admin/calendar` · `/admin/ops/calendar` · `/admin/cleaning` · `/mobile` 홈 · `/mobile/cleaning` | `<Beds24LiveRefresh>` (`src/components/shared/beds24-live-refresh.tsx`) |
| `/mobile/calendar` | 기존 예약 구독과 **같은** 디바운스에 신호 채널을 붙였다 — 예약 변경에 두 번 읽지 않는다 |

- **표마다 postgres 변경 알림을 켜지 않는다.** 재고 웹훅 한 번에 요금 12개월(건물당 ~9,500행)을 다시
  써서 알림이 행 수만큼 쏟아진다. DB 설정(publication)도 바꾸지 않는다.
- **공개 채널이다.** 채널 이름에 조직 UUID 가 들어가고 내용은 「바뀌었다」뿐이라, 알아도 얻는 데이터가
  없다. 실제 값은 서버가 권한을 확인하고 읽는다.
- **신호는 절대 실패를 만들지 않는다.** 보내기 실패는 경고 로그만 남기고, 화면은 다음 이동 때 맞는다.
  서비스 클라이언트는 호출할 때 불러온다(동기화 모듈을 테스트가 직접 import 하므로).
- `router.refresh()` 는 서버 컴포넌트만 다시 받는다 — 열린 패널·입력·선택 같은 클라이언트 상태는 남는다.
- 실측(2026-09-29): 익명 키로 구독한 클라이언트가 서비스 키 `httpSend` 신호를 받는 것을 확인했다.

**2026-09-17 실측 — 가격 웹훅은 우리에게 오지 않고 있다.** (→ 2026-09-29 전환 완료, 07 문서 참고)

| | |
| --- | --- |
| 2026-07-22 ~ 09-16 배달 | **20,157건, 전부 예약** |
| 가격 배달 | **0건** |

Beds24 설정 화면의 그 칸은 **「予約Webhook」**(예약 웹훅)이고, 거기 우리 URL 을 포함해 3개가
등록돼 있다. 저쪽의 첫 번째 URL 이름도 `beds24**booking**webhook` 이다 — 저쪽 `priceWebhook` 은
**별개 함수라 URL 이 다르고 그 칸에 없다.** 즉 가격 트리거는 다른 곳에 등록돼 있다.

**토큰 권한 문제가 아니다.** 웹훅은 Beds24 → 우리 방향이라 우리 API 토큰과 무관하다
(그 토큰으로 요금 33,306행을 방금 가져왔다).

#### 가격 웹훅이 어디 있는지 찾았다 (2026-09-25)

`設定 → Marketplace → API → **Webhooks**` 의 **`Inventory Webhooks`** 화면이다. API 로는 안
보인다 — `/properties/webhooks` 는 500, `/settings/webhooks` 는 404 를 준다. 이 화면만이
가격·재고 트리거의 설정 지점이다.

**예약 웹훅과 결정적으로 다른 점: URL 칸이 프로퍼티당 한 줄만 받는다.**

예약 웹훅 칸은 `\r\n` 으로 여러 개를 받는다 — 실제로 9개 건물 전부에 3개가 들어 있다
(저쪽 Firebase · 우리 · 또 다른 수신처). 재고 웹훅 칸은 그게 안 된다. 그래서 **가격 알림은
주인이 하나**고, 지금 그 자리는 저쪽 `priceWebhook` 이 갖고 있다.

##### 우리가 주인이 되고, 저쪽으로 넘겨준다

없어질 쪽이 주인을 쥐고 있으면 **저쪽을 내리는 날 가격 웹훅이 같이 죽고**, 그 시점에 Beds24
설정을 9개 건물 다시 만져야 한다. 반대로 하면 정리가 환경변수 하나로 끝난다.

```
지금 (변수 없음)     Beds24 ──▶ 저쪽              우리는 관여하지 않는다
전환일 (변수 설정)   Beds24 ──▶ 우리 ──▶ 저쪽      저쪽은 지금과 동일하게 동작한다
정리 후 (변수 삭제)  Beds24 ──▶ 우리
```

| | |
| --- | --- |
| 구현 | `src/lib/beds24/webhook-forward.ts` · `BEDS24_PRICE_WEBHOOK_FORWARD_URL` (미설정 = 꺼짐) |
| 시점 | `after()` — 응답을 보낸 **뒤에** 넘긴다. 저쪽이 느려도 Beds24 에게는 이미 2xx 를 준 뒤라 재배달이 안 생긴다 |
| 시크릿 | 전달 URL 에서 `secret` 질의 파라미터를 **뺀다**. 저쪽은 요구하지 않고, 남의 주소로 나갈 이유도 없다 |
| 실패 | 던지지 않는다. 전달이 빠져도 양쪽 모두 15분 주기 동기화가 따로 돈다 |

##### `GET` 핸들러가 없으면 조용히 전부 잃는다

재고 웹훅은 `GET` + 질의 파라미터로도 온다(저쪽 원본: `const data = method === "GET" ?
req.query : req.body`). 우리 라우트는 `POST` 밖에 없었다 — 그대로 주인을 받았으면 GET 배달이
**405 로 떨어지고, Beds24 는 실패를 화면에 알려주지 않는다.** 가격 알림이 통째로 사라진 것을
아무도 모른 채 요금이 주기 동기화로만 갱신된다(즉시 → 15분). 2026-09-25 에 `GET` 핸들러를
추가했다. 판정 로직은 기존 `extractPriceWebhookSignal` 을 그대로 쓴다.

`GET` 으로는 예약이 오지 않으므로 가격 배달만 처리하고, 나머지는 원문을 `beds24_webhook_events`
에 남긴 뒤 2xx 로 받아준다 — `POST` 쪽과 같은 원칙(재배달 폭주 방지)이다.

> **전환일 절차**는 `docs/engineering/07-environment-setup.md` → 「Beds24 재고(가격) 웹훅 전환」.

### ③ 주기 동기화 — 웹훅에 기대지 않는다

**저쪽도 둘 다 돌린다.** 아키텍처 문서 기준:

```
priceWebhook                onRequest      가격/재고 변경 수신
scheduledBeds24PriceSync    every 15 min   전체 가격 캐시 동기화   ← 이것도 있다
```

우리도 같은 두 번째 축을 둔다.

| | |
| --- | --- |
| 라우트 | `/api/beds24/rates-sync` (`CRON_SECRET` 또는 Beds24 웹훅 시크릿) |
| 트리거 | `.github/workflows/beds24-rates-sync.yml` — 매시 `:07 :22 :37 :52` |
| 멱등 | `(room_id, stay_date)` upsert. 겹쳐 돌아도 행이 안 늘고, 지우지 않아 과거는 이력으로 남는다 |

> **GitHub Actions 는 정시에 안 온다.** 이 저장소에서 `*/5` 가 실제로 40분~3시간 40분 뒤에 돈
> 적이 있다. 15분으로 적어 두되 그보다 늦는 것을 전제한다 — 멱등이라 늦거나 겹쳐도 해가 없다.
> **즉시 반영은 웹훅이 한다**(2026-09-29 전환 완료). 주기 동기화는 놓친 배달과 minStay 를 메우는 안전망이다.

**건물 하나가 실패해도 나머지는 갱신된다.** 각 건물 요청을 따로 감싸 `skipped` 에 남기고 넘어간다
— 2026-09-17 에 일시적 `fetch failed` 하나가 전체 실행을 500 으로 죽이는 것을 실제로 겪었다.

### 최소 숙박일 모드 (2026-09-25 구현)

시안: Claude Design 「StayOps 운영 관리자 영역」 `6-minstay.dc.html`

편집 모드를 **둘로 갈랐다** — `가격` 과 `최소 숙박일`. 같은 격자·같은 축·같은 선택 규칙을
쓰고 **패널 안쪽만 다르다**. 껍데기까지 달라지면 두 화면을 따로 익혀야 한다.

왜 한 패널에 안 넣었나: 묻는 것이 다르다. 가격은 「얼마로?」이고 칸마다 다른 값을 계산하지만,
최소 숙박일은 「몇 박으로?」 하나를 고른 칸 전부에 넣는다. 한 패널에 두면 **어느 쪽을 고치는
중인지 모르는 채로 적용**하게 되는데, 가격은 틀리면 채널로 그대로 나간다.

| 화면 요소 | 하는 일 |
| --- | --- |
| 모드 배지 | 지금 무슨 모드인지. 버튼이 아니라 **상태 표시**라 누를 수 없게 생겼다 |
| **「1박 갭 자동 선택 (N)」** | 화면 안의 갭을 한 번에 고른다. **과거 날짜는 뺀다** — 표시는 하지만(「어제 이 밤을 버렸다」는 정보다) 고쳐도 팔 수 없다 |
| 갭 개수 상자 | 숫자를 크게 적는다. 갭은 눈에 안 띄는 손실이라 작게 적으면 손이 안 간다 |
| 1박 / 2박 / 직접 입력 | 1박이 기본. 나머지는 되돌리거나 다른 값으로 바꿀 때 |
| 갭 목록 | `아라키초A  502  11/24 화` — **건물 · 방 · 날짜(요일)**만 적는다. 격자와 같은 순서 |
| 감지 기준 | 규칙 세 줄을 화면에 적어 둔다 |

**건물을 적고 채널은 뺀다 (2026-09-28 개정).** 처음에는 앞뒤 예약의 채널 칩을
(`Booking ▸ 1박 ▸ Airbnb`) 달았다. 그런데 **최소 숙박일을 정하는 데 채널은 필요 없고**,
「Airbnb ▸ 1박 ▸ Airbnb」가 플랫폼이 두 번 찍힌 것처럼 읽혔다. 반대로 방 번호만으로는 **어느
건물인지** 몰랐다 — 여러 건물의 갭을 한 번에 고르기 때문이다(사용자 지적). 패널 머리글도
「아라키초A 502 / 오쿠보B 107」처럼 건물별로 묶어 적는다.

앞뒤 판정(`ops-gap-context.ts` — 앞은 `checkOut === D`, 뒤는 `checkIn === D + 1`)은 계산에 그대로
남아 있다(테스트 포함). 화면에 다시 쓸 일이 생기면 그걸 쓴다.

**감지 기준을 화면에 적어 두는 이유.** 「왜 이건 갭이 아니지?」가 반드시 나온다. 규칙을 숨기면
그때마다 코드를 열어야 한다.

**자동 선택은 축을 비운다.** 축(객실·주·요일)으로 고른 것이 아니므로 축 선택에 넣으면 안 된다 —
축을 다시 누를 때 「축이 기여한 칸만 걷는」 규칙에 걸려 갭이 같이 걷힌다.

## 쓰기 대상 유닛 — 실측으로 확정 (2026-09-25)

> **요구사항(사용자):** 「어느 건물이건 어느 객실이건 활성 객실을 찾아내서, 가격 수정이나
> 최소숙박일수 설정이 **제대로 반영**되어야 한다.」

한 캘린더 행 뒤에 Beds24 방 계정이 여럿일 수 있다. 쓰기 대상은 **둘로 갈리고, 서로 다른 축**이다.

| 쓰는 것 | 대상 | 왜 |
| --- | --- | --- |
| 가격 `p1`·`p3` | **가격 소스 유닛 하나** | 자식 유닛은 자기 가격이 없다 |
| 가격 `p2` | **안 쓴다** | Beds24 규칙이 `p1 × 1.48` 로 계산한다 |
| 최소숙박 · 재고 | **그 날짜의 활성 유닛 전부** | 화면이 활성들의 최솟값을 보여준다 |

### 가격 링크의 실제 모양

`GET /properties?includePriceRules=true` 실측 (아라키초A 201·501호):

```
소스 방 383975                      자식 방 502229
  price1 = 자기 값                    rule1 = 383975 의 price1 × 1   ← 자기 값이 없다
  Booking.com = 자기 p1 × 1.48
  Agoda       = 자기 p1 × 1.35
  Homepage    = 자기 p1 × 1
```

자식에 직접 쓰면 **링크가 있는 자리에 직접값이 끼어들어** 다음에 소스가 바뀔 때 어느 쪽이
이기는지 예측할 수 없다. Beds24 는 그래도 `success` 를 준다.

`p2`(부킹닷컴)를 우리가 쓰지 않는 이유도 같다 — 규칙이 계산하는 값이라 직접 쓰면 규칙과 싸운다.
`p3`(홈페이지)는 `× 1` 이라 `p1` 과 같은 값을 쓰는 것이 맞다.

**가격 소스와 활성 유닛은 서로 다른 축이다.** 같은 건물에서도 방향이 반대다:

```
아라키초A 501호   소스 383975 (활성)    자식 502229 (잠김)   ← 소스 = 활성
아라키초A 201호   소스 383971 (잠김)    자식 601545 (활성)   ← 소스 = 잠김
```

### 최소숙박은 왜 「활성 전부」인가

저쪽은 활성 유닛 **하나**를 골라 거기에만 쓰고, 헷갈리는 방 둘을 코드에 박아 뒀다
(`PREFERRED_DUAL_ROOM_IDS` — 가부키초 803호 · 아라키초A 501호). 그게 필요했던 이유는
**활성이 둘인 날짜가 실제로 있기 때문**이다. 실측 (2026-09-25 ~ 2027-03-31, 188일):

```
아라키초A·가부키초 듀얼 21개 방   10/01~10/04  4일   ← 유닛 교체 구간
다카다노바바 401호                188일 전부
오쿠보C                          0일
```

교체 구간은 이런 모양이다 (아라키초A 201호):

```
09/29~09/30   383971 m=2 (판매)   601545 m=99 (잠금)
10/01~10/04   383971 m=2 (판매)   601545 m=2  (판매)   ← 둘 다 활성
10/05~        383971 m=50(잠금)   601545 m=2  (판매)
```

**하나만 쓰면 화면의 숫자가 안 바뀐다.** 표시는 활성 유닛들의 **가장 짧은** minStay 이므로
(`ops-rate-merge.ts`, 저쪽 `getMinStayFromUnitInfos` 도 동일), 다른 활성 유닛이 더 짧은 값을
들고 있으면 한쪽만 고쳐도 표시가 그대로다 — 「저장했는데 그대로인데?」가 된다. 저쪽이
가부키초 803호에서 겪은 것이 이것이고, **하드코딩은 그 증상을 방마다 때운 것**이다.

그래서 **활성 전부에 쓴다**(`resolveMinStayWriteRoomIds`). 어느 것이 「진짜」인지 고를 필요가
없어지고, 방이 늘거나 유닛이 교체돼도 표를 고칠 일이 없다. 다카다노바바 401호처럼 저쪽이
못 다루는 경우도 자동으로 맞는다.

`rooms.preferred_min_stay_room_id` 는 **탈출구**다. 보통 비어 있고, 특정 유닛에만 써야 하는
예외가 생기면 채운다 — 그 유닛이 **활성일 때만** 적용된다.

### 잠긴 유닛은 절대 건드리지 않는다

Beds24 에 「비활성」 스위치가 따로 없고 **`minStay ≥ 50` 이 곧 잠금**이다. 거기에 `1` 을 쓰면
잠금이 풀려 **일부러 접어둔 listing 이 조용히 다시 열린다.** 접어둔 유닛은 나중에 다시 쓸 수
있게 남겨 둔 상태다(사용자 확인 2026-09-25).

> **더블부킹은 이 규칙의 이유가 아니다.** 실측 결과 의존 설정이 있는 유닛 47개 중 46개가
> **서로 의존**(`qty 1` · `sumAllBookings` · `includeBookings` 상호 지정)이라 Beds24 가 이미
> 막는다. 예외는 가부키초 302호(`452062` 의 `includeBookings` 가 비어 있음) 하나인데,
> 둘이 동시에 팔 수 있는 날이 0일이라 지금 노출은 없다. **설정 흠으로 기록해 둔다.**

### 알려진 데이터 흠 — 다카다노바바 방 이름

Beds24 의 roomType 이름이 `2 · 3 · 4 · 5 · 6 · 7 · 8 · 9` 로 들어가 있다(`201호`가 아니다).
저쪽은 이름을 안 보고 roomId 로 하드코딩해 이 문제를 안 겪었다. 우리는 이름을 그대로 가져오므로
**캘린더에도 `4` 로 보이고, `401_2`(556719)가 본 유닛 `4`(513700)와 한 행으로 안 합쳐진다.**
2026-09-25 에 「어느 쪽이 진짜인가」를 두고 실제로 혼선이 있었다.

**결정 (2026-09-25): 지금 그대로 둔다.** 개명도, 정규화 규칙 추가도 하지 않는다.

`401_2` 가 별도 행으로 남아도 괜찮은 이유는 그 계정이 **예전에 테스트로 만든 뒤 안 쓰는
것**이기 때문이다(사용자 확인). 행이 나뉘어 있으므로 다카다노바바에서는 **한 행에 활성
유닛이 둘인 상황도 생기지 않는다.**

> **읽는 사람에게.** 이름만 보면 `401_2` 가 진짜 401호처럼 보이고 `4` 는 쓰레기처럼 보인다.
> **반대다** — `4`(513700)가 예약 100건을 들고 도는 본 유닛이고, `401_2`(556719)는
> 마지막 예약이 2026-06-09 다. 2026-09-25 에 이 이름 때문에 실제로 혼선이 있었다.

다시 쓰기로 하면 그때 **A.** Beds24 에서 `201·301…901` 로 개명(원천이 고쳐짐) 또는
**B.** 우리 정규화에 `N` → `N01` 추가 중 하나를 정하면 된다.

## 차단(블록) — 구현 (2026-09-28)

쓰기 계층은 2026-09-25 에 만들어 뒀고(`block-write.ts`), 이번에 **화면과 서버 액션을 붙여
실제로 쓸 수 있게** 했다. 규칙 자체는 위 「저쪽 블록의 실제 규칙」 그대로다.

### 차단은 **12개월 전부** 보인다 (2026-09-29)

예전 BLOCK 막대는 `room_blocks` 만 봤는데, 그건 현장 예약 캘린더용 동기화(`room-blocks-sync.ts`)라
**이번 달 + 2개월**만 채운다. 판매 캘린더는 12개월을 보므로 그 너머의 Beds24 차단(예: 아라키초B
2027-05-01~06-11)이 **빈 칸처럼** 보였고, 거기에 `+` 가 떴으며 「차단 해제」도 안 나왔다.

이제 격자가 이미 읽는 12개월 요금 칸의 `override_kind`(운영 중 유닛 기준 — `ops-rate-merge`)로
구간을 묶는다(`buildBlockRanges`, `src/lib/ops-block-ranges.ts`, 테스트 4건). 판정 규칙:

- **요금 칸이 있으면 그게 정답이다.** 차단을 걸고 풀 때 요금 칸의 `override_kind` 를 바로 고쳐 두므로
  (`block-write.ts` `patchLocalOverride` — 되읽기로 검증된 뒤, **있는 행만**) 가장 최신이다.
- 요금 칸이 없는 날만 `room_blocks` 로 채운다. 합집합으로 하면 구간의 일부만 풀었을 때
  `room_blocks` 의 원래 행이 남아 **푼 날도 막힌 채** 보인다.
- **끝이 열린 「판매 전」 차단도 숨기지 않는다**(사용자 결정 — 전부 보이게). 현장 예약 캘린더는 여전히
  숨긴다(`room-blocks-sync` 의 규칙 그대로).

수동 예약 · 예약 수정의 겹침 검사(`readOpsRoomUnavailableNights`)도 같은 기준으로 요금 표의 blackout 을
「찬 밤」으로 센다 — 예전에는 `room_blocks`(3개월)만 봐서 그 너머 차단 위에 예약을 만들 수 있었다.

### 구간 단위로 쓴다 — 끊기면 나눈다

Beds24 는 `{from, to, override}` 를 받으므로 칸 하나씩 보내면 왕복이 칸 수만큼 늘고,
크레딧은 계정 단위 5분 예산이라 그만큼 다른 동기화를 밀어낸다. 그래서 고른 칸을 **방별
연속 구간**으로 묶는다(`groupSelectionIntoRanges`).

**끊긴 구간을 하나로 묶으면 안 된다.** 10/1 · 10/2 · 10/5 를 골랐는데 `10/1~10/5` 로 보내면
**고르지도 않은 10/3 · 10/4 가 같이 막힌다** — 팔리고 있던 밤이 조용히 판매 정지된다.
눈으로는 못 잡으므로 회귀 테스트로 고정했다(`ops-calendar-selection.test.ts`).

패널이 「9칸」이 아니라 **「2구간 · 9박」**으로 보여주는 이유도 이것이다. 구간 수를 감추면
위 사람이 「10/1~10/5 를 막았다」고 오해한다.

### 「선택 해제」와 「차단 해제」를 가른다 (2026-09-28)

예전 차단 패널 하단의 「해제」는 **Beds24 차단 해제**였다. 선택을 비우는 버튼으로 읽혀, 누르면
「Beds24 에 보내는 중」이 떴다(사용자 지적). 그때 고른 날(아라키초A 401 · 10/18~10/24)은
원래 막혀 있지 않아 `override: none` 을 다시 쓴 것뿐이라 **바뀐 것은 없었다**(두 유닛 모두
`none` 확인). 크레딧만 썼다.

| 버튼 | 자리 | 하는 일 |
| --- | --- | --- |
| **선택 해제** | 하단 왼쪽 | 화면의 선택만 비운다. 아무 데도 안 보낸다(Esc 와 같다) |
| **차단** | 하단 오른쪽 | 고른 칸을 막는다 — **한 번 더 묻는다**(막는 순간 채널에서 내려간다) |
| **차단 해제** | 본문 | 고른 칸 중 **실제로 막혀 있는 밤이 있을 때만** 나타난다. **그 밤들만** 풀고, 확인 없이 바로 한다(푸는 것은 다시 파는 쪽이다) |

막혀 있지 않은 날에 헛쓰기를 하지 않도록 「차단 해제」는 격자의 블록 목록(`blockedCellKeys`)과
겹치는 칸만 보낸다.

목록의 방 이름이 `아라키초A::401` 처럼 **행 키 그대로** 보이던 것도 고쳤다(`__` 로 잘랐는데 실제
구분자는 `::`) → `아라키초A 401`. 바닥에 따로 있던 작은 「선택 해제」 링크는 하단 버튼으로 옮겼다.

### 최소숙박과 달리 **모든 유닛에 건다**

최소숙박은 그 날짜의 활성 유닛만 고른다. 블록은 아니다 — 막는 것은 「그 물리적 방을 팔지
않는다」는 뜻이고, 한 유닛만 막으면 **나머지 listing 으로 그 방이 팔린다.** 잠긴 유닛에
`override: blackout` 을 걸어도 잠금(`minStay`)은 그대로라 부작용이 없다.

### 큐에 넣지 않는다

가격은 수천 칸을 한 번에 바꾸므로 큐·배치가 필요하다. 블록은 방 몇 개 × 밤 며칠이고,
무엇보다 **사람이 화면 앞에서 결과를 기다린다** — 「막혔나 안 막혔나」를 모른 채 넘어가면
그 자리에서 초과예약이 난다. 저쪽도 동기로 한다.

첫 구간이 실패하면 **거기서 멈춘다.** 이어서 더 쓰면 「어디까지 됐는지」를 사람이 알 수 없다.
이미 성공한 구간은 되읽기로 검증된 상태라 그대로 두어도 안전하다.

### 라이브 검증 (2026-09-28 실측)

되읽기 검증이 코드 안에 있지만 **그 코드가 맞는지는 한 번은 진짜로 써 봐야 안다** —
Beds24 는 아무것도 안 들어가도 `success: true` 를 준다. 사노 `481152` · 2027-08-10~12
(예약 0건)로 확인했다.

② create    ok · 3박
③ 건 뒤     override=blackout                        ← 실제로 들어감
④ 스냅샷    numAvail {08-10:0, 08-11:0, 08-12:0}     ← 저장됨
⑤ clear     ok · 3박
⑥ 푼 뒤     override=none                            ← 원상복구

(**실제 Beds24 에 쓴다.** 대상 날짜를 바꿀 때는 예약을 먼저 확인할 것.)

### 실패 문구를 사유별로 나눈 이유

`save_failed_not_rolled_back` 만 문구가 다르다 — **Beds24 에는 걸렸는데 되돌리지도 못한**
경우라, 사람이 Beds24 화면에서 직접 풀어야 한다. 다른 실패와 같은 문구로 묶으면 그냥
재시도하고 넘어가는데, 그러면 **화면엔 아무것도 없는데 방은 판매 정지**인 고아 블록이 남는다.

## 취소된 예약 보기 (2026-09-28 구현 · 저쪽 규칙 그대로)

> **사용자 지시:** 「취소 기준이라던가 그런 거 전부 저쪽 프로젝트에서 그대로 가져오도록
> 해」 → `BuildingCalendar.jsx` 를 줄 단위로 읽어 아래에 옮겼다.

### 「추가로 보기」가 아니라 **「취소만 보기」**다

여기서 제일 헷갈리는 부분이다. 저쪽 판정은 한 줄이다:

```js
// 렌더용 맵: OFF→일반만, ON(Cancelled Only)→캔슬만
if (isCancelled === showCancelled) { ... }
```

**켜면 일반 예약이 사라지고 취소된 것만 남는다.** 토글 라벨도 켜지면
`Show Cancelled` → **`Cancelled Only`** 로 바뀐다. 우리도 같게 맞췄다 — 켠 뒤 라벨이
「취소만 보는 중」으로 바뀌지 않으면 일반 예약이 왜 사라졌는지 알 수 없다.

**왜 합쳐 보여주지 않는가:** 취소된 자리는 대개 **다시 팔린다.** 취소 막대와 그 자리를
메운 막대가 같은 밤에 겹쳐 서로를 덮는다.

### 「취소만 보기」에서는 수기 예약 `+` 를 숨긴다

빈 칸의 `+` 는 수기 예약을 만드는 입구다. 그런데 이 모드에서는 **일반 예약 막대가 안 보여서
팔린 밤도 빈칸처럼 보인다.** 거기에 `+` 가 뜨면 **이미 찬 방에 예약을 넣으려 하게 된다.**
지난 일을 보는 화면이지 예약을 만드는 화면이 아니다.

### 계산에는 **항상** 취소를 뺀다

토글과 무관하다. 저쪽도 맵을 둘로 나눠 둔다 — 계산용(항상 취소 제외)과 렌더용
(`isCancelled === showCancelled`). 그래서 「취소만 보기」를 켜도 **갭 판정 · 팔린 밤 빗금 ·
선택 차단은 그대로** 동작한다. 취소된 예약은 없는 예약이고, 그 밤은 여전히 팔 수 있다.

### 겹치면 층을 나눈다

취소 막대는 같은 밤에 여러 건이 겹친다. 한 손님이 취소하고 다른 손님이 잡았다가 또
취소하면 그 밤에 취소 막대가 셋이다. 한 줄에 그리면 서로 덮어 **아무것도 못 읽는다.**

2026-09-28 실측(최근 90일):

| | |
| --- | --- |
| 취소가 걸린 방-밤 | 3,069칸 |
| **2건 이상 겹치는 칸** | **622칸 (20%)** |
| 4건 이상 | 25칸 |
| 한 칸 최대 | **5건** |

드문 일이 아니라서 층 나누기가 필수다(`assignBarLanes`, 저쪽 `cancelledBarLaneMap`).
방마다 체크인 순으로 훑으며 **비어 있는 첫 층**에 놓고, 층 수만큼 예약 트랙을 키운다.
**체크아웃 날 밤은 비어 있으므로** `checkOut === 다음 checkIn` 이면 같은 층에 놓는다.

같은 날 시작하면 **짧은 것을 먼저** 놓는다 — 긴 것이 0층을 먼저 차지하면 짧은 것들이
전부 아래로 밀려 층이 불필요하게 늘어난다. 회귀 테스트: `ops-bar-lanes.test.ts` (9건).

> **`+N` 으로 접어 봤다가 되돌렸다 (2026-09-28).** 「트랙이 커지는 게 보기 힘들다」는
> 지적에 0층만 그리고 나머지를 `+N` 배지로 접은 적이 있다. 두 번 시도했는데 —
> 구간 전체에 배지를 띄우니 **또 하나의 예약 막대처럼** 보였고, 막대 오른쪽 끝에 숫자만
> 붙이니 이번엔 **몇 건이 어느 날짜에 있는지**가 안 보였다. 결론은
> **「모든 예약 막대가 보이고, 줄이 그만큼 자연스럽게 늘어난다」**(사용자 확정).
> 접는 방식을 다시 제안하기 전에 이 문단을 읽을 것.

### 취소 기준 자체

저쪽은 `status === 'cancelled'` 하나만 본다. 우리는 `cancelled` 와 `no_show` 를 함께 보는데,
**`no_show` 는 실제로 0건**이라(2026-09-28 실측: `confirmed` 11,703 · `cancelled` 4,238)
현재 동작은 같다.

### 저쪽과 하나만 다르게 둔 것

저쪽은 취소 막대에 `[Cancelled] ` 접두어를 붙이고 회색(`#8E8E93`)으로 칠한다. 우리는
**회색 + 취소선**으로 표시하고 접두어는 붙이지 않는다 — 「취소만 보기」에서는 **모든 막대가
취소**라 접두어가 전부 붙어 폭만 먹고 손님 이름이 잘린다. 신호는 같고 자리는 덜 먹는다.

## 수동 예약 생성 (2026-09-28 구현)

원본: `BuildingCalendar.jsx` → `ManualBookingModal`(약 800줄) + `functions/index.js` → `createBooking`

**격자에서 기간을 먼저 고르고, 오른쪽 사이드 패널에서 나머지를 적는다.** 입력은 저쪽과
같다 — 체크인/체크아웃, 손님 이름, **총액**, 성인·어린이, 이메일·전화, 메모.

### 기간은 격자에서 고른다 — 체크인 → 체크아웃 (2026-09-28 개정)

저쪽(`handleDateCellClick`)과 같은 흐름이다.

1. 빈 칸의 `+` 를 **누르는 순간** 그 날이 체크인으로 찍힌다. 패널은 아직 안 열린다.
2. 같은 방 위에서 포인터를 움직이면 체크인부터 그 날까지가 **실제 예약 막대와 같은
   자리·모양으로** 미리 칠해진다(「N박 · 10/23」). 막대 끝은 칸 단위로 점프하지 않고 늘어난다.
3. **누른 채 끌어서 놓거나(드래그), 떼었다가 한 번 더 누르면(클릭 두 번)** 그 날이 체크아웃이다
   (그 날 밤은 숙박에 안 들어간다). 이때 패널이 열린다. 키보드는 ←/→ 로 늘리고 Enter 로 확정한다.

**끊기지 않게 한 방법(2026-09-28 개정).** 처음에는 칸마다 `onMouseEnter` 로 격자 상태를 바꿔서,
마우스가 한 칸 옮길 때마다 **격자 전체(객실 × 날짜)가 다시 그려져** 막대가 끊겨 따라왔다.
지금은 `OpsBookingDraft`(`ops-booking-draft.tsx`)가 그 방의 예약 줄 위에 레이어로 깔려
**포인터 좌표로 날짜를 잡고 자기만 다시 그린다.** 칸 경계·막대·빗금 위를 지나도 끊기지 않는다.
팔린 밤 너머를 가리키면 `resolveDraftCheckout()` 이 **벽 앞으로 당겨** 막대가 거기서 멈춘다 —
미리보기와 확정이 같은 함수라 보이는 그대로 잡힌다.

처음에는 `+` 를 누르자마자 입력창이 떴다. 그러면 **기간을 격자에서 볼 수 없고** 날짜를
피커로 다시 골라야 했다(2026-09-28 지적).

세부 규칙 — `checkoutCandidates()`(`src/lib/ops-manual-booking.ts`):

| 상황 | 동작 |
| --- | --- |
| 체크인 칸을 다시 누름 | 무른다(저쪽: 같은 날 두 번 = 취소). 드래그하다 제자리에 놓은 것은 무르지 않고 클릭 모드로 남는다 |
| Esc · 툴바의 「취소」 | 무른다 |
| 이미 팔린 밤을 넘어가는 날 | **넘어갈 수 없다** — 막대가 벽 앞에서 멈추고, 거기서 놓으면 그 날이 체크아웃이다. 팔린 밤의 날짜 자체는 체크아웃으로 고를 수 있다 — 다음 손님이 들어오는 날 아침에 나가는 것은 정상이다 |
| 체크인보다 앞 날짜 | **그 날부터 다시** 고른다 |
| 다른 방의 `+` | 그 방에서 다시 시작한다(저쪽과 같다) |
| 예약 막대를 누름 | 고르던 것을 버리고 상세를 연다(저쪽과 같다) |
| 편집 모드 · 「취소만 보기」 | 고르던 것이 보이지 않는다 |
| `MAX_STAY_NIGHTS`(60) | 그 너머는 누를 수 없다 |

**저쪽과 다르게 한 것 두 가지.**

- 저쪽은 두 번째 클릭에서 겹침을 검사하고 `alert` 로 튕겨냈다. 우리는 **막대가 벽 앞에서
  멈춰** 처음부터 겹치는 기간을 잡을 수 없다 — 튕겨내면 처음부터 다시 골라야 한다.
- 저쪽은 체크인보다 앞을 누르면 앞뒤를 바꿔 **그 날을 체크인, 처음 날을 체크아웃**으로 삼는다.
  그러면 처음 찍은 밤이 숙박에서 빠진다. 우리는 그 날부터 다시 고른다.

고르는 동안 그 방의 줄은 기간 레이어가 덮으므로 막대가 클릭을 가로채지 않는다. 툴바에는
「{방} · {날짜} 체크인 — 이어서 체크아웃 날짜를 누르세요」가 떠서 무엇을 기다리는지 알려 준다.

빈 칸의 `+` 는 **칸 전체가 누르는 자리**다. 글리프만 히트 영역이면 11px 과녁을 맞혀야 해서
실제로 못 누른다. 평소에는 거의 안 보이게 두고 칸에 올렸을 때 드러낸다 — 빈 칸마다 진한
`+` 가 박혀 있으면 정작 봐야 할 가격과 예약이 묻힌다.

### 입력은 **오른쪽 사이드 패널**이다 (2026-09-28 개정)

콘솔의 입력·상세는 공용 `.panel` 프리미티브(오른쪽 패널)를 쓴다 — 컴플레인 등록, 주문·청소
상세 등. 수동 예약만 중앙 모달이라 따로 놀았다(사용자 지적, CLAUDE.md §4). 패널이면 **격자에서
고른 기간이 가려지지 않는다.** 껍데기는 `.panel` · `.fld` · `.btn` 을 그대로 쓰고
(`ops-booking-panel.tsx`), Esc·포커스·스크롤 잠금은 `useAdminPanelA11y` 가 한다. 보내는 중에는
닫히지 않는다.

패널의 날짜 칸은 공용 `AdminDateRangePicker` 다(CLAUDE.md §4a). 격자에서 고른 값이 들어와
있고 **고치는 용도**다 — 창 밖으로 넘어가는 숙박도 여기서 늘린다. 날짜가 잘못되면 **그 자리에
이유를 적는다** — 「만들기」만 흐려 두면 왜 안 되는지 알 수 없다.

### 팔 수 있는 날만 고른다 — 격자 · 피커 · 서버가 같은 규칙 (2026-09-28)

**팔 수 없는 밤** = ① 살아 있는 예약(취소·노쇼 제외)이나 블록이 있는 밤, ② 파는 유닛이 없는 밤
(행의 유닛이 하나도 `1 ≤ minStay < 50` 이 아니다 — 격자에서는 요금 칸이 빈다).

| 자리 | 동작 |
| --- | --- |
| 격자 | 그 밤에는 `+` 가 안 뜨고, 끌어도 막대가 그 앞에서 멈춘다 |
| 패널 피커 | 그 날은 **회색 + 가로줄**로 막힌다. 체크인을 찍은 뒤에는 **그 밤을 넘어가는 체크아웃**도 막힌다. 체크인보다 앞을 누르면 그 날부터 다시 고른다. 「이번 달」 바로가기는 숨긴다 |
| 서버 | 만들기 직전에 **예약·블록 겹침을 다시 본다** → `occupied` + 그 밤들 |

- 격자가 들고 있는 예약은 화면 창(30일·한 달)뿐이라, 피커가 **여는 달마다**
  `loadRoomAvailability` 로 그 달과 다음 달을 읽는다(최대 62일). **아직 모르는 날도 막는다** —
  모르는 날을 열어 두면 그대로 초과예약이 된다. 읽기에 실패하면 그렇다고 적는다.
- 읽기가 늦게 도착해 지금 잡힌 숙박에 막힌 밤이 드러나면, 그 날짜를 적고 「만들기」를 막는다.
- **서버 검사가 필요한 이유:** 화면은 몇 초 전의 사정이고, 그 사이 채널 예약이 들어올 수 있다.
  **Beds24 는 수기 예약의 겹침을 막아 주지 않는다.** 2026-09-28 전까지는 이 검사가 없어서, 피커로
  창 밖 날짜를 고르면 초과예약을 만들 수 있었다.
- 셋 다 **같은 매칭**을 쓴다 — `readOpsRoomUnavailableNights()`(`src/lib/ops-calendar.ts`)가 격자의
  예약→객실 행 매칭(`makeReservationRoomAxis` · `blockRoomAxisKey`)을 그대로 재사용한다. 둘이
  다르게 매칭하면 격자에는 빈 칸인데 서버가 막거나, 그 반대가 된다.
- 유닛 교체 구간을 걸치는 숙박(`unit_changes`)은 피커가 미리 막지 않는다 — 기간에 따라 달라지는
  규칙이라 서버가 **어느 날짜부터 갈리는지**와 함께 거절한다(위 「예약은 roomId 하나에 붙는다」).

### 금액은 **총액**이다

1박 단가가 아니다. Beds24 예약 한 건에 붙는 값이 총액이라 그대로 맞춘다(저쪽 라벨도
`Total Price`). 그래서 **숙박 일수가 바뀌면 그 금액은 더 이상 그 숙박의 값이 아니다** —
날짜를 바꾸면 골라 둔 기준가를 버린다.

### 가격을 찾아 주지 않으면 아무도 안 쓴다

총액을 손으로 계산하려면 날짜별 요금을 따로 봐야 한다. 그래서 **총액 칸 바로 아래에 채널별
합계 카드 두 장**(에어비앤비 · 부킹닷컴)을 두고, 누르면 채워 넣는다. 카드를 고르면
`-10 / -5 / 0 / +5 / +10 %` 조정이 붙는다(저쪽과 같은 값).

- **입력칸이 주인공이고 카드는 바로가기다.** 라벨이 위, 금액이 아래이고 격자 막대와 같은
  채널 색 점이 붙는다.
- **밤별 내역은 2박 이상일 때만, 접어서** 둔다(열 이름 있음). 1박이면 합계가 곧 그 밤이다.
- 처음 구현은 밤별 표와 버튼에 **같은 숫자가 두 번** 나오고 표에 열 이름이 없어 어느 쪽이
  에어비앤비인지 읽을 수 없었다(2026-09-28 지적) — 그래서 위처럼 바꿨다.

**요금을 모르는 밤이 하나라도 있으면 그 채널 카드는 막는다**(채널마다 따로 판정한다). 모르는
값을 빼고 더한 숫자를 「제안」으로 내밀면 그게 그대로 청구된다. 화면에는 추정치라고 적고 직접
입력하게 한다.

### 예약은 roomId **하나**에 붙는다

가격은 소스 유닛에, 최소숙박은 활성 유닛 전부에 쓰지만 예약은 다르다 — Beds24 예약 한 건은
roomId 하나에 속한다. 그래서 **숙박 전체에서 한 유닛**을 골라야 한다.

우리 계정에는 유닛이 교체되는 구간이 있다(듀얼 21개 방이 10/01~10/04 에 둘 다 활성, 그 전후로
주인이 바뀐다). 그 구간을 걸치면 어느 유닛에 붙여도 **뒷날짜에는 잠긴 유닛**이 되어 채널에서
사라지거나 재고가 어긋난다. 저쪽도 같은 결론이라 그런 예약을 **거부한다**.

우리도 거부하되 **어느 날짜부터 갈리는지 같이 알려준다**(2026-09-28 사용자 확인) —
「안 된다」만 하면 사람이 무엇을 고쳐야 할지 모른다.

> **저쪽보다 덜 거부한다.** 저쪽은 날짜마다 「선호 유닛」을 고른 뒤 결과가 전부 같아야
> 통과시킨다. 교체 구간처럼 둘 다 활성인 날에는 선호가 B 를 고를 수 있어, 앞뒤가 A 뿐인
> 숙박이 **괜히 거부**된다. 우리는 **교집합**을 본다 — 모든 밤에 살아 있는 유닛이 하나라도
> 있으면 그걸 쓴다. 고른 유닛이 전 기간 활성이라는 보장은 그대로라 안전하고 헛거부만 준다.

### 손님 이름으로 차단을 만들지 않는다 (2026-09-28 결정)

저쪽은 손님 이름에 `blackout` 이나 `room block` 이 들어가면 **예약이 아니라 차단**을 만든다
(`lowerGuestName.includes(...)`). 화면 어디에도 안 적힌 매직 문자열이다.

**빼기로 했다.** 우리는 차단 전용 모드가 따로 있고 되읽기 검증·재고 스냅샷·보상 롤백까지
갖췄다. 숨은 문자열은 모르면 못 쓰고, 알면 실수로 발동한다 — 실제 손님 이름에 그 단어가
들어가면 예약 대신 차단이 만들어진다.

### 만든 뒤 바로 보인다

웹훅을 기다리지 않는다. 방금 만든 예약이 화면에 없으면 사람은 또 만든다. 만들어진 예약을
**예약 웹훅과 같은 처리기**(`processBeds24WebhookBooking`)에 태워 우리 표에 넣는다 —
형식이 갈리지 않는다. 이 단계가 실패해도 예약은 만들어진 것이므로 실패로 돌리지 않는다.

## 예약 상세 — 사이드 패널 (2026-09-28)

막대를 누르면 **오른쪽 사이드 패널**(`ops-reservation-panel.tsx`, 공용 `.panel`)이 뜬다. 처음에는
객실·채널·날짜 세 줄뿐인 가운데 카드였다 — 손님에게 연락하거나 채널과 이야기하려면
연락처·채널 예약번호·요청 사항이 필요하다(사용자 지적). 저쪽 `ReservationDetailModal` 이
보여주던 것(연락처·국가·인원·총액·수수료·순수익·도착 시각·손님 요청·채널 예약번호)에
Beds24 원본에 있는 나머지를 더했다.

| 섹션 | 내용 (원본 필드) |
| --- | --- |
| 머리글 | 손님 · 건물 · 방 · 채널 · 박수 · 인원 · 취소 여부 |
| 숙박 | 체크인 ─ N박 ─ 체크아웃(요일), 도착 예정(`arrivalTime`), 「체크인 N일 전에 들어온 예약」 |
| 금액 | 총액(`price`) · 수수료(`commission`) · 실수령 · 1박 평균 · 요금 설명(`rateDescription`, 접힘) |
| 손님 | 이메일 · 전화 · 휴대폰 · 국가(국기 + 로캘 이름) · 언어 · 주소 |
| 메시지 | 손님 요청(`comments`) · 내부 메모(`notes`) · 채널 메시지(`apiMessage`, 접힘) |
| 예약 | 채널 · 채널 예약번호(`apiReference`) · Beds24 번호 · 그룹 예약 · 플래그 · 예약/변경/취소 시각(도쿄) |

- **빈 값은 줄째 숨긴다.** 실측(체크인 6월 이후 3,762건): 이메일 50% · 전화 62% · 국가 74% ·
  손님 요청 54% · 내부 메모 17% · 주소 7% · 도착 시각 8건. 「—」가 줄지어 있으면 있는 값이 안 보인다.
- 연락처·번호에는 **복사 버튼**을 단다.
- **국가가 없으면 전화번호로 추정한다**(`resolveGuestCountry`) — Airbnb 는 국가를 거의 안 주고
  전화번호는 늘 준다. 추정한 국가 옆에는 「전화번호로 추정」을 붙인다(국적과 다를 수 있다).
  결정·실측은 `01-decision-log.md` 2026-09-28.
- 시각은 Beds24 가 **UTC** 로 주므로 도쿄로 바꿔 적는다(그대로 보이면 9시간 틀린다).
- **취소된 예약은 Beds24 가 금액을 ¥0 으로 바꾼다** — 0원 매출로 오해하지 않게 그 자리에 적는다.
- 머리글과 숙박은 격자가 이미 들고 있으므로 **읽기를 기다리지 않고** 바로 그린다. 나머지는 막대를
  누른 그 한 건만 `loadReservationDetail` 로 읽는다(30일 창 수백 건의 원본을 격자에 싣지 않는다).

**원본을 통째로 보내지 않는다.** `raw_payload` 에는 **결제 토큰**(`stripeToken` · `pcibookingToken`)이
들어 있다. `buildOpsReservationDetail()`(`src/lib/ops-reservation-detail.ts`)이 **이름을 지정한
필드만** 꺼내고, 토큰이 새지 않는다는 것을 테스트로 못 박았다. 서버는 service-role 로 읽으므로
**조직을 직접 건다**(`organization_id` 조건).

취소는 이 패널의 하단 「예약 취소」에서 한다 — 규칙은 아래 그대로다.

### 채널 예약은 날짜를 못 바꾼다 — 총액은 바꾼다 (2026-09-29 사용자 결정)

| 예약 | 고칠 수 있는 것 |
| --- | --- |
| **직접 · 수기** | 이름 · 이메일 · 전화 · 성인 · 어린이 · 내부 메모 · **날짜 · 총액** |
| **Airbnb · Booking.com** | 이름 · 이메일 · 전화 · 성인 · 어린이 · 내부 메모 · **총액**(매출 기록 보정) |

저쪽은 모든 예약의 날짜·금액을 고칠 수 있었다. 그런데 채널 예약은 **채널이 주인**이다 — Beds24
에서 날짜를 바꿔도 채널 쪽 예약은 그대로라 손님이 받은 예약 내용과 어긋나고, 채널이 변경을
보내면 덮인다. 채널 예약 폼에는 날짜 칸 대신 「{채널}에서 바꿔야 합니다」를 적는다.
**서버에서도 막는다**(`channel_locked`) — 화면이 칸을 숨겨도 요청은 누구나 만들 수 있다.

**총액은 채널 예약도 고친다**(같은 날 두 번째 결정). 바꿔도 **채널이 손님에게 청구하는 금액은
안 바뀐다** — Beds24 기록, 즉 우리 매출 계산만 바뀐다. 매출 기록을 바로잡는 용도라 칸 바로 아래에
그 사실을 적는다.

### 메모는 **내부 메모**(`notes`)에 쓴다 (2026-09-29 사용자 결정)

저쪽은 `comments`(손님 요청)를 덮어써서 **손님이 채널에서 남긴 원래 요청이 사라졌다.** 우리는
Beds24 내부 메모에 쓴다 — 손님에게 안 보이고 원문이 남는다. 페이로드에 `comments` 가 절대 안
들어간다는 것을 테스트로 고정했다.

### 바뀐 것만 보낸다

안 바뀐 필드까지 보내면 그 사이 채널이 바꾼 값(예: 손님이 인원을 늘림)을 화면이 들고 있던 옛
값으로 되돌린다. 저쪽도 보낸 필드만 매핑했다(`hasOwnProperty`). **원래 값은 화면이 아니라 DB 에서**
읽어 다시 비교한다 — 화면이 보낸 「원래 값」을 믿으면 채널 잠금을 우회할 수 있다.

### 저쪽보다 두 가지를 더 본다

저쪽은 날짜를 바꿔도 **아무것도 검사하지 않았다.** 우리는 **새로 묵게 되는 밤**만 골라
(`addedNights` — 줄이는 것은 검사할 것이 없다) —

1. **다른 예약·블록과 겹치는지** — 격자와 같은 매칭(`readOpsRoomUnavailableNights`), 이 예약 자신은
   뺀다(`excludeReservationId`). 겹치면 `occupied` + 그 밤들.
2. **그 예약의 유닛이 새 밤에 팔리고 있는지** — 예약은 roomId 하나에 붙어 있고 수정해도 유닛은
   그대로다. 잠긴 유닛의 밤으로 늘리면 접어둔 listing 이 다시 열린다. 아니면 `no_active_unit`.

날짜 피커도 같은 규칙으로 팔 수 없는 밤을 막는다(`use-room-availability.ts` — 수동 예약 패널과
공용). 이 예약 자신의 밤은 비어 있는 것으로 보고, **묵고 있는 손님은 원래 체크인(과거)을 그대로
둔 채 체크아웃만 늘릴 수 있다**(체크인을 과거로 **옮기는** 것만 막는다).

### 그 밖에

- 이름을 비울 수 없다 · 성인 1명 이상 · 어린이 0명 이상 · 총액 0 이상(저쪽과 같다).
- 취소된 예약은 고치지 않는다(하단에 「닫기」만).
- 국가·도착 시각은 저쪽도 Beds24 쓰기 지원을 확인하지 못해 **보기만** 했다 — 우리도 보기만.
- 고친 뒤 **Beds24 에서 그 예약을 다시 읽어**(`fetchBeds24BookingById`) 예약 웹훅과 같은 처리기로
  우리 표를 맞춘다. 실패해도 Beds24 에는 들어갔으므로 실패로 돌리지 않는다.

## 예약 취소 (2026-09-28 구현)

원본: `BuildingCalendar.jsx` 의 예약 상세 패널 + `functions/index.js` → `cancelBooking`

막대를 누르면 예약 상세가 뜨고, **취소는 거기서만** 한다.

### 되돌릴 수 없다

취소는 Beds24 와 **채널 양쪽**에 나가고, 다시 `confirmed` 로 돌려도 **손님에게 간 취소
통지는 취소되지 않는다.** 저쪽은 `window.confirm` 으로 한 번 물었다.

우리도 한 번 묻되 **무엇이 취소되는지**(손님·객실·날짜)를 그 자리에 적는다 — 브라우저 기본
확인창에는 그게 안 들어가서, 「예」를 누를 때 무엇을 지우는지 모른 채 누르게 된다.

### 사유는 선택이다

저쪽은 사유를 아예 안 받는다. 우리는 받되 **비워도 된다** — 필수로 만들면 급할 때 아무
글자나 넣게 되고 그러면 사유 칸이 쓸모없어진다. 적으면 Beds24 주석에 `Cancelled: {사유}` 로,
비우면 `Cancelled by User` 로 남는다(저쪽과 같은 형식이라 병행 기간에 둘이 같아 보인다).

### 예약번호를 잘못 집으면 **엉뚱한 예약이 취소된다**

`readBeds24BookingId`(`reservation-status.ts`)를 쓰면 안 된다 — 그쪽은 `apiReference` 를
먼저 보므로 **채널 예약코드**(`HMZEYJJX5W`)를 돌려준다. 우리 표의 실제 모양은 이렇다:

```
source_reservation_id   HMZEYJJX5W::room::O207
raw_payload.apiReference HMZEYJJX5W      ← 채널 예약코드
raw_payload.id           92553068        ← Beds24 예약번호 (이걸 써야 한다)
```

그래서 `readBeds24CancelTargetId` 를 따로 뒀다. **숫자일 때만** 취소를 부르고, 아니면
「예약번호를 못 찾았다」고 멈춘다 — 모르는 값으로 취소를 시도하는 것보다 안전하다.

### 서버가 두 가지를 더 본다

1. **이미 취소된 예약은 다시 취소하지 않는다.** 같은 요청을 두 번 보내면 Beds24 에
   주석만 덧씌워진다. 화면에서도 취소된 예약에는 버튼이 없다.
2. **편집 모드에서는 막대를 눌러도 상세가 안 열린다.** 칸 선택이 먼저다 — 막대를 누르다
   상세가 뜨면 드래그 선택이 끊긴다.

취소 후에는 우리 표를 바로 `cancelled` 로 바꾼다. 웹훅이 오면 같은 값으로 덮인다.

## 1박 갭 감지 — 이 기능이 업무 시간을 줄인다 (2026-09-16 정밀 확인)

> **사용자 확인:** 「재고·최소숙박은 내 업무 시간을 굉장히 단축시켜주는 기능이다. 1박 갭 감지가
> 중요하다.」 → 원본 `getCheckInGapInfo` · `gapCellSet` 을 줄 단위로 읽어 아래에 옮겼다.
> **이 규칙은 임의로 단순화하지 않는다.**

### 무엇을 찾는가

**「하루만 비어 있는데 최소 2박이라 아무도 살 수 없는 날」.**

```
11/20        11/21         11/22
예약 있음  │  비어 있음  │  예약 있음
           └ 팔 수 있는 밤은 1박
             그런데 minStay = 2
             → 아무도 못 산다. 이 밤은 그냥 버려진다
```

객실 90개 × 12개월을 눈으로 훑어 이런 날을 찾는 것이 원래 업무였다. **자동으로 찾아서 한 번에
`1박`으로 바꾸는 것**이 이 기능의 전부다.

### 판정식 (원본 그대로)

```js
availableNightsFromDate =
    nextDateStatus === "blocked"   ? 1
  : nextDateStatus === "available" ? 2
  : 0;

isSegmentEntry = (previousDateStatus === "blocked" || previousDateStatus === "past");

isOneNightMinStayGap =
  availableNightsFromDate === 1 && cellMinStay === 2 && isSegmentEntry;
```

세 조건이 **전부** 맞아야 한다.

| 조건 | 뜻 | 왜 필요한가 |
| --- | --- | --- |
| `availableNightsFromDate === 1` | **내일이 막혀 있다** | 이틀 이상 이어지면 2박으로 팔 수 있다 |
| `cellMinStay === 2` | 그 칸의 최소 숙박일이 **정확히 2** | 1이면 이미 팔린다. 3 이상은 다른 정책이다 |
| `isSegmentEntry` | **어제가 막혀 있거나 과거다** | 구간의 **첫날**만 센다. 안 그러면 같은 공실을 여러 번 센다 |

### 「막혀 있다 / 팔 수 있다」의 정의

`available`(팔 수 있다)이 되려면 **다섯 가지가 전부** 참이어야 한다.

| # | 검사 | 아니면 |
| --- | --- | --- |
| 1 | `minStay` 를 숫자로 읽을 수 있다 | `unknown` — **갭으로 세지 않는다** |
| 2 | `override !== "blackout"` | `blocked` (price_blackout) |
| 3 | `1 ≤ minStay < INACTIVE_MINSTAY_THRESHOLD` | `blocked` (inactive_room) |
| 4 | `numAvail > 0` | `blocked` (numavail_zero) |
| 5 | 그 날짜에 예약·블록이 없다 | `blocked` (reservation_or_block) |

**1번이 중요하다.** 가격 데이터가 아직 안 온 칸은 `unknown` 이 되고, `unknown` 은
`availableNightsFromDate = 0` 이라 갭이 되지 않는다. **모르는 것을 갭이라고 하지 않는다** —
잘못 감지해서 minStay 를 바꾸면 실제로 팔리면 안 되는 방이 팔린다.

3번의 `INACTIVE_MINSTAY_THRESHOLD` 는 StayOps 의 `BEDS24_INACTIVE_MIN_STAY_THRESHOLD = 50`
과 같은 개념이다 — **기준을 맞춘다.**

### 객실 하나에 roomId 가 여럿일 때 (듀얼 객실)

여기가 가장 까다롭다. 같은 「201호」가 Beds24 에서 두 계정으로 존재할 수 있다.

- **오늘 날짜**: 팔 수 있는 유닛들 중 `pickPreferredRoomInfo` 로 하나를 고른다
- **어제·내일 날짜**: `getDualRoomPhysicalStatus` 를 쓴다 — **roomId 가 바뀌어도 같은 방으로 본다**

원본 주석이 이유를 적어 놨다:

> *"For dual-account rooms, physical continuity matters more than keeping the same Beds24 roomId.
> If the sellable roomId changes on the next date, the room should still be treated as continuously
> sellable for gap detection."*

**물리적으로 같은 방이면 이어진 것이다.** 이걸 안 하면 유닛이 바뀌는 날마다 가짜 갭이 쏟아진다.

듀얼 객실에는 검사가 둘 더 붙는다 — `roomId` 가 없는 예약(`generic_reservation_without_roomid`)과
`roomId` 가 없는 블록이 그 날짜에 걸리면 **어느 유닛인지 몰라도 막힌 것으로 본다.** 안전 쪽이다.

### 감지 범위와 제외

- **예약이 하나도 없는 객실은 통째로 건너뛴다** (`roomAllReservationsMap[room].length === 0`).
  예약이 없으면 갭이라는 개념 자체가 없다
- **과거 날짜도 감지 대상에는 들어간다.** 다만 「자동 선택」 버튼이 **자기가 과거를 걸러낸다**
- 이미 예약이 찬 칸은 `isGap` 이 아니다 (`!isFullyOccupied && gapCellSet.has(...)`)
- 성능: 화면 범위 전체를 `gapInfoByCellKey` 에 미리 계산해 O(1) 조회한다.
  90객실 × 30일 = 2,700칸을 매 렌더마다 재계산하면 안 된다

### 구현 (2026-09-17)

| | |
| --- | --- |
| 판정식 | `src/lib/ops-gap-detection.ts` — **순수 모듈** |
| 회귀 테스트 | `src/lib/__tests__/ops-gap-detection.test.ts` (14건) |
| 데이터 | `room_daily_rates` (`min_stay` · `num_avail` · `override_kind`) |

저쪽과 다르게 한 것 하나 — **점유 판정에 예약·블락을 함께 본다.** `numAvail` 은 요금 동기화
시점의 값이라 그 뒤에 들어온 예약을 모른다(예약은 웹훅으로 실시간, 요금은 주기 동기화).
그 틈으로 이미 팔린 밤이 갭으로 잡히면 minStay 를 1로 바꿔 놓고 「왜 안 팔리지」가 된다.

듀얼 유닛은 **날짜별로** 판단한다. `rooms.status` 는 `inventory-sync` 가 읽은 **오늘 하루의
스냅샷**이라 「10월 3일에 이 유닛이 팔렸는가」에는 답하지 못한다. 한 행에 유닛이 여럿이면
그 날짜에 **팔 수 있는 유닛**의 값을 쓴다(저쪽 `pickPreferredRoomInfo(sellableInfos)` 와 같다).

창의 **하루 바깥까지** 요금을 읽는다. 판정이 어제·내일을 보는데 가장자리에서 데이터가 끊기면
실제 갭을 「모른다」로 흘려보낸다.

### 유닛이 여럿인 칸 — 운영 값과 가격을 다르게 다룬다 (2026-09-17)

한 캘린더 행 뒤에 Beds24 **방 계정이 여럿**일 수 있다. 오쿠보C 는 셋이고 그중 하나가
**메인**이다.

```
450096 오쿠보 2-1 (메인)  p1 79000  p2 116920  p3 102700   minStay 50 ← 10/1 부터 비활성
496532 1-13-1-2           p1 79000  p2 —       p3 —        minStay 99
648399 OkuboCC            p1 79000  p2 —       p3 —        minStay 2  ← 10/1 부터 판매
```

메인은 Beds24 화면에서 AirBnB · Booking.com · Agoda · Homepage 네 줄을 다 들고 있고,
나머지 둘은 에어비앤비 한 줄만 연결로 받는다. 그래서 **부킹닷컴·아고다 가격은 메인에만
있다.** 판매 중인 유닛에는 없다.

규칙 (`src/lib/ops-rate-merge.ts`, 저쪽 `getDisplayUnitInfosForDate` +
`getMergedRoomChannelPrices` + `getMinStayFromUnitInfos`):

| | 어디서 읽나 | 여럿이면 |
| --- | --- | --- |
| 최소숙박 | **운영 중인 유닛만** (`1 ≤ minStay < 50`) | 가장 **짧은** 값 |
| 재고 | 운영 중인 유닛만 | 하나라도 있으면 **있다** |
| blackout | 운영 중인 유닛만 | 하나라도 걸리면 **막힘** |
| 가격 p1·p2·p3 | 운영 중인 유닛 **먼저, 없으면 그 행의 아무 유닛** | 항목마다 **처음 나오는 값** |

운영 중인 유닛이 하나도 없으면 그 칸은 **비운다**(저쪽 `EMPTY_PRICE_CELL`).

두 가지를 헷갈리면 안 된다.

- **가격 폴백을 안 걸면** 10/1 부터 부킹닷컴 가격이 사라진다 — 판매 유닛에 없기 때문이다
- **최소숙박까지 폴백을 걸면** 메인의 `50` 이 올라와 「팔 수 없는 날」이 된다.
  그건 팔리는 방을 안 판다는 뜻이다

폴백은 **항목별**이다. 유닛 하나를 골라 그 행을 통째로 쓰지 않는다 — p1 은 판매 유닛 것,
p2 는 메인 것으로 섞이는 것이 정상이다.

### 쓰기 대상 유닛 — **가격과 최소숙박이 서로 다른 유닛으로 간다** (2026-09-24)

읽기는 위 병합 규칙으로 메인을 몰라도 되지만, **쓸 때는 대상 유닛을 골라야 한다.** 저쪽 주석
그대로다 — *"Price writes must target the source price row, while inventory/min-stay writes
must continue to target the active roomId."*

| 쓰는 것 | 대상 | 왜 |
| --- | --- | --- |
| 가격 `p1·p2·p3` | **가격 소스 유닛**(메인) | 가격은 연결로 퍼진다. 소스가 아닌 곳에 쓰면 반영되지 않는다 |
| 최소숙박 · 재고 | **그 날짜에 운영 중인 유닛** | 재고는 유닛마다 따로다. 안 파는 유닛의 minStay 를 바꿔도 아무 일도 안 일어난다 |

오쿠보C 2026-10-01 이면 — **가격은 450096, 최소숙박은 648399.** 둘이 다른 유닛이다.

실제 채널 가격은 그대로다. 그래서 쓴 뒤 **다시 읽어 대조한다**(워커의 readback 검증) —
소스는 직접 설정값만(`includeLinkedPrices=false`), 연결 유닛은 전파값까지(`true`) 읽는다.
기준이 달라 한 번의 조회로 합칠 수 없다.

판정은 순수 모듈 `src/lib/beds24/write-target-room.ts` + 테스트 12건.

### 페이지를 쭉 내리고, 날짜 머리글이 따라온다 (2026-09-24 확정)

**격자 안에서 스크롤하지 않는다.** 객실이 90개라 안에서 굴리면 작은 창 안을 들여다보는 꼴이
된다. 페이지를 쭉 내리면서 보고, **날짜 머리글과 조작 패널이 화면을 따라온다.**

`position: sticky` 가 붙어 있었는데도 안 먹던 이유 — 격자 카드의 `overflow: hidden`(둥근
모서리용)이 **그 카드를 스크롤 상자로 만든다.** 그러면 안쪽 sticky 는 페이지가 아니라 카드에
붙고, 카드가 페이지와 함께 올라가니 머리글도 같이 사라진다.

`overflow: clip` 으로 바꿨다 — 모서리만 깎고 **스크롤 상자를 만들지 않는다.**

- 머리글은 **불투명해야 한다**(`--card2`). 붙어 있는 동안 아래 객실 줄이 비치면 숫자가 겹친다
- 조작 패널도 `sticky` 다. 아래쪽 객실을 고르는데 조작부가 위에 남아 있으면 값을 넣으려고
  매번 올라와야 한다
- 스크롤 상자는 `.adm .content` 이고 그 위에 상단 바(62px)가 있다 — `top` 은 그 안쪽
  기준이라 0 부터 센다

> 한 번은 반대로 갔었다 — `.ops` 에 `height: 100%` 를 주고 격자 안에서 스크롤하게. 머리글은
> 고정됐지만 **보이는 객실이 한 화면치로 줄어** 정작 아래를 훑을 수가 없었다. 이 화면은
> 「길게 내려 보는」 화면이다.

가격을 보려면 일곱 번이다. 라벨 자체를 눌러 달력에서 고르면 한 번에 간다.

| 뷰 | 고르는 것 | 공용 프리미티브 |
| --- | --- | --- |
| 30일 | **날짜** — 고른 날이 창의 **시작일**이 된다 | `AdminDatePicker` |
| 월간 | **달** | `AdminMonthPicker` |

**달력은 새로 만들지 않는다.** 이 콘솔에는 달력이 하나뿐이다(CLAUDE.md §4a). 여기만의 것은
방아쇠에 뜨는 글자뿐이라, 공용 `AdminDatePicker` 에 `display` 를 선택적으로 더했다 —
고른 날이 곧 30일 창의 시작일이라 방아쇠에는 `09/23 → 10/22` 로 범위가 떠야 한다.

월간 뷰의 URL 파라미터는 `month` 가 아니라 **`ym`** 이다 — 공용 월 선택기가 그 키로 이동한다.
우리만 다른 이름을 쓰면 그 컴포넌트를 못 쓰고 달력을 또 만들게 된다. 월 선택기는 화살표를
스스로 들고 있으므로 그쪽에서는 우리 화살표를 접는다.

### 선택 (2026-09-24 구현)

평소에는 **읽는 화면**이다. 「가격 수정」을 눌러야 칸이 선택 대상이 된다 — 저쪽도 `priceMode`
토글로 갈라 놓았다. 읽으려다 실수로 바꾸는 일을 막는 것이 이 구분의 목적이다.

판정은 순수 모듈 `src/lib/ops-calendar-selection.ts` + 테스트 19건.

#### 스코프 바 — 세 축이 곱해진다

| 축 | 내용 |
| --- | --- |
| 객실 | 전체 / 개별 |
| 기간 | **주 단위** — 요금이 주말가·평일가로 주 단위로 움직인다 |
| 요일 | 전체 / **주말·금~일** / **평일·월~목** / 개별 |

**빈 축은 「전체」다.** 요일을 하나도 안 고르면 전 요일이지, 아무 날도 아닌 게 아니다.
「이번 주 × 금토일 × 3층 전부」가 칩 세 번으로 나온다.

**사내 주말은 금·토·일이다.** 일반적인 토·일이 아니다 — 주말 요금이 금요일부터 붙는다.
여기를 토·일로 바꾸면 **금요일이 평일가로 팔린다.** 테스트로 못 박았다.

주는 **월요일 시작**이고 일요일은 앞 주에 붙는다. 일요일을 다음 주로 밀면 주말 한 덩어리가
두 칩으로 쪼개진다.

#### 직접 조작도 같이 쓴다

- 칸 **드래그** — **누른 칸부터 지금 칸까지의 사각형**(스프레드시트처럼). 누른 칸의 상태가
  방향을 정한다(꺼진 칸에서 시작하면 켜고, 켜진 칸에서 시작하면 끈다). 매 칸 다시 판단하면
  드래그가 깜빡인다. **Shift+클릭**은 직전에 누른 칸부터 사각형을 더한다
  - **2026-09-28 개정 — 인식이 끊기던 것.** 예전에는 칸마다 `mouseenter` 로 지나간 칸만 켰다.
    빨리 움직이면 브라우저가 중간 칸 이벤트를 건너뛰어 **칸이 빠졌고**, 칸 하나마다 격자 전체를
    다시 그려 더 무거워졌으며, 예약 막대 줄·칸 경계를 지나면 끊겼다(사용자 지적).
  - 지금은 스크롤 영역 **한 곳**에서 포인터를 받아 **좌표로 (행, 열)을 잰다** — 막대·빗금·경계
    위에서도 끊기지 않는다. 두 모서리로 사각형을 정하므로(`applyDragRect`) 지나간 경로와 무관하게
    빠지는 칸이 없고, **모서리가 바뀔 때만** 다시 그린다. 포인터를 붙잡아(capture) 격자 밖에서
    놓아도 끝나고, 화면 위·아래 끝에 가면 **저절로 스크롤**한다. 커서는 십자(`cell`)
- **객실명 클릭** — 그 행 전체
- **날짜 머리글 클릭** — 그 열 전체. **Shift 를 누르면 직전 날짜부터 범위**
- 전부 골라져 있는 묶음을 다시 누르면 **해제**된다

#### 축을 바꿔도 직접 찍은 칸은 살아남는다

선택을 통째로 덮어쓰면 칸을 하나씩 손본 것이 축을 건드릴 때마다 날아간다. **직전 축이
기여했던 키만** 걷어내고 새 축을 얹는다(저쪽 `scopeCellKeysRef` 와 같다).

> **고른 칸과 직전 축 키는 한 state 에 둔다**(2026-09-24 회귀). 축 키를 `useRef` 에 넣고
> `setSelection` 업데이터 **안에서** 갱신했더니, 객실 체크를 풀어도 그 칸이 선택에 남았다 —
> React 는 업데이터를 **두 번 부르고**(StrictMode · 동시성 렌더) 두 번째 호출 때는 ref 가 이미
> 새 값이라 걷어낼 대상을 못 찾는다. 판정식(`applyScopeToSelection`)은 처음부터 멀쩡했고
> **부르는 쪽이 업데이터를 불순하게** 썼다. 한 state 로 묶으면 업데이터가 순수해져 몇 번을
> 불려도 같은 결과가 나온다. 회귀 테스트 4건이 그 성질을 고정한다.

#### 자동으로 빠지는 것

- **과거 날짜.** 지난 밤의 가격을 바꿔도 아무 일도 안 일어나는데 「42칸」에는 들어가 사람을
  속인다
- **팔린 밤.** 단, blackout(Beds24 차단)·재고 블록·**취소된 예약**은 막지 않는다 —
  차단해 둔 날도 가격은 미리 정해 둘 수 있고 취소된 예약은 이미 없는 예약이다.
  저쪽 `isCellPriceBlocked` 가 `hasBlockingReservation` 만 보는 이유다

**빠진 개수를 따로 알리지 않는다**(2026-09-24). 한때 「판매된 N칸 제외」 배지를 띄웠는데,
칸을 고를 때마다 나타났다 사라져 **그 아래 격자가 위아래로 들썩였다.** 팔린 칸은 격자에서
빗금으로 이미 보이고, 남는 숫자(**고른 칸 수**)가 무엇이 바뀔지를 정확히 말한다.
현재 가격이 없어 빠지는 칸은 **확인 단계**가 「{count}칸이 바뀝니다」로 말해 준다.

#### 선택하는 동안 화면이 움직이지 않는다

칸을 고르는 내내 위쪽 줄 높이가 고정이다.

- 조작 패널은 **편집 모드 내내** 떠 있다. 선택이 비면 「격자에서 칸을 고르세요」로 자리만 지킨다
- 「현재 → 변경」 자리에 최소 폭을 줘, 값이 들어왔다 나가도 옆 버튼이 좌우로 밀리지 않는다
- 1박 갭 버튼은 **첫 줄**에 있다. 아래 줄이면 갭 칸을 고를 때마다 줄이 새로 생긴다
- 아래 줄(확인 · 경고 · 결과)은 **값을 치거나 누른 뒤에만** 열린다 — 선택 상태로는 열지 않는다
- **줄 높이를 못 박는다.** 현황 줄의 「해제」 버튼(22px)은 고른 칸이 있을 때만 나타나는데,
  높이를 내용에 맡기면 글자만 있을 때 24px · 버튼이 생기면 32px 이 되어 **칸을 고를 때마다
  8px 씩 격자가 밀린다**
- **가로 스크롤바도 숨긴다.** 넘칠 때만 생기는 막대가 줄 높이를 바꿔 격자를 밀어낸다
  (콘솔의 `.ops__props` 와 같은 처리)

### 「선택 해제」 (2026-09-28)

세 패널(가격 · 최소 숙박일 · 차단) 아래의 버튼은 **격자에서 고른 칸을 비운다** — Beds24 에는 아무것도
안 보낸다. 원래 라벨이 「해제」 하나라 **차단 모드의 「차단 해제」와 헷갈렸다**(사용자 지적) —
「선택 해제 / 選択解除 / Clear selection」으로 바꿨다. **Esc** 도 같다(편집 모드에서, 입력칸에 커서가
없을 때만). 가격 패널에서는 적어 둔 금액도 같이 비운다 — 남겨 두면 다음에 고른 칸에 그 값이 걸린다.

**저장하면 선택이 비워진다**(2026-09-30 버그 수정). 가격 · 최소 숙박일(「1박으로」 포함)을 보내 **접수되면**
고른 칸을 비운다. 예전에는 저장한 칸이 선택에 남아, 다음에 한 칸을 누르면 앞서 저장한 4칸까지 잡혀
「5칸 저장」이 됐고 요약(객실 4개까지 + 「외 N」)에서 새로 누른 객실이 가려졌다. 접수가 실패하면 선택을
그대로 둔다(고쳐서 다시 보낼 수 있게). 반영 결과 문구는 패널에 남는다. 차단은 원래 끝나면 비운다.

### 조작 패널은 **격자 오른쪽**이다 (2026-09-24 확정)

시안(`3-select.dc.html`)대로 세로 카드로 둔다. 한때 위쪽 가로 바로 만들었다가 되돌렸다.

**이유는 세로다.** 위에 두면 그만큼 격자가 아래로 밀리는데, **가격을 고칠 때야말로 객실을
아래까지 길게 봐야 한다.** 옆에 두면 세로를 0 먹는다(편집 모드 상단 소모 115px → 41px).

옆에 두니 세로로 쌓을 자리가 생겨 따라온 것들:

- **무엇을 고치는가**를 머리말에 적는다 — 「아라키초A · 402 · 501 · 502 / 11/20 → 11/22」.
  「9칸」만으로는 **어느 방 어느 날인지 모른 채** 적용하게 되는데, 가격은 채널로 그대로 나간다
- 현재 평균 → 변경을 **큰 숫자 두 개**로 나란히. 가로 바에서는 작게 한 줄에 박혀 잘못 읽기 쉬웠다
- 빠진 칸은 **개수가 아니라 이유**를 적는다 — 「기준이 될 현재 가격이 없습니다」
- 채널 규칙을 화면에 적는다 — 「에어비앤비 가격만 씁니다. 부킹닷컴은 Beds24 가 자동으로
  맞춥니다.」 없으면 「왜 부킹닷컴은 안 바뀌지?」가 나온다
- 확인이 **2단계**다 — 「다음 · N칸 확인」 → 「N개 객실 N칸이 바뀝니다」
- 두 버튼은 **크기가 다르다**(1 : 1.6). 같으면 어느 쪽이 기본인지 안 읽힌다

패널은 **내용 높이만큼만 선다**(`align-self: flex-start`). 늘리면 격자 높이(객실 90개 =
화면 끝까지)를 따라가고, 바닥에 붙은 「다음 · N칸 확인」이 프리셋에서 한참 아래로 떨어진다 —
값을 누르고 적용하려면 마우스가 화면을 세로로 가로질러야 한다. **시안은 객실 11개짜리라 이
차이가 안 보인다.**

편집 모드가 아닐 때 스코프 바는 **바탕이 없다.** 전에는 그 줄이 격자 카드 *안*에 있어
`--surface2` 가 머리띠처럼 읽혔는데, 패널을 옆으로 빼면서 카드 밖으로 나오자 페이지 바탕과
색이 비슷해 **희미한 빈 상자**로 보였다. 편집 모드일 때만 카드가 된다.

가로 바에서 가져온 것: 모드 토글 없는 금액·퍼센트 한 덩어리, 고른 칸 수·조작 안내를 **줄을
새로 만들지 않고** 스코프 바 오른쪽에 붙이는 것.

### 조작 — 가격 · 「1박으로」 (2026-09-24 구현)

계산은 순수 모듈 `src/lib/ops-price-adjustment.ts` + 테스트 18건. **여기서 나온 숫자가 그대로
채널로 나간다** — 반올림 한 번, 기준가 하나만 틀려도 잘못된 가격에 팔린다.

#### 모드 토글이 없다

금액과 퍼센트를 한 줄에 둔다. 금액을 쓰면 % 배지가 계산되고, 퍼센트를 누르면 금액이 채워진다
(기준은 현재 평균). 다만 **적용 결과는 다르다.**

| | 적용 |
| --- | --- |
| 금액 | 고른 칸 **전부**를 그 값으로 |
| 퍼센트 | 칸마다 **자기 현재가** × (1 + %/100), 반올림 |

퍼센트는 칸마다 결과가 다르므로 「변경」을 **범위**로 보여준다(`¥44,000 ~ ¥66,000`).
프리셋은 저쪽과 같은 `-20 · -10 · -5 · +5 · +10 · +20 · +30`.

#### 현재 가격이 없는 칸은 빠진다

퍼센트는 기준가가 있어야 계산되고, 「원래 안 팔던 날」에 값을 넣는 것은 다른 행위다
(저쪽도 `if (!currentPrice.hasPrice) return;` 로 거른다). **몇 칸이 빠졌는지 알려준다.**

#### 확인을 한 번 더 받는다

첫 버튼 「다음 · {count}칸 확인」 → 확인 단계 [취소] [**{count}칸 반영**]. (2026-09-29 사용자 요청으로 확인
버튼의 문장 「{rooms}개 객실 {count}칸이 바뀝니다. 채널에 그대로 나갑니다.」를 짧게 줄였다 — 버튼 안에서
두 줄로 차 거추장스러웠다. 채널 규칙은 바로 위 안내 줄이 말한다.) 그리고 비정상 값에는
경고를 띄운다 — 0원 이하, 현재가의 절반 아래, 현재가의 세 배 위. **막지는 않는다**(있을 수
있는 조정이다) 대신 반드시 눈에 띄게 한다.

#### 저장은 `p1`·`p3` 에 같은 값, `p2` 는 **건드리지 않는다**

부킹닷컴 가격은 Beds24 가 에어비앤비 가격에서 규칙으로 파생시킨다. 우리가 직접 쓰면 그
규칙과 충돌한다(저쪽이 `p1`·`p3` 만 쓰는 이유).

#### 서버가 같은 계산을 다시 한다

화면이 보낸 금액을 그대로 믿지 않는다. 보이는 것과 보내는 것이 갈라지면 「¥30,000 으로
바꿨다」는데 다른 값이 나간다. 실패 사유는 **코드로** 돌려주고 문구는 화면이 사전에서 고른다 —
서버가 한국어를 돌려주면 일본어·영어 사용자에게 한국어가 뜬다.

#### 낙관적 표시

접수하면 **서버 응답을 기다리기 전에** 화면의 가격을 새 값으로 바꾸고 점선 밑줄을 친다.
왕복 동안 옛 값이 보이면 사람은 「안 됐나?」 하고 다시 누른다(저쪽도 같은 이유로 앞으로 당겼다).

#### 「1박으로」 — 이 기능의 목적

1박 갭 칸이 선택에 들어 있으면 그 자리에서 `minStay = 1` 로 보낸다. 찾아만 주고 못 고치면
**오히려 일이 한 단계 는다** — Beds24 를 따로 열어 하나씩 바꿔야 하기 때문이다.

가격과 달리 **그 날짜에 운영 중인 유닛**으로 간다. 실측(오쿠보C · 2026-10-01):

```
같은 칸,  가격  → 450096 (소스/메인)
          최소숙박 → 648399 (그날 파는 유닛)
```

### 반영되면 새로고침 없이 보인다 (2026-09-28)

**문제.** 가격·최소숙박을 바꾸면 Beds24 에는 들어가는데 **우리 화면은 새로고침해야** 새 값이
보였다(사용자 지적). 원인 셋이 겹쳐 있었다.

1. 서버 액션은 **접수만 하고** 돌아온다. 그때 다시 그린 화면(`revalidatePath`)은 워커가 쓰기
   전이라 옛 값이다. 워커는 몇 초 뒤 Beds24 에 쓰고 `room_daily_rates` 를 고치지만 화면은 모른다.
2. 작업 상태 조회(`getPriceJobStatus`)는 있었지만 **부르는 곳이 없었다.**
3. 가격은 흐린 새 값을 먼저 그렸지만 표시 순서가 `pending ?? 서버값` 이라 **거둬지지 않았고**,
   최소숙박은 그마저 없었다. 패널은 접수만 되면 「반영 완료」라고 했다 — 사실은 큐에 있을 뿐이었다.

**지금.** 격자의 `runWrite`(`ops-write-tracker.ts`)가 한 흐름으로 묶는다.

```
누름 ─▶ 새 값을 흐리게(점선 밑줄) ─▶ 접수 ─▶ 상태를 묻는다(0.8초 → 최대 2초 간격, 90초까지)
                                              │
            ┌─────────────────────────────────┼──────────────────────────┐
         완료·일부 실패·시간 초과                  실패                     접수 실패
            │                                 │                          │
   router.refresh() 로 서버 데이터만 다시 받음   흐린 값을 거두고 되돌림      흐린 값을 거둠
   → 새 데이터가 도착하면 흐린 값을 거둠           + refresh
```

- **새로고침이 아니다.** `router.refresh()` 는 서버 컴포넌트 데이터만 다시 받는다 — 스크롤·선택·
  열린 패널이 그대로다. 갭 표시·변경 이력 점도 같이 새로 온다.
- **흐린 값은 「새 데이터가 도착했을 때」 거둔다**(렌더 중 비교). 반영 전에 도착한 재렌더에서
  거두면 옛 값으로 튄다 — 그래서 끝난 쓰기의 값만 거둔다.
- 패널은 **Beds24 에 실제로 들어간 뒤에** 「반영 완료」라고 한다. 일부만 들어갔으면 그렇게,
  실패면 되돌렸다고, 90초가 지나도 안 끝났으면 「아직 반영 중 — 끝나면 격자에 나타난다」고 적는다
  (워커가 멈춘 게 아니면 크론이 이어 받는다).
- 패널을 닫아도 툴바에 **「Beds24 에 보내는 중…」** 표시가 반영이 끝날 때까지 남는다.
- 블록은 큐가 아니라 **동기**로 쓰므로(아래 「차단」) 응답이 올 때 이미 반영돼 있다 — 이 흐름이
  필요 없다.

#### 속도 — 누르고 진하게 바뀔 때까지 (2026-09-28)

「반영 완료」까지 걸리는 시간을 줄이려고 경로의 군더더기를 걷었다.

| 자리 | 전 | 후 |
| --- | --- | --- |
| 워커 깨우기 | `void kickWorker()` — 배포 환경은 응답과 함께 함수를 멈춰 **다음 크론(실측 수십 분 지연)까지** 밀릴 수 있었다 | `after(kickWorker)` — 응답 뒤에도 끝까지 돈다. 앞선 작업이 있으면 큐가 빌 때까지 이어서(최대 5건·50초) |
| 「저장」 응답 | `revalidatePath` 로 **페이지 전체 재렌더**를 응답에 실었다(접수만 했는데) | 뺐다 — 반영 뒤 화면이 스스로 다시 받는다 |
| 작업 완료 기록 | 연결 유닛 전파 확인(경고용, 되읽기 + 재시도)까지 **끝내고** 완료 | 완료를 **먼저** 적고 그다음 확인 |
| 이력·로컬 반영 | 방마다 차례로 | 방끼리 동시에 |
| 흡수한 형제 작업 | 하나씩 update | 한 번에(`in`) |
| 화면 상태 확인 | 0.8초부터 최대 2초 간격 | 0.5초부터 최대 1.5초 |
| 확정 표시 | 데이터 다시 받기가 **끝나야** 점선이 걷혔다 | 완료가 확인되는 **즉시** 진하게, 다시 받기는 뒤에서 |

**「1박으로」가 실패로 끝나던 것도 여기서 잡혔다.** Beds24 는 minStay 1 을 빈칸으로 저장하고
다른 설정이 없으면 **그 날짜 줄 자체를 빼고** 돌려준다(저쪽 2026-09-25 `3e44564` 실측). 되읽기
검증(`price-write-verification.ts`)이 줄이 없으면 「모른다」로 봐서, Beds24 에는 들어갔는데도
재시도 끝에 실패로 끝났다 — 새 화면은 그 실패를 보고 값을 되돌렸을 것이다. 이제 **줄이 없으면
1박**이다. 단 그 방의 응답이 **통째로 비었으면** 읽기 실패일 수 있어 여전히 「모른다」.

### 가격을 쓴 뒤 **링크 가격까지** 우리 표를 맞춘다 (2026-09-29)

우리는 소스 `p1` 만 쓴다. 부킹닷컴(`p2`)·`p3` 와 **실제로 파는 자식 유닛의 `p1`** 은 Beds24 링크가
계산하는데, 그 값을 우리 표로 가져오는 것은 요금 동기화뿐이고 그게 GitHub Actions 라 **실측 약
6시간 간격**이다(15분 설정). 그동안 격자의 부킹닷컴 가격과 수동 예약 패널의 「부킹닷컴 합계」가
옛 값이었다. 워커가 작업을 끝낸 뒤 **쓴 날짜만** `includeLinkedPrices` 로 다시 읽어(소스 + 그 소스를
가리키는 유닛) `price1~3` 을 그대로 옮긴다(`refreshLinkedLocalRates`). 실패해도 작업은 이미 끝났다.

### 가격 링크가 **웹훅에 지워지던** 버그 (2026-09-29)

가격을 쓸 유닛은 `rooms.external_price_source_room_id` 로 정한다(방 마스터 동기화가 Beds24 가격 규칙에서
채운다). 그런데 **예약 웹훅이 방 정보를 갱신할 때 이 칸을 `null` 로 덮었다** — 웹훅은 가격 규칙을
모르는데 기본값이 `null` 이었다(`room-sync.ts` `upsertRoom`). 예약이 들어오는 **판매 유닛일수록**
링크가 지워졌다: 전수 대조에서 Beds24 에는 링크가 있는데 우리 DB 에서 빠진 유닛 **17개**(648399,
6015xx 등 10/01 교체 후 판매 유닛).

증상: 그 방의 가격을 고치면 소스뿐 아니라 **링크된 판매 유닛에도 직접** 보낸다. Beds24 는 링크 칸의
직접값을 무시하므로 되읽기가 그 유닛에서 실패해 작업이 **「일부 실패」**로 끝났다(채널 가격은 소스를
통해 제대로 나갔다 — 표시만 틀렸다).

고침: 가격 소스를 **모르면(`undefined`) 그 칸을 아예 보내지 않는다**(`buildRoomIdentityUpdate`,
`src/lib/beds24/room-identity.ts`, 회귀 테스트 3건). 방 마스터 동기화만 값을(없으면 `null` 을)
명시적으로 넘긴다. 지워진 17개는 배포 후 **가격 소스 칸만** 실시간 Beds24 값으로 복구했다(전체 마스터
동기화는 다른 건물 이름·객실 구성까지 덮을 수 있어 쓰지 않았다).

### 작업 큐와 워커 (2026-09-24 구현)

화면에서 Beds24 로 **바로 쏘지 않는다.** `beds24_price_jobs` 에 접수만 하고 워커가 처리한다.

이유 둘 — Beds24 V2 의 **5분 크레딧이 계정 단위**라 객실 90개를 즉시 순차 POST 하면 예약
동기화·웹훅과 다투고 429 가 난다. 그리고 **모바일에서 특히 중요하다**: 접수하고 응답하면
화면을 꺼도 서버가 끝낸다.

| | |
| --- | --- |
| 접수 | `enqueueBeds24PriceJob` — **여기서 대상 유닛이 정해진다**(가격→소스, 최소숙박→운영 중) |
| 워커 | `runNextPriceJob` — 락 하나로 직렬화, 한 번에 최대 5작업 / 45초 |
| 실행 | 접수 직후 호출(정상 경로) + 크론 `3,13,…,53`(안전망) |

#### 쓰고 나서 **반드시 다시 읽는다**

**Beds24 는 값을 반영하지 않고도 `success: true` 를 돌려준다.** 되읽어 대조하지 않으면 반영
실패가 「성공」으로 기록되고, 화면에는 바뀐 값이 뜨는데 채널에 나가는 가격은 옛것이다.

- 우리가 POST 한 유닛 → `includeLinkedPrices=false`(직접 설정값만). 연결된 Daily Price 쪽에
  잘못 쓰인 요청을 성공으로 오인하지 않기 위해서다
- 연결 유닛 → `includeLinkedPrices=true`, **`p1` 만**. 안 맞아도 **작업을 실패로 만들지
  않는다** — 소스 쓰기는 성공했고 전파가 늦은 것일 수 있다. 크게 로그를 남기고 그 유닛의
  로컬 값은 건드리지 않아 다음 동기화가 실제 값으로 채우게 둔다
- **잘린 응답으로는 「일치한다」를 증명할 수 없다.** 쪽이 남으면 검증 실패로 다룬다
- 링크 전파에 시간이 걸려 최대 3회 재시도(500ms · 1s)

`minStay 1` 은 Beds24 가 **빈칸으로 돌려준다.** 양쪽을 1 로 정규화해 비교하지 않으면
**「1박으로」가 성공했는데 실패로 보고된다.**

#### 검증을 통과한 값만 우리 표에 바로 반영한다

다음 요금 동기화(최대 15분 뒤)를 기다리면 그동안 화면이 옛 값을 보여주고, 사람은 반영이 안
된 줄 알고 한 번 더 바꾼다.

#### 요금 동기화가 **양보한다**

저쪽이 실제로 겪은 사고다 — 작업이 POST 후 검증 재시도를 도는 사이 주기 동기화가 Beds24 에서
옛 가격을 읽어 캐시를 덮었고, 「Beds24 가 되돌렸다」는 허위 이력까지 남겼다. `rates-sync` 는
대기 중인 작업이 있으면 `202 yielded_to_price_job` 으로 물러난다.

#### 크레딧 쿨다운은 **모든 경로가** 본다

429 를 맞거나 잔여 크레딧이 10 미만이면 `beds24_sync_locks` 의 `api_cooldown` 을 켠다.
쓰기만 쉬면 크론이 계속 긁어 한도가 안 풀린다. 쉬는 시간은 Beds24 가 알려준 리셋 +2초,
15~300초로 가둔다.

#### 그 밖에

- **멈춘 작업 회수** — 15분 넘게 `processing` 이면 되돌린다. 서버리스에서는 함수가 중간에
  사라지는 일이 정상 범주다
- **작업 합치기** — 같은 건물·같은 종류·2분 안이면 하나로 합친다. 같은 날짜는 나중 것이
  이기고, **항목별이 아니라 날짜 단위로 통째로** 덮는다. 안 합치면 중간 상태가 채널로
  나간다(5만원 → 6만원인데 5만원이 실제로 팔릴 수 있다)
- 작업 락 수명 15분 — 저쪽은 5분이었다가 *"백오프 + 검증 재시도로 6분 넘게 도는 job의 락이
  만료되어 두 번째 job이 같은 roomId에 동시에 POST"* 하는 사고를 겪고 올렸다

#### 실측 (2026-09-24)

11개월 뒤 빈 날짜(201호 · 2027-08-15)에서 `minStay 2 → 3 → 2`.

```
POST → 되읽기 검증 → 로컬 반영 → completed
Beds24 직접 조회:  2027-08-15 minStay=3   (바뀌었다)
원복 후:           2027-08-13~17 minStay=2 (구간이 원래대로 합쳐졌다)
```

무효 쓰기(같은 값)만으로는 **POST 가 아무것도 안 해도 통과한다.** 그래서 실제로 바꿨다가
되돌려 확인했다. 요금 동기화 양보도 확인 — 대기 작업을 두니 `202 yielded_to_price_job`.

### 읽기는 쪽을 나눠야 한다 (2026-09-17 회귀)

PostgREST 는 한 번에 **1,000행까지만** 준다(Supabase `db-max-rows` 기본값). 초과분은 오류가
아니라 **조용히 잘린다** — 화면은 멀쩡히 그려지고 데이터만 사라진다.

30일 창 하나에 필요한 행:

| 표 | 행 수 | 1,000행 |
| --- | --- | --- |
| `room_daily_rates` | 객실 91 × 32일 = **2,912** | **넘는다** |
| `reservations` | 716 | 아직 밑 |
| `room_blocks` | 5 | 밑 |
| `rooms` | 91 | 밑 |

첫 화면에서 실제로 터졌다 — **9/28 부터 가격·최소숙박이 통째로 비어 보였다.** 값이 없는 칸은
「안 판다」로 그리므로 잘린 것과 팔지 않는 날을 화면에서 구별할 수 없다. 갭 판정도 그 구간을
전부 `unknown` 으로 봤다.

`readAllPages()` (`src/lib/ops-calendar.ts`) 로 네 표를 전부 쪽 나눠 읽는다. 예약은 지금
1,000행 밑이지만 같이 고쳤다 — 넘는 순간 **예약 막대가 조용히 사라지고**, 그건 이미 팔린 방을
비었다고 보여준다는 뜻이다.

쪽을 나눌 때는 **정렬이 유일해야 한다.** 같은 값이 여럿이면 쪽 경계에서 어떤 행은 두 번 오고
어떤 행은 한 번도 안 온다. 날짜 뒤에 `id` 를 붙여 순서를 못 박았다(요금은 `(room_id,
stay_date)` 가 유니크라 그대로 확정).

### 고치는 방법

| 버튼 | 값 | 언제 |
| --- | --- | --- |
| **1박으로** | `minStay = 1` | **이게 본래 목적이다.** 버려지던 하루를 판다 |
| 2박으로 | `minStay = 2` | 되돌리기 |
| 직접 입력 | 3 ~ 30 | 성수기·장기 정책 |

`POST /setMinStay` 로 `cells: [{roomName, date, dateKey, roomId, minStay}]` 를 보낸다.
서버가 roomId 별로 묶어 `calendar: [{from, to, minStay}]` 로 Beds24 에 쓴다.
**가격과 같은 큐를 탈 수 있다** — 응답에 `queued: true` + `jobId` 가 오면 워커가 처리한다.

### 원본에 있던 함정 — 고쳐서 가져온다

원본 주석에 실패 기록이 남아 있다. **같은 자리를 밟지 않는다.**

| 원본에서 있었던 일 | 우리가 할 것 |
| --- | --- |
| 롤백이 `catch` 에만 있었다. `fetch` 는 `.catch` 로, 타임아웃은 `Promise.race` 로 resolve 되어 **catch 에 도달하지 않았다.** 서버가 실패해도 낙관적 minStay 가 화면과 캐시에 남아 건물을 바꿨다 와도 되살아났다 | **실패 경로를 하나로 모으고** 낙관적 패치를 반드시 되돌린다 |
| 「최신 서버에서 재조회」라는 주석만 있고 **실제 재조회가 없었다.** 화면이 낙관적 값만 보고 있었다 | 쓰기 직후 **되읽어 대조한다** (「쓰기 안전장치」 ③과 같은 원칙) |
| 롤백 백업으로 `roomPrices` 와 `priceCache` **전체를 `structuredClone`** 했다. 수 MB 가 되어 적용 직후 메인 스레드가 멈칫했다 | **바뀌는 칸의 이전 `m` 값만** 백업한다 |
| 타임아웃 180초 → 실패로 처리하지만 **Beds24 에는 적용됐을 수 있다** | 「타임아웃 — 반영됐을 수 있음」을 **실패와 구분해서** 보여준다 |

## 뷰 모드 두 가지 — 월간 / 30일 (2026-09-16 확인)

저쪽 캘린더에는 격자의 **가로축을 정하는 토글**이 하나 더 있다(`viewMode`). 지금까지 못 보고
있었는데, 실제로는 이쪽이 **평소에 쓰는 모드**다.

| | `monthly` (월간) | `rolling` (30일) |
| --- | --- | --- |
| 버튼 표시 | `Monthly` | `30-Day View` |
| 가로축 | 그 달 **1일 ~ 말일** | **시작일부터 30일** |
| 시작일 | 달의 1일 | **어제** (오늘 − 1일) |
| 이동 | 이전 달 / 다음 달 | **± 30일** |
| Today | 이번 달로 | **시작일을 다시 「어제」로** |

**핵심은 「어제부터 30일」이다.** 오늘을 왼쪽 끝에 붙이지 않고 **하루만 뒤로 물려서** 시작한다 —
어제 체크아웃이 왼쪽 끝에 걸려 보이고, 그 오른쪽이 오늘 이후 한 달이다. 월간 뷰는 달이 바뀔 때
「오늘」이 격자 오른쪽 끝에 처박히는데, 30일 뷰는 **언제 열어도 오늘이 항상 왼쪽 근처**다.

원본 그대로:

```js
// rolling: rollingStartDate 부터 30일
for (let i = 0; i < 30; i++) days.push(start.add(i, 'day'));

// Today / 모드 전환 시
const yesterday = new Date();
yesterday.setDate(yesterday.getDate() - 1);
setRollingStartDate(yesterday);
```

**날짜 점프 검색도 이 모드로 떨어진다.** 날짜를 입력해 이동하면(`applyDateSearch`) **무조건
`rolling` 로 전환하고 그 날짜를 시작일로 잡는다.** 「2026-12-24 를 보자」가 곧 「12/24 부터
30일을 보자」다. 그리고 그 검색의 **Today 버튼은 도쿄 기준 오늘**을 넣는다
(`Intl.DateTimeFormat` / `Asia/Tokyo`) — StayOps 의 도쿄 운영일 규칙과 이미 같다.

### 우리는 이렇게 가져온다

- **두 모드 전부 가져온다.** 기본값은 **30일 뷰**로 둔다 — 열자마자 오늘이 보여야 한다.
- 30일 뷰의 시작일 계산은 **도쿄 기준 어제**다. 브라우저 로컬 시간으로 `setDate(-1)` 하지 않는다
  (저쪽은 로컬 기준이라 밤에 열면 하루 어긋날 수 있다 — **이건 고쳐서 가져온다**).
- 이동 단위는 ±30일. **월 단위로 바꾸지 않는다** — 바꾸면 오늘이 다시 격자 끝으로 밀린다.
- 월간 뷰의 월 이동은 StayOps 의 `shiftMonthKey()` 를 쓴다 (CLAUDE.md 4a).

## 선택과 조작 — 저쪽 실제 설계 (2026-09-16 재확인)

앞서 「드래그 방식이라 모바일에 못 옮긴다」고만 적었는데, **실물을 보니 훨씬 정교했다.**
드래그는 여러 선택 수단 중 하나일 뿐이고, **이미 모바일에서도 쓸 수 있는 구조가 들어 있다.**

### 평소에는 일반 캘린더, 「가격 수정」을 누르면 선택 모드

`priceMode` 토글이다(`isBulkSelectMode = priceMode || gapEditMode`). 이 구분이 중요하다 —

| | 일반 모드 | 선택 모드(가격 수정) |
| --- | --- | --- |
| 칸을 누르면 | **예약 생성 시작** (시작일 → 종료일 두 번 클릭) | 셀 선택 토글 |
| 스코프 바 | 없음 | **뜬다** |
| 드래그 | 스크롤 | 범위 선택 |

**예약 생성과 블록은 별도 탭이 아니라 캘린더에서 바로 한다.** 빈 칸을 클릭하면 시작일,
한 번 더 클릭하면 종료일이 되어 그 범위로 예약 생성 흐름이 열린다. 같은 날을 두 번 누르면
0박이라 선택이 취소된다. 다른 방을 누르면 시작점이 그 방으로 옮겨간다.

### 스코프 바 — 자유도 높은 일괄 선택

선택 모드에서 위에 뜨는 세 줄. **이것이 이 화면의 핵심 조작부다.**

```
Scope    1 rooms × 11 dates = 11 cells

ROOMS    [전체] [201호] [202호] [301호] [302호] [401호] [402호] [501호] …
PERIOD   [전체] [10/26–11/1] [11/2–11/8] [11/9–11/15] [11/16–11/22] …   ← 주 단위
DAYS     [매일] [주말·금~일] [평일·월~목] [월][화][수][목][금][토][일]
```

- **주 단위 기간 칩** — 「11/9–11/15」처럼 한 주씩. 임의 기간이 아니라 주 단위로 끊어
  누르기 쉽게 했다
- **요일 프리셋** — 같은 프리셋을 다시 누르면 해제된다
- **선택 결과를 식으로 보여준다** — `1 rooms × 11 dates = 11 cells`

> **「주말」은 금·토·일이다.** 월~목이 평일이다(원본 주석: *「금·토·일(사내 주말가) / 월~목」*).
> 일반적인 토·일이 아니므로 **그대로 따라야 한다.** 요금 체계가 그 기준으로 짜여 있다.

이 구조는 **드래그 없이도 원하는 범위를 정확히 집는다.** 「다음 주 주말 전 객실」이 세 번의
탭으로 끝난다 — 모바일에서도 그대로 쓸 수 있다는 뜻이다. 모바일을 위해 새 방식을 발명할 필요가
없고, **이 스코프 바를 좁은 화면에 맞게 배치하면 된다.**

### 선택에서 자동으로 빠지는 것

`buildSelectableCells` 가 거른다.

- **과거 날짜는 못 고른다** — 오늘 이전은 아예 선택 대상이 아니다
- **예약·블록이 있는 칸은 자동으로 빠진다.** 몇 개가 빠졌는지(`skipped`) 세어 알려준다

**이걸 반드시 가져와야 한다.** 「42칸 선택」이라 해 놓고 그중 5칸이 이미 팔린 방이면 그 5칸은
바뀌지 않는데, 말해주지 않으면 바뀐 줄 안다.

판정은 모드마다 다르다 — 가격 모드는 `isCellPriceBlocked`, 갭 모드는 `isCellOccupied`.

### 그 밖의 선택 수단

- **객실 이름의 체크박스** — 그 행 전체 선택
- **날짜 열 머리글 클릭** — 그 열 전체 선택, **Shift 로 범위**
- **드래그** — 사각 범위

## 모바일 입력 설계

**스코프 바를 그대로 쓴다.** 위에서 확인했듯 드래그 없이도 정확한 선택이 되는 구조가 이미 있다.

좁은 화면에서 달라지는 것:

- 세 줄(ROOMS/PERIOD/DAYS)을 **가로 스크롤되는 칩 줄**로. 줄당 한 축
- `1 rooms × 11 dates = 11 cells` 식은 **항상 고정**으로 보인다
- 격자에서의 개별 탭 토글은 그대로 (드래그가 아니라 탭이므로 스크롤과 충돌하지 않는다)
- 드래그 선택은 **데스크톱 전용**으로 둔다 — 없어도 스코프 바로 다 된다

확인 단계는 아래 「확인 단계」와 동일하다.

### 확인 단계

저쪽에도 2단계 흐름이 있다(`step 1: 입력 → step 2: 확인`). **그 구조를 가져오되 내용을
강화한다.**

```
아라키초A · 402, 501, 502호     3개 객실
11월 20일 ~ 26일 · 주말(금~일)   3박
가격  ¥26,100 → ¥30,000          9칸 변경

⚠ 예약이 있어 제외된 칸 2개
⚠ 평소의 1/10 이하인 칸 1개

[ 취소 ]  [ 9칸 저장 ]
```

- **칸 수를 센다.** 예상보다 크면 손이 멈춘다
- **제외된 칸을 밝힌다** — 위 「선택에서 자동으로 빠지는 것」
- 퍼센트 모드는 칸마다 결과가 다르므로 **범위**로 보여준다
- **비정상 값 경고** — 0원, 평소의 1/10 이하, 10배 이상. 막지 않되 한 번 더 묻는다

## 쓰기 안전장치

### 켜기 전까지 쓰지 않는다

**병행 기간에는 이쪽이 Beds24 에 쓰지 않는다**(전체 계획의 확정 원칙). 화면과 로직은 만들되
실제 전송은 막아 둔다.

그러면 「켜기 전에 어떻게 검증하는가」가 남는다. 세 단계로 푼다.

**① 미리보기 모드** — 보낼 페이로드를 화면·로그에 그대로 보여주고 전송은 하지 않는다.
사람이 눈으로 대조할 수 있다.

**② 한 방·짧은 기간으로 실전 확인** — 전환 직전에 **거의 안 쓰는 객실 하나**의 **짧은 기간**에만
실제로 써 본다. Beds24 화면에서 반영을 확인하고 되돌린다. 전면 전환은 그다음이다.

**③ 쓴 것을 되읽어 대조한다** — 쓰기 직후 같은 구간을 다시 읽어 **의도한 값이 들어갔는지** 확인한다.
POST 성공 응답만으로는 부족하다.

### 그 밖에

- **크레딧 인식 대기** — Beds24 는 5분 단위 크레딧 제한이 있다. 응답 헤더
  (`x-five-min-limit-remaining` / `-resets-in`)를 읽어 잔여가 적으면 선제 대기한다.
  헤더 이름은 소문자다 — 2026-08-07 에 대문자로 찾다가 가드가 한 번도 발동하지 않은 적이 있다
  ([01-beds24-integration.md](../engineering/01-beds24-integration.md)).
- **실패 복구** — 여러 칸을 쓰다 중간에 실패하면 **어디까지 됐는지** 남기고 사람에게 보여준다.
  조용히 반만 적용된 상태가 제일 나쁘다.
- **누가 무엇을 바꿨는지 남긴다** — 가격 변경 이력. 저쪽에도 `price_change_logs` 가 있다.

  `collapseCellRuns`). 27칸이 9줄이 된다. 건물이 하나뿐인 수정이면 줄마다 건물 이름을 되풀이하지 않는다.
  최대 400칸 + 「외 N칸」.
- **방 이름은 판매 캘린더 행과 같은 규칙**(`opsRoomDisplayName`): Beds24 유닛 라벨을 표시 라벨로
  (가부키초 `203#`·`K203` → `203`, STAY ARI `O302` → `302`, 아라키초 `201_2` → `201`). 같은 방의 유닛 둘이
  같은 날 같은 값으로 남았으면 한 칸으로 센다. **건물 이름은 보는 사람 언어로**(`cleaning.buildingLabels` —
  이번에 STAY ARI · 사노 키 추가, 사노 = 佐野 / Sano), 언어는 서버가 세션에서 정한다.
- **7일씩** 거슬러 읽는다(「이전 7일 더 보기」). 건수로 끊으면 한 번의 대량 수정이 쪽 경계에서 잘리기
  때문이다. 그래도 경계에 걸친 수정은 붙일 때 합친다(`appendChangeGroups` — 범위 요약은 합칠 수 있다).
  한 창에서 2만 칸을 넘으면 잘렸다고 알린다.

### Beds24 에서 바꾼 최소숙박 · 차단도 남긴다 (2026-09-29, 사용자 요청)

재고 웹훅은 값 없이 「바뀌었다」만 준다. 요금 동기화가 우리 표를 덮기 **전에** 이전 값과 비교해 달라진 칸을
`price_change_logs`(작성자 「Beds24」, `adjust_mode = 'beds24'`)에 남긴다 — 예전엔 가격(`price1`)만 봤다.
누가 바꿨는지는 Beds24 가 주지 않으므로 **「Beds24」로만** 적는다(사용자 확인).

| 무엇 | 어느 유닛 | 조건 |
| --- | --- | --- |
| 가격 `price1` | 가격 소스 유닛만(링크 슬롯은 따라 바뀐다) | 이전 값을 알 때 |
| 최소숙박 `min_stay` | 모든 유닛 | 이전·이후 **둘 다 판매 중 값(1~49)** — 50 으로 잠그거나 푸는 것은 유닛 교체라 안 센다 |
| 차단 `blackout` | 판매 중인 유닛(최소숙박 1~49) | `override` 가 blackout ↔ 그 밖. 값은 **1 = 차단 · 0 = 열림** |

공통: 오늘 이후만. **우리 앱이 쓴 값은 안 잡힌다** — 워커·차단 쓰기가 우리 표를 먼저 고쳐 두므로 동기화 때는
같은 값이다. 가격 개입 판정은 여전히 `price1` 만 읽는다. 순수 함수 `detectExternalRateChanges`
(`src/lib/beds24/external-price-changes.ts`, 테스트 6건).

**우리 앱이 건 차단도 변경 이력에 남긴다** — 같은 표 `field = 'blackout'`, `adjust_mode = 'block'`, 작성자는 누른
사람. 한 번 누른 것은 같은 시각이라 한 줄로 묶인다(차단은 큐 작업이 아니라 `job_id` 가 없다 — 묶음 키는
`job_id` 또는 `<adjust_mode>:<시각>`). 방당 유닛 하나만 적는다. 마이그레이션
`202609290002_price_change_logs_blackout.sql`(허용 값에 `blackout` 추가, 운영 적용).

**같은 방의 유닛 둘이 같이 바뀐 줄은 한 번으로 센다**(변경 이력 · 칸 호버 둘 다).

**칸 호버 이력을 행 키로 붙인다.** 예전에는 로그에 적힌 라벨 그대로 칸을 찾아, Beds24 유닛 라벨로 남은
줄(STAY ARI `O302`, 가부키초 `203#`)이 격자의 「302」·「203」 칸에 안 떴고 건물이 달라도 번호가 같으면 섞일 수
있었다. 이제 `room_id` → 행 키(`건물::표시 라벨`)로 붙인다.

### Beds24 전송 — 「우리가 보낸 것이 제대로 들어갔나」

- 원본 둘을 시각순으로 합친다: 가격·최소숙박 작업 `beds24_price_jobs`, 차단·해제 `beds24_block_logs`(신설 —
  `docs/engineering/04-data-model.md`). 30줄씩 「더 보기」.
- 상태 배지: **반영됨**(되읽기 검증까지 통과) · **일부 실패** · **실패** · **대기** · **보내는 중**. 실패는
  객실별 사유(워커의 되읽기 불일치 문구 그대로), 차단 실패는 사유 코드를 사람 말로(`hsReasons`, ko/ja/en).
- **멈춤 감지.** 대기·보내는 중이 3분(`SEND_STALL_MINUTES`)을 넘으면 빨갛게 세우고 「지금 보내기」 —
  워커를 응답 뒤에 깨운다. **실패한 작업을 다시 넣지는 않는다**(대개 값·유닛 문제라 또 실패하고, 그 사이
  누가 다른 값을 넣었을 수 있다 — 다시 하려면 캘린더에서 새로 고친다).
- 「지금 보내기」는 **첫 작업을 기다렸다가 결과를 말한다** — 보냄 · 보낼 것 없음 · Beds24 쿨다운(N초) · 다른
  전송 진행 중 · 연결 오류(`hsSendResult`). 남은 작업은 응답 뒤에. 처음엔 응답 뒤에만 돌려 잠금이 막혀 있어도
  「반응 없음」으로만 보였다(2026-09-29 사용자 보고).
- **고아 잠금 회수**(`breakOrphanedWorkerLock`). 같은 날 실측: 개발 서버에서 Supabase 연결이 끊겨 워커 잠금 해제가
  실패했고, 잠금 TTL(15분) 동안 「지금 보내기」와 캘린더 열기가 전부 「남이 돌고 있다」로 조용히 멈췄다. 이제
  잠금을 잡은 지 1분이 넘었는데 `processing` 인 작업이 하나도 없으면 죽은 잠금으로 보고 회수한다(본 그 잠금일 때만
  — lockId 비교). 살아 있는 워커는 잡자마자 작업을 `processing` 으로 바꾸므로 헷갈리지 않는다.
- 대기·보내는 중인 줄이 있으면 첫 쪽을 4초마다 다시 읽는다.
- 도구줄 「이력」 버튼의 빨간 숫자 = 최근 7일 전송 실패(작업 실패·일부 실패 + 차단 실패) + 멈춘 대기 작업
  (`countOpsHistoryAlerts`). 실패는 알림 없이 조용히 쌓이므로 버튼이 먼저 말한다.

## 속도 — 버튼 · 건물 이동이 느리던 것 (2026-09-30, 사용자 보고)
